## Как читать эту главу

**🎯 Interview core:** вопросы 1–7, 9–17, 19–22. **🔬 Optional precision:** вопросы 8 и 18. Первый проход восстанавливает выбор механизма и его жизненный цикл; второй добавляет повторный вход, границы времени и совместное управление нагрузкой.

```text
поток событий → выбрать нужные значения → допустить работу в очередь
  → занять место → выполнить попытку → решить о повторе
    → дождаться завершения → записать исход в позицию входа
отмена владельца проходит через все ожидающие и работающие слои
```

Предпосылки: [таймеры и цикл событий](09-event-loop-and-scheduling.md), [обещания, отмена и актуальность](10-promises-and-async-await.md). Браузерная интеграция отмечена отдельно. В примерах со временем первый вызов обёртки принимаем за начало отсчёта. Все отметки указаны в миллисекундах от этого момента. Для расчёта считаем, что таймеры срабатывают без опоздания; настоящий браузер может выполнить их позже.

## Ментальная модель

Представьте мастерскую. Приёмщик может дождаться, пока клиент закончит уточнять заказ; диспетчер — отправлять сводку с ограниченной частотой; два мастера — брать не больше двух заказов одновременно; после временной неисправности можно попробовать снова. Это четыре разных ограничения.

| Вопрос | Механизм |
|---|---|
| Нужен последний ввод после паузы? | Отложенный вызов после затишья — debounce |
| Нужны обновления и во время непрерывного потока? | Ограничение частоты — throttle |
| Нельзя одновременно держать больше N незавершённых операций? | Ограничитель одновременной работы — concurrency limiter |
| Временный отказ допускает безопасную повторную попытку? | Политика повторов — retry |

Мастера здесь обозначают незавершённые операции, а не потоки процессора. Ограничитель сетевых запросов сам по себе не переносит тяжёлые вычисления с основного потока. Очередь и число попыток нуждаются в собственных пределах.

## Связное объяснение в формате вопросов и ответов

### 🎯 1. Что debounce делает с потоком вызовов?

Он объединяет близкие вызовы и откладывает выполнение до паузы. Каждый новый вызов сдвигает момент допустимого выполнения. Для поиска обычно нужен последний текст, а не каждый промежуточный префикс.

В примерах ниже **время указано в миллисекундах от первого обращения к обёртке**. Для первого обращения прошло 0 мс; все остальные отметки отсчитываются от него. Буквы A, B и C обозначают разные значения, которые мы передаём при вызовах.

Пусть задержка `wait` равна 100 мс, а обработчик должен выполняться только после паузы (`leading=false`, `trailing=true`):

| Когда вызываем обёртку | Какое значение передаём |
|---|---|
| В начале примера, 0 мс | A |
| Через 40 мс от начала | B |
| Через 80 мс от начала | C |

Выполнится только обработчик со значением **C — через 180 мс от начала**: после последнего обращения прошло ещё 100 мс без новых вызовов. Значения A и B были заменены более свежим входом.

Для такого расчёта считаем, что таймер выполняется сразу по истечении задержки. В настоящем браузере он может сработать позже; здесь мы сравниваем правила debounce, а не предсказываем точное время запуска.

Похоже на ожидание тишины после аплодисментов: новый хлопок продлевает ожидание. Метафора объясняет паузу, но не ведение результатов и ошибок. Непрерывный ввод может откладывать выполнение бесконечно: это свойство простого варианта, а не потерянный таймер.

### 🎯 2. Что означают leading и trailing?

`leading` разрешает вызов в начале серии, `trailing` — отложенный в конце. Сначала согласуйте, что считается серией и нужен ли повтор для единственного события.

| `leading`: выполнять в начале? | `trailing`: выполнять после паузы? | Один вызов | Несколько вызовов до паузы |
|---|---|---|---|
| `false` — нет | `true` — да | После паузы | Последний после паузы |
| `true` — да | `false` — нет | Сразу | Только первый; каждый вход продлевает запрет |
| `true` — да | `true` — да | Только сразу | Первый сразу и последний после паузы |

Если и `leading`, и `trailing` равны `false`, наш вариант сообщает об ошибке. Если оба параметра равны `true`, единственный вход не исполняется повторно в конце. Это осмысленный выбор, совпадающий с привычной формой Lodash; название debounce само по себе не определяет все дополнительные правила.

### 🎯 3. Как сохранить последние аргументы и this?

Нужно хранить аргументы последнего нужного входа и его получателя. Обычная функция-обёртка получает `this` при вызове; стрелка внутри таймера может использовать уже сохранённые данные.

```js
function trailingDebounce(fn, wait) {
  let timer = null;
  return function (...args) {
    if (timer !== null) clearTimeout(timer);
    const receiver = this;
    timer = setTimeout(() => {
      timer = null;
      fn.apply(receiver, args);
    }, wait);
  };
}
```

Это намеренно минимальная версия для объяснения: она не проверяет параметры и не предоставляет отмену. Полный договор далее. Если сделать внешнюю обёртку стрелкой, вызывающий объект уже не сможет задать ей свой `this`. Сохранённые объекты могут измениться до вызова: копируется список аргументов, а не глубокий снимок всех значений.

### 🎯 4. Чем cancel отличается от flush?

`cancel()` удаляет ожидающий вызов и забывает его аргументы. `flush()` немедленно выполняет уже ожидающий отложенный вызов; если такого вызова нет, ничего не делает. В нашем варианте оба завершают текущую серию: следующий вход начинает новую.

При закрытии формы обычно нужна отмена. При явном действии «применить сейчас» может понадобиться принудительное выполнение. Автоматически выполнять сохранение при каждом уничтожении владельца нельзя: пользователь мог отменить действие.

`cancel()` не отменяет сетевой запрос, который обработчик уже успел начать. Для него нужен собственный сигнал. `flush()` при `leading=true` и единственном входе не создаёт дубликат.

### 🎯 5. Как выглядит debounce с полным оговорённым договором?

Ниже учебный вариант: настройки — логические значения, задержка — конечное число от 0 до 2³¹−1. Вызов обёртки и `flush` возвращают `undefined`. Результат `fn` не раздаётся вызывающим; это **не обещающий debounce** и не полная замена библиотеке.

```js
function debounce(fn, wait, { leading = false, trailing = true } = {}) {
  if (typeof fn !== "function") throw new TypeError("fn");
  if (!Number.isFinite(wait) || wait < 0 || wait > 2147483647) {
    throw new RangeError("wait");
  }
  if (typeof leading !== "boolean" || typeof trailing !== "boolean" ||
      (!leading && !trailing)) throw new TypeError("edges");
  let timer = null;
  let args;
  let receiver;
  function invoke() {
    const a = args, r = receiver;
    args = receiver = undefined;
    fn.apply(r, a);
  }
  function expire() {
    timer = null;
    if (args) invoke();
  }
  function wrapped(...a) {
    const first = timer === null;
    if (timer !== null) clearTimeout(timer);
    timer = setTimeout(expire, wait);
    if (first && leading) {
      args = a; receiver = this;
      invoke();
    } else if (trailing) {
      args = a; receiver = this;
    }
  }
  wrapped.cancel = () => {
    if (timer !== null) clearTimeout(timer);
    timer = null;
    args = receiver = undefined;
  };
  wrapped.flush = () => {
    if (timer === null) return;
    clearTimeout(timer);
    timer = null;
    if (args) invoke();
  };
  return wrapped;
}
```

Таймер устанавливается до первого вызова, а сохранённые данные очищаются до выполнения `fn`. Поэтому внутренний повторный вход в обёртку относится к уже существующей серии, а завершение старого вызова не стирает его новые аргументы.

Синхронное исключение из `fn` при первом вызове или `flush` получает вызывающий код; из таймера — среда. Возвращённое `fn` обещание здесь не ожидается. Для асинхронной работы обработчик обязан сам наблюдать свой отказ, как браузерная интеграция в упражнении EX10. `wait=0` без первого немедленного вызова означает таймерную задачу, а не выполнение в текущем стеке.

### 🎯 6. Чем throttle отличается от debounce?

Ограничение частоты сохраняет возможность выполнять работу при непрерывном потоке. Новый вход не должен постоянно отодвигать уже назначенное окно. Например, положение прокрутки нужно показывать во время движения, а поиск можно отложить до паузы.

Сравним на одинаковых вызовах. Задержка — 100 мс. Время снова отсчитываем от первого обращения к обёртке; для расчёта таймеры не опаздывают.

| Когда вызываем обёртку | Какое значение передаём |
|---|---|
| В начале примера, 0 мс | A |
| Через 40 мс от начала | B |
| Через 80 мс от начала | C |
| Через 140 мс от начала | D |

**Debounce с выполнением только после паузы** (`leading=false`, `trailing=true`) выполнит обработчик один раз — со значением **D через 240 мс от начала**. Последний вход был на отметке 140 мс, затем прошло 100 мс тишины.

**Наш throttle с немедленным первым и отложенным последним вызовом** (`leading=true`, `trailing=true`) выполнит обработчик три раза:

1. Со значением **A сразу, в начале примера**.
2. Со значением **C через 100 мс от начала**: за первое окно пришли B и C, и сохранено последнее значение.
3. Со значением **D через 200 мс от начала**: вход D попал в следующее окно и дождался его окончания.

Debounce всё время сдвигал ожидание после каждого нового входа. Throttle сохранил ближайшее назначенное выполнение, поэтому обновление появилось и до окончания всей серии.

Это не серверная квота запросов за календарную минуту. Для визуальных обновлений бывает правильнее [объединение через requestAnimationFrame](09-event-loop-and-scheduling.md), потому что оно связано с возможностью отрисовки, а не с выбранным числом миллисекунд.

### 🎯 7. Какой throttle мы реализуем?

У нашего варианта окно начинается с фактического выполнения. Первый вход выполняется сразу при `leading=true`; новые входы во время окна заменяют отложенный при `trailing=true`. В конце окна отложенный вход выполняется и открывает новое окно. Пустой конец окна просто снимает блокировку.

```js
function throttle(fn, wait, { leading = true, trailing = true } = {}) {
  if (typeof fn !== "function") throw new TypeError("fn");
  if (!Number.isFinite(wait) || wait <= 0 || wait > 2147483647) {
    throw new RangeError("wait");
  }
  if (typeof leading !== "boolean" || typeof trailing !== "boolean" ||
      (!leading && !trailing)) throw new TypeError("edges");
  let timer = null;
  let args;
  let receiver;
  function invoke(a, r) { fn.apply(r, a); }
  function expire() {
    timer = null;
    if (!args) return;
    const a = args, r = receiver;
    args = receiver = undefined;
    timer = setTimeout(expire, wait);
    invoke(a, r);
  }
  function wrapped(...a) {
    if (timer === null) {
      timer = setTimeout(expire, wait);
      if (leading) invoke(a, this);
      else { args = a; receiver = this; }
    } else if (trailing) {
      args = a; receiver = this;
    }
  }
  wrapped.cancel = () => {
    if (timer !== null) clearTimeout(timer);
    timer = null;
    args = receiver = undefined;
  };
  return wrapped;
}
```

В отличие от debounce, уже поставленный таймер не перезапускается при каждом входе. Задержка строго положительная: нулевую в этом учебном договоре отклоняем. `cancel()` забывает отложенное и разрешает новую серию; он не откатывает первый вызов. Возврат — `undefined`, ошибки и асинхронный результат принадлежат `fn` так же, как в debounce.

### 🔬 8. Почему границы времени и повторный вход требуют точного договора?

Если вход и таймер допустимы в один момент, важен реальный порядок обработки задач. Нельзя без дополнительного условия требовать единственный порядок только по одинаковым отметкам времени. Поздний таймер нашего throttle открывает следующее окно от своего фактического выполнения: он не выпускает «накопившиеся» вызовы залпом.

В debounce и throttle состояние меняется **до** пользовательской функции. Та может повторно вызвать обёртку или отменить её. Проверяйте оба направления: старое завершение не должно терять новый вызов, а отмена из первого обработчика действительно должна убрать окно. Настоящий браузер может задерживать и ограничивать таймеры; управляемые часы проверяют наш договор, а не устройство браузерного планировщика.

### 🎯 9. Почему Promise.all не ограничивает число запросов?

Он наблюдает исходы переданных значений, а не выдаёт разрешения на запуск. Если сначала вызвать все загрузки, ограничивать уже поздно.

```js
const started = [];
const tasks = ["A", "B", "C"].map(id => {
  started.push(id);
  return Promise.resolve(id);
});
console.log(started);
console.log(await Promise.all(tasks));
```

Оба массива — `["A", "B", "C"]`; работа началась при обходе, до ожидания агрегата. Ограничителю нужны **фабрики задач (task factories)**, например функция, которая начнёт запрос только после получения места.

### 🎯 10. Какой инвариант хранит ограничитель?

Число занятых мест всегда между нулём и пределом. Запуск увеличивает счётчик один раз; любой исход, включая синхронный выброс и усвоенный thenable, освобождает место один раз. Очередь хранит ещё не вызванные фабрики.

```text
pending → slot reserved → factory called → operation settles → slot released
             active++                                      active--
```

Резервировать место нужно до вызова пользовательского кода: фабрика может синхронно добавить новую задачу. Нормализация через `Promise.resolve().then(factory)` позволяет наблюдать синхронный выброс, обычное значение и обещание одним путём.

### 🎯 11. Как реализовать очередь, чтобы каждый ожидающий получил исход?

Ниже очередь первого пришедшего — первого запущенного (**FIFO**). `run` возвращает отдельное обещание; `close` отклоняет ожидающих и запрещает новые задачи. По умолчанию хранится не более 1000 ожидающих. Существующие работающие задачи при закрытии продолжают занимать места до завершения.

```js
function createLimiter(concurrency, { maxQueue = 1000 } = {}) {
  if (!Number.isInteger(concurrency) || concurrency < 1) {
    throw new RangeError("concurrency");
  }
  if (!Number.isInteger(maxQueue) || maxQueue < 1) {
    throw new RangeError("maxQueue");
  }
  let active = 0;
  let closed = false;
  let closeReason;
  const queue = [];
  function pump() {
    while (!closed && active < concurrency && queue.length) {
      const job = queue.shift();
      job.detach();
      active++;
      function finish(ok, result) {
        active--;
        if (job.signal?.aborted) job.reject(job.signal.reason);
        else if (ok) job.resolve(result);
        else job.reject(result);
        pump();
      }
      Promise.resolve().then(() => {
        job.signal?.throwIfAborted();
        return job.task({ signal: job.signal });
      }).then(value => finish(true, value), error => finish(false, error));
    }
  }
  return {
    get activeCount() { return active; },
    get pendingCount() { return queue.length; },
    run(task, { signal } = {}) {
      if (closed) return Promise.reject(closeReason);
      if (typeof task !== "function") return Promise.reject(new TypeError("task"));
      if (signal?.aborted) return Promise.reject(signal.reason);
      if (active >= concurrency && queue.length >= maxQueue) {
        return Promise.reject(new RangeError("queue full"));
      }
      return new Promise((resolve, reject) => {
        const job = { task, signal, resolve, reject, detach };
        function detach() { signal?.removeEventListener("abort", onAbort); }
        function onAbort() {
          const index = queue.indexOf(job);
          if (index < 0) return;
          queue.splice(index, 1);
          detach();
          reject(signal.reason);
        }
        signal?.addEventListener("abort", onAbort, { once: true });
        queue.push(job);
        pump();
      });
    },
    close(reason = new DOMException("Queue closed", "AbortError")) {
      if (closed) return;
      closed = true;
      closeReason = reason;
      for (const job of queue.splice(0)) {
        job.detach();
        job.reject(reason);
      }
    },
  };
}
```

Сигнал — настоящий `AbortSignal`, фабрика — обычная функция. Работа резервируется синхронно, а фабрика вызывается в микрозадаче. При отмене уже выбранной задачи до её вызова проверка предотвращает старт. При отмене ожидающей удаляется запись и её обработчик. Не вызывайте `run` с уже начатым Promise вместо функции.

Массив с `shift`/удалением — ясная учебная реализация, а не обещание O(1). Для большой очереди нужен подходящий контейнер и отдельный профиль нагрузки. Сюда не входят приоритеты, распределённая очередь, восстановление после перезапуска и бессрочный поток.

### 🎯 12. Почему отменённую работающую задачу нельзя сразу вычесть из active?

Сигнал сообщает об отмене, но операция может его игнорировать. Если сразу освободить место и запустить следующую, физически незавершённых операций окажется больше предела. Наш вариант ждёт фактического исхода и затем отклоняет результат точной причиной отмены, даже если операция вернула успех.

Поэтому отмена ожидающей задачи немедленна, а обещание работающей при игнорировании сигнала может оставаться ожидающим. Нужен кооперативный источник или собственный гарантированный способ завершить работу. Назвать тайм-аут освобождением места недостаточно: [race не останавливает проигравшую операцию](10-promises-and-async-await.md).

`close()` сам по себе не отменяет работающих. Их сигналы принадлежат владельцу. Повторное закрытие безвредно и сохраняет первоначальную причину, включая `null`.

### 🎯 13. Как сохранить порядок результатов и пережить частичный отказ?

Порядок запуска, завершения и выходного массива — три разные вещи. Для конечного плотного массива фабрик можно немедленно собрать обещания всех `run` и наблюдать их через `allSettled`. Позиции отчёта останутся позициями входа; B может закончиться до A.

```js
async function collect(limiter, factories, options) {
  const outcomes = await Promise.allSettled(
    factories.map(factory => limiter.run(factory, options)),
  );
  return outcomes.map((outcome, index) => ({ index, ...outcome }));
}
```

Это сохраняет каждый успех и отказ, но не возвращает исходные операции к жизни и не делает отказ успешным. При политике «остановиться после первого отказа» нужно отдельно прекратить допуск ожидающих и передать отмену работающим. `Promise.all` в одиночку этого не делает. Все уже созданные обещания должны остаться наблюдаемыми.

### 🎯 14. Чем ограничение одновременности отличается от частоты и обратного давления?

Два мгновенных запроса могут освободить места почти сразу: ограничитель не гарантирует «не больше двух в секунду». Ограничение частоты требует своего временного договора. Ограниченная очередь тоже не ускоряет медленного потребителя: при заполнении нужно отклонить добавление, приостановить производителя либо отбросить работу по явно выбранной политике.

**Обратное давление (backpressure)** означает, что скорость потребителя влияет на производство. Создать миллион обещаний через `map`, а внутри ограничить два активных — всё ещё значит хранить огромный вход и отчёт. Для потока нужен постепенный приём данных; это связано с [итерацией](06-collections-symbols-and-iteration.md), но не требует строить новый потоковый фреймворк в этой главе.

Не ожидайте вложенную задачу того же ограничителя, удерживая последнее место: при пределе 1 внешняя ждёт внутреннюю, а внутренняя ждёт её место. Нужна другая граница ограничения или изменение структуры зависимостей.

### 🎯 15. Как решить, имеет ли смысл повторять отказ?

Сначала проверьте **безопасность и временность**, затем число попыток и бюджет времени. Отмена владельца, неверный ввод, ошибка авторизации и программный дефект обычно не исправляются немедленным повтором. Ошибка соединения не доказывает, что сервер не применил действие.

Идемпотентность означает одинаковый запрошенный эффект повторного действия, а не одинаковый ответ и не отсутствие серверного журнала. Повтор платежа или создания сущности требует серверного договора: например, стабильного ключа идемпотентности для одной логической операции и серверного устранения дублей. Случайный новый ключ на каждой попытке этой защиты не даёт.

HTTP 429, 502, 503 или 504 могут быть кандидатами только по договору сервиса и операции. `fetch` сам не отклоняет Promise из-за HTTP-статуса; адаптер должен проверить ответ. Не повторяйте любой `TypeError`: в браузере им может проявиться и постоянная конфигурационная проблема. Полный HTTP-разбор — [домен 9](../09-http-api-design-and-real-time-communication/README.md).

### 🎯 16. Зачем увеличивать задержку и добавлять случайный разброс?

Без паузы ошибки создают дополнительные запросы, когда сервису и так тяжело. Экспоненциальная задержка (**exponential backoff**) растёт до предела. Случайный разброс (**jitter**) рассинхронизирует клиентов, получивших один отказ одновременно.

```js
function fullJitterDelay(failedAttempt, base, maximum, sample) {
  const cap = Math.min(maximum, base * 2 ** (failedAttempt - 1));
  return Math.floor(sample * cap);
}
console.log([1, 2, 3, 4].map(n => fullJitterDelay(n, 100, 250, 0.5)));
```

Результат — `[50, 100, 125, 125]`. Здесь первая неудача имеет номер 1; `sample` берётся из `[0, 1)`. Это полный разброс от нуля до текущего предела с округлением вниз, а не единственно возможная формула. Нулевая выпавшая задержка допустима; бюджет попыток всё равно обязателен.

### 🎯 17. Как написать повтор с пределом попыток и отменяемым ожиданием?

Вспомогательное ожидание освобождает таймер при отмене и обработчик при любом исходе. Повторно используемый принцип из 1.10 здесь входит в полный договор цикла.

```js
function abortableSleep(ms, { signal } = {}) {
  return new Promise((resolve, reject) => {
    if (!Number.isFinite(ms) || ms < 0 || ms > 2147483647) {
      reject(new RangeError("ms")); return;
    }
    if (signal?.aborted) { reject(signal.reason); return; }
    const timer = setTimeout(() => { cleanup(); resolve(); }, ms);
    function cleanup() { signal?.removeEventListener("abort", onAbort); }
    function onAbort() {
      clearTimeout(timer); cleanup(); reject(signal.reason);
    }
    signal?.addEventListener("abort", onAbort, { once: true });
  });
}
```

Теперь функция повторов. `maxAttempts` включает первый запуск. Политика `shouldRetry` синхронно возвращает логическое значение; по умолчанию повтор запрещён. Для проверяемости можно передать генератор случайных чисел и функцию ожидания. Это обычные параметры маленькой функции, а не отдельная инфраструктура.

```js
async function retry(operation, {
  maxAttempts = 3, baseDelay = 100, maxDelay = 5000,
  shouldRetry = () => false, random = Math.random,
  sleep = abortableSleep, signal,
} = {}) {
  if (typeof operation !== "function" || typeof shouldRetry !== "function" ||
      typeof random !== "function" || typeof sleep !== "function") {
    throw new TypeError("callbacks");
  }
  if (!Number.isInteger(maxAttempts) || maxAttempts < 1 || maxAttempts > 30 ||
      !Number.isFinite(baseDelay) || baseDelay < 1 ||
      !Number.isFinite(maxDelay) || maxDelay < baseDelay || maxDelay > 2147483647) {
    throw new RangeError("retry options");
  }
  for (let attempt = 1; ; attempt++) {
    signal?.throwIfAborted();
    try {
      const value = await operation({ attempt, signal });
      signal?.throwIfAborted();
      return value;
    } catch (error) {
      signal?.throwIfAborted();
      if (attempt === maxAttempts) throw error;
      const eligible = shouldRetry(error, attempt);
      signal?.throwIfAborted();
      if (typeof eligible !== "boolean") throw new TypeError("sync policy");
      if (!eligible) throw error;
      signal?.throwIfAborted();
      const cap = Math.min(maxDelay, baseDelay * 2 ** (attempt - 1));
      const sample = random();
      if (!Number.isFinite(sample) || sample < 0 || sample >= 1) {
        throw new RangeError("random");
      }
      await sleep(Math.floor(sample * cap), { signal });
    }
  }
}
```

Договор ограничен максимум 30 попытками и допустимым диапазоном таймера. Ошибка классификатора или ожидания завершает цикл. Последняя исходная причина сохраняется без подмены общим сообщением; после последней попытки паузы нет. Проверка сигнала после успеха не позволяет вернуть результат отменённой операции. Если источник игнорирует сигнал и не завершается, функция не может магически прервать его `await`.

### 🔬 18. Как совместить Retry-After, общий срок и несколько слоёв повторов?

Сервер может прислать `Retry-After` в секундах либо HTTP-датой. Это нельзя читать как готовые миллисекунды. Для выбранной политики задержка должна уважать серверное ожидание и общий оставшийся бюджет; если ждать уже бессмысленно, нужно завершить операцию, а не сократить серверную задержку до удобного предела.

Учебный `retry` выше не разбирает HTTP-заголовки и не реализует общий срок сам. Владелец может передать объединённый сигнал закрытия и срока, затем тот же сигнал должен дойти и до запроса, и до паузы. `AbortSignal.timeout` в браузере считает активное время и не является точным календарным будильником. При строгом дедлайне дополнительно проверяйте время на границах; таймер не гарантирует выполнение в момент срока.

Три слоя по три попытки способны превратить один вызов в 27 нижележащих попыток. Повторы должны принадлежать выбранному слою и учитывать общий бюджет, состояние сервиса и другие запросы. Случайная задержка снижает синхронность, но не ограничивает общий объём: нужны пределы очереди, попыток и нагрузки. Число 27 — максимум по такой модели, а не результат обязательного поведения каждой библиотеки.

### 🎯 19. Где держать место: на всю операцию или на одну попытку?

Оба договора возможны. Если `limiter.run(() => retry(...))`, место занято вместе с паузами: меньше активных логических операций, но работающий ресурс может простаивать. Если `retry(() => limiter.run(...))`, место занимает только попытка: во время паузы может работать другой запрос, а повтор снова ждёт очередь.

Во втором случае нужен общий ограничитель для всех попыток и бюджет для ожидающих повторов; нельзя построить новый ограничитель внутри каждой попытки. Нельзя повторять через тот же ограничитель, уже ожидая его из занятого места. Отсчёт общего срока должен включать очередь, попытки и паузы, если таков пользовательский договор.

### 🎯 20. Как распространить отмену через весь конвейер?

Один сигнал владельца должен попасть в очередь, выполняющую фабрику, сам запрос и ожидание между попытками. Перед стартом, после ожидания и перед применением результата проверяется актуальность. Причина отмены передаётся как значение; проверка только `error.name === "AbortError"` теряет произвольные причины.

```text
owner.abort(reason)
  → pending: remove + reject(reason)
  → active API: stop if supported
  → retry wait: clear timer + reject(reason)
  → no next attempt; ignore stale UI result
```

У родителя могут быть несколько детей: закрытие группы отменяет их всех. Отказ одного ребёнка не должен автоматически отменять остальных, если нужна независимая частичная обработка. Для отдельной отмены ребёнка объединяйте его сигнал с родительским при поддержке среды. Владелец дочернего запроса не получает право отменить общий родительский AbortController.

### 🎯 21. Почему debounce поиска не устраняет старые ответы?

Он влияет только на следующий запуск. Новый текст может уже появиться, пока предыдущий запрос ещё работает и новый таймер только ждёт. Версию и отмену старого запроса нужно менять **при новом вводе**, а не лишь при следующем запуске запроса: иначе старый ответ заполнит интерфейс в этой паузе.

Затем проверяйте версию и жизнь владельца перед отображением успеха и ошибки. Это продолжение [модели 1.10](10-promises-and-async-await.md), а не обещание, что сервер всегда остановится. Удаление обработчика, `cancel` таймера и отмена запроса — три разных действия при завершении владельца. Браузерная реализация находится в [EX10](../../exercises/prompts/by-domain/01-javascript-and-async-programming.md#js-coord-ex10).

### 🎯 22. Какие проверки доказывают договор, а какие только среду?

Для debounce/throttle нужны управляемые часы и явный порядок входов: одиночный вызов, серия, непрерывный поток, оба края, отмена, принудительное выполнение и повторный вход. Не угадывайте, успеет ли машина выполнить всё за 20 мс.

Для очереди управляйте обещаниями: заполнить места, завершить B перед A, отклонить задачу, отменить ожидающую, закрыть очередь. Отдельно проверьте источник, игнорирующий сигнал: место остаётся занятым. Для повторов подставляйте последовательность исходов, фиксированные случайные числа и контролируемое ожидание; проверяйте отсутствие лишнего запуска и паузы.

Настоящие таймеры, `AbortController` и событие `input` проверяются в браузере отдельно. Они подтверждают интеграцию в конкретной среде, а не точность временной модели, прекращение серверных эффектов или готовность к промышленной нагрузке.

## Краткий справочник

| Механизм | Хранимое состояние | Завершение владельца |
|---|---|---|
| Debounce | Таймер серии, последние аргументы/получатель | `cancel`, отдельно отменить начатую работу |
| Throttle | Таймер окна, последний отложенный вход | `cancel`, не откатывая первый вызов |
| Очередь | Занятые места, фабрики, обещания ожидающих | Отклонить ожидающих, передать сигнал активным |
| Повторы | Номер попытки, политика, пауза, общий бюджет | Прервать паузу и запретить следующий старт |
| Отчёт | Позиции входа и независимые исходы | Не оставлять необработанных обещаний |

## Типичные ошибки

- Создавать новую обёртку debounce на каждом событии и терять общий таймер.
- Перезапускать таймер throttle на каждом входе, получив debounce.
- Ожидать результат запроса от обёртки с возвратом `undefined`.
- Передавать ограничителю уже начатую работу или освобождать место до её окончания.
- Оставлять обещания удалённых из очереди задач в ожидании навсегда.
- Повторять отмену, неверный пароль, каждый HTTP-ответ или платёж без серверного договора.
- Умножать повторы на нескольких слоях и считать jitter общим ограничителем нагрузки.
- Менять актуальность поиска лишь после паузы, разрешая старому ответу пройти раньше.

## Ловушки на интервью

- Единственный вход при `leading+trailing` не обязан давать два выполнения: договор уточняется заранее.
- `flush` и `cancel` влияют на ожидающий вызов, а не на уже полученный сетевой эффект.
- Ограничение active не ограничивает число стартов в секунду и размер сохранённого массива.
- Порядок отчёта не равен порядку завершения; `allSettled` не отменяет соседей.
- Отмена активной игнорирующей сигнал задачи не даёт права освободить место раньше времени.
- Три попытки — первый старт и два повтора, а не три дополнительных запуска.

## Практические рекомендации

Начните с пользовательского требования и таблицы состояний. Для конечной пачки задайте предел одновременности и очереди, немедленно наблюдайте все возвращённые обещания. Для повторов согласуйте допустимость операции, серверные ограничения и общий бюджет; по умолчанию не повторяйте неизвестный отказ.

Учебные функции намеренно имеют узкий договор. Для продукта сравните проверенную библиотеку с требованиями и зафиксируйте её версию/семантику. API очистки очереди у разных версий может по-разному завершать ожидающие обещания; название метода не заменяет документацию. Не добавляйте зависимость только ради выполнения этой главы.

## Как объяснить тему на интервью за 30–60 секунд

### Debounce и throttle

«Debounce ждёт паузу и объединяет серию входов; throttle сохраняет обновления во время непрерывного потока с ограниченной частотой. Сначала уточню первый и последний вызов, аргументы и возврат. Таймер принадлежит одной стабильной обёртке, а при закрытии я отменю отложенное. Уже начатый запрос требует отдельной отмены и проверки актуальности».

### Ограничитель одновременной работы

«Очередь получает фабрики, чтобы работа не началась заранее. Перед запуском резервируется место, после любого фактического исхода оно освобождается. Я отдельно ограничиваю ожидающие задачи и решаю, что делать при закрытии. Если активная операция игнорирует отмену, она продолжает занимать место до завершения. Порядок отчёта сохраняю по входным позициям».

### Безопасные повторы

«Повтор разрешён только для подходящего временного отказа безопасной операции. Я ограничиваю попытки и общий срок, увеличиваю задержку и добавляю случайный разброс. Сигнал должен отменять запрос и паузу. Повторы на нескольких слоях могут умножить нагрузку; HTTP-тайм-аут не доказывает отсутствие серверного эффекта».
