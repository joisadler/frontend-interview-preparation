## Ментальная модель

Память удобно представлять как граф: объекты — узлы, ссылки — стрелки. Отправные точки, от которых среда начинает искать живые данные, называют **корнями (roots)**. Для практического рассуждения это активные вызовы, доступные глобальные и модульные привязки, а также связи, которыми среда удерживает зарегистрированные операции.

```text
долгоживущий источник → обработчик → замыкание → состояние → DOM-поддерево
```

Если панель закрыли, но источник продолжает хранить обработчик, вся эта цепочка может остаться доступной. Удаление панели с экрана меняет лишь одну связь.

Представьте склад с реестром выданных вещей. Уборщик видит записи реестра, но не знает, что мероприятие уже закончилось. Закрытие мероприятия должно убрать его записи. Аналогия объясняет различие между доступностью и полезностью; настоящий сборщик не читает бизнес-смысл и не работает по обещанному расписанию.

## Связное объяснение в формате вопросов и ответов

### 🎯 1. Что JavaScript делает с памятью автоматически?

Среда выделяет память для значений и служебных структур, код использует её, а **сборщик мусора (garbage collector, GC)** может освободить память, которую больше не нужно сохранять для наблюдаемого поведения программы. Не нужно вручную освобождать каждый объект после вызова функции.

Но конец области видимости имени не равен концу жизни значения. Функция может вернуть объект или замыкание; другая часть программы продолжит им пользоваться. И наоборот, переменная может существовать долго, но уже хранить другое значение.

```js
function makeRecord() {
  const record = { title: "Draft" };
  return record;
}
const saved = makeRecord();
console.log(saved.title); // "Draft"
```

Вызов завершился, а объект доступен через `saved`. Следующий шаг — понять, откуда вообще начинается поиск доступных объектов.

### 🎯 2. Что такое достижимость и путь от корня?

**Достижимость (reachability)** означает, что к объекту ведёт цепочка сильных ссылок от доступной отправной точки. Такой **путь удержания (retaining path)** может проходить через свойства, элементы коллекции, функции и связи среды.

Практический вопрос звучит так: «Кто всё ещё способен обратиться к этому объекту?» Для браузера недостаточно посмотреть только на свои переменные: обработчик в `window`, активный таймер или хранилище объектных URL могут поддерживать жизнь данных.

Корень — не обязательно свойство `window`. Например, верхнеуровневый `const` в модуле не становится свойством глобального объекта, но доступное состояние модуля всё равно может удерживать данные. Конкретные подписи корней в снимке зависят от движка.

ECMAScript описывает наблюдаемую живость значений и ограничения слабых ссылок, а не обязательную структуру кучи или один алгоритм GC. Движок может исключить фактически ненаблюдаемые значения. Поэтому рисуем нужные программе пути, а точное удержание проверяем инструментом.

### 🎯 3. Достаточно ли присвоить переменной `null`?

Это убирает одну ссылку. Другие ссылки остаются самостоятельными владельцами того же объекта.

```js
let item = { payload: [1, 2, 3] };
const registry = new Map([["current", item]]);
item = null;
console.log(registry.get("current").payload.length); // 3
registry.delete("current");
console.log(registry.size); // 0
```

После `item = null` путь через `registry` сохраняется. После `delete` этот путь убран; отсюда не следует, что память уже освобождена. `delete object.field` также удаляет свойство и его ссылку, а не сам объект.

Не нужно ставить `null` в конце каждой короткой функции. Полезнее убрать действительно долгоживущую запись: из кеша, реестра, владельца состояния. Очистка локального имени при сохранённом псевдониме проблему не решит.

### 🎯 4. Вызывает ли циклическая ссылка утечку сама по себе?

Нет. Взаимные ссылки внутри островка объектов не создают путь от корней к этому островку.

```js
function makeCycle() {
  const first = {};
  const second = { peer: first };
  first.peer = second;
  return first;
}
let cycle = makeCycle();
console.log(cycle.peer.peer === cycle); // true
cycle = null;
```

После удаления единственного внешнего пути цикл может быть собран. Момент сборки этот пример не показывает. Если сохранить `first` в глобальном массиве, доступным останется весь цикл.

**🧓 Legacy:** простое подсчитывание ссылок плохо справляется с такими циклами; отсюда происходит старое правило «циклы вызывают утечки». Современную трассирующую сборку нельзя объяснять этим правилом. Понимать идею обхода графа полезно, учить все фазы конкретного движка здесь не требуется.

### 🎯 5. Когда именно GC освободит недостижимый объект?

Общего обещанного момента нет. Ни `null`, ни конец функции, ни очередной таймер не обязывают среду немедленно освободить память. Стандарт не гарантирует, что каждый подходящий объект вообще будет собран до завершения среды.

Рабочая модель трассирующего сборщика: начать от корней, отметить доступные объекты и рассмотреть остальные для освобождения. Реальные движки делят работу на поколения и части, могут выполнять часть работы параллельно. Это детали реализации, не обещание ECMAScript о конкретной паузе.

Поэтому проверка «через 100 мс слабая ссылка должна стать пустой» некорректна. Для кода можно проверить удаление регистрации или записи, а для диагностики — наблюдать накопление объектов в сравнимом сценарии. Эти два вида доказательств дополняют друг друга.

### 🎯 6. Почему замыкание может удерживать большой граф объектов?

**Замыкание (closure)** сохраняет доступ к нужным внешним привязкам. Если доступная функция читает объект, через этот объект могут оставаться доступными и его вложенные данные.

```js
function createReader() {
  let report = { rows: [10, 20, 30] };
  return {
    read: () => report?.rows.length ?? 0,
    clear: () => { report = null; },
  };
}
const reader = createReader();
console.log(reader.read()); // 3
reader.clear();
console.log(reader.read()); // 0
```

Здесь возвращённая функция читает текущую привязку `report`, а не навсегда застывшую копию объекта. `clear()` убирает путь через эту привязку. Если потребитель ранее сохранил отдельную ссылку на исходные данные, очистить её придётся у её владельца.

Само замыкание не является утечкой: сохранять данные между вызовами часто и есть его задача. Ошибка возникает, когда время жизни обработчика оказывается дольше времени жизни нужных ему данных.

### 🔬 7. Любая ли функция удерживает все локальные переменные навсегда?

Такое правило слишком сильное. Лексическая модель объясняет доступ к именам, но не обещает физическое хранение каждого значения. Оптимизации и совместные внутренние окружения зависят от движка; `eval` и отладчик тоже могут влиять на результат.

Если обработчику нужен лишь идентификатор большого отчёта, лучше выразить это явно: передать идентификатор отдельной фабрике.

```js
function createLabelReader(id) {
  return () => `Report ${id}`;
}
function prepareLabel(report) {
  return createLabelReader(report.id);
}
const getLabel = prepareLabel({ id: 7, rows: [10, 20] });
console.log(getLabel()); // "Report 7"
```

Это про ясный договор данных: функции не нужен отчёт целиком. Пример не измеряет экономию байтов и не доказывает устройство окружений во всех движках. При подозрении на удержание проверяем реальный путь, а не делаем вывод по длине исходника.

### 🎯 8. Почему удалённый DOM-узел может остаться в памяти?

**Отсоединённый DOM-узел (detached DOM)** больше не находится в документе. Это ещё не означает, что к нему нельзя добраться из JavaScript.

Браузер. Намеренная ошибка жизненного цикла: завершение удаляет узел, но оставляет обработчик в долгоживущем `window`.

```js
function mountLeakyPanel(host) {
  const panel = document.createElement("section");
  host.append(panel);
  const onResize = () => { panel.textContent = String(innerWidth); };
  window.addEventListener("resize", onResize);
  return () => { panel.remove(); };
}
```

Путь после закрытия: `window → обработчик resize → замыкание → panel`. Исправленный вариант, тоже браузер:

```js
function mountPanel(host) {
  let panel = document.createElement("section");
  host.append(panel);
  const onResize = () => { panel.textContent = String(innerWidth); };
  window.addEventListener("resize", onResize);
  return () => {
    if (panel === null) return;
    window.removeEventListener("resize", onResize);
    panel.remove();
    panel = null;
  };
}
```

Сначала снимаем обработчик, потом разрываем ссылку на узел. Функцию завершения можно вызвать повторно. Её сохранение потребителем после вызова больше не удерживает панель через `panel`.

Один обработчик на самом отсоединённом узле не доказывает утечку: если весь связанный граф недостижим, внутренний цикл не спасает его. Искать нужно внешний путь. Намеренно сохранённая панель для повторного открытия тоже может быть допустима — если это ограниченное и понятное владение.

### 🎯 9. Как правильно удалить обработчик события?

Для `removeEventListener` должны совпасть цель, тип события, объект функции и значение `capture`. Две одинаково написанные стрелки — разные функции. Новый результат `bind()` тоже не совпадёт с прежним.

Браузер; сначала неверная попытка, затем правильная очистка:

```js
const target = new EventTarget();
let hits = 0;
const onPing = () => { hits += 1; };
target.addEventListener("ping", onPing, true);
target.removeEventListener("ping", onPing, false); // другой capture
target.dispatchEvent(new Event("ping"));
console.log(hits); // 1
target.removeEventListener("ping", onPing, true);
target.dispatchEvent(new Event("ping"));
console.log(hits); // 1
```

В браузерах с поддержкой опции `signal` группу обработчиков удобно связать с одним `AbortController`. В проверенном Chromium это работает. Для старой целевой среды проверьте совместимость или храните функции явно.

```js
// Браузер
const target = new EventTarget();
const controller = new AbortController();
let hits = 0;
target.addEventListener("ping", () => { hits += 1; }, {
  signal: controller.signal,
});
target.dispatchEvent(new Event("ping"));
controller.abort();
target.dispatchEvent(new Event("ping"));
console.log(hits); // 1
```

`once: true` снимает обработчик после события. Если событие никогда не наступит, это не заменяет завершение владельца. Отмена контроллера не отменяет произвольные таймеры и подписки: они должны поддерживать сигнал или очищаться отдельно.

### 🎯 10. Как таймер удерживает данные и что значит его отменить?

Среда хранит запланированную функцию. Функция может удерживать данные, даже если создавшая её функция уже завершилась. Одноразовый таймер временно продлевает их жизнь; забытый интервал способен делать это всё время работы страницы.

Браузер; `onTick` — синхронная функция без исключений:

```js
function startTicker(onTick) {
  let active = true;
  const id = setInterval(() => { if (active) onTick(); }, 1000);
  return () => {
    if (!active) return;
    active = false;
    clearInterval(id);
    onTick = null;
  };
}
```

Отмена убирает будущую регистрацию, а `onTick = null` освобождает путь к потребителю даже через сохранённую функцию остановки. Уже выполняющийся вызов нельзя «отмотать назад». Для асинхронной работы могут понадобиться отдельная отмена операции и защита от позднего результата; полная координация остаётся в 1.10–1.11.

В тесте сначала проверяем, что обработчик работает, затем — что после остановки работа больше не запускается. Не привязываем правильность к точному интервалу или падению показателя памяти.

### 🎯 11. Чем подписка отличается от обычной локальной функции?

**Подписка (subscription)** передаёт функцию источнику, который может жить дольше её создателя. API подписки должен возвращать способ отписаться или принимать явный сигнал отмены.

Переносимая модель источника; обработчики синхронны и не выбрасывают исключений:

```js
function createBus() {
  const listeners = new Set();
  return {
    subscribe(fn) {
      listeners.add(fn);
      return () => { listeners.delete(fn); };
    },
    emit(value) {
      for (const fn of [...listeners]) fn(value);
    },
    get size() { return listeners.size; },
  };
}
const bus = createBus();
let total = 0;
const unsubscribe = bus.subscribe(value => { total += value; });
bus.emit(2);
unsubscribe();
unsubscribe();
bus.emit(3);
console.log(total, bus.size); // 2, 0
```

Здесь повторная отписка безопасна. В конкретной библиотеке её договор надо прочитать, а не предполагать. Копия списка в `emit` означает, что уже выбранный для текущей рассылки обработчик ещё может быть вызван при изменении подписок внутри рассылки. Для закрываемого интерфейса полезна дополнительная проверка состояния владельца.

Та же идея относится к наблюдателям: использованный `MutationObserver` или `ResizeObserver` требует подходящего `disconnect()` по окончании работы. GC не заменяет требование прекратить ненужные уведомления.

### 🎯 12. Когда кеш становится источником утечки?

**Кеш (cache)** намеренно удерживает данные ради повторного доступа. Ошибка — отсутствие политики, согласованной с задачей: ограничение размера, вытеснение, срок жизни или очистка при смене владельца.

Переносимый пример: кеш с ограничением числа записей и вытеснением по порядку первого добавления (**FIFO**). `get()` не обновляет порядок; алгоритм LRU здесь не реализуется.

```js
function createCache(limit) {
  if (!Number.isInteger(limit) || limit < 1) {
    throw new RangeError("Positive integer limit required");
  }
  const entries = new Map();
  return {
    set(key, value) {
      if (!entries.has(key) && entries.size === limit) {
        entries.delete(entries.keys().next().value);
      }
      entries.set(key, value);
    },
    get(key) { return entries.get(key); },
    clear() { entries.clear(); },
    get size() { return entries.size; },
  };
}
const cache = createCache(2);
cache.set("a", 1); cache.set("b", 2); cache.set("c", 3);
console.log(cache.get("a"), cache.size); // undefined, 2
cache.clear();
```

Две записи всё ещё могут содержать огромные файлы. Ограничение количества не равно ограничению байтов. TTL тоже не обещает, что просроченная запись физически удалится ровно в срок: нужен механизм очистки, особенно если проверка срока происходит только при чтении.

Удержание в пределах оправданного бюджета — нормальная работа кеша. Для диагностики надо отличать прогрев от бесконечного накопления новых ключей. Самодельный кеш необязателен: часто достаточно исправить политику уже используемой библиотеки.

### 🔬 13. Можно ли заменить очистку слабыми ссылками?

Слабые связи полезны для данных, отсутствие которых допустимо. `WeakMap` подходит для метаданных, привязанных к объектному ключу без независимого продления его жизни. Но он не завершает интервал, не снимает подписку и не задаёт бюджет кеша с текстовыми ключами.

`WeakRef` требует обрабатывать отсутствие значения. `FinalizationRegistry` даёт необязательное уведомление после возможной сборки; он не является надёжным деструктором. Освобождать через него единственный объектный URL или обязательную подписку нельзя: уведомление может не прийти.

Механика слабых коллекций уже разобрана в [1.6](06-collections-symbols-and-iteration.md). Здесь правило выбора: **обязательное завершение — явная операция владельца; необязательные метаданные — возможное применение слабой связи**. Не добавляйте слабые ссылки только для того, чтобы скрыть неизвестный путь удержания.

### 🎯 14. Почему строку объектного URL недостаточно просто забыть?

**Объектный URL (object URL)** связывает адрес вида `blob:…` с объектом в хранилище браузера. `URL.createObjectURL(blob)` создаёт такую регистрацию. Пока она существует, удаление вашей переменной со строкой не заменяет `URL.revokeObjectURL(url)`.

Браузер; функция единолично владеет `src` переданного `img`. Каждый экземпляр управляет только своими URL:

```js
function createPreview(img) {
  let current = null;
  let disposed = false;
  function clear() {
    img.removeAttribute("src");
    if (current !== null) URL.revokeObjectURL(current);
    current = null;
  }
  return {
    set(blob) {
      if (disposed) throw new Error("Preview disposed");
      const next = URL.createObjectURL(blob);
      clear();
      current = next;
      img.src = next;
    },
    dispose() {
      if (disposed) return;
      disposed = true;
      clear();
      img = null;
    },
  };
}
```

При замене освобождается прежняя регистрация, при завершении — текущая. Новый URL сначала создаётся: если неверный аргумент вызовет исключение, старое изображение останется во владении. Сохранённый объект управления после завершения больше не удерживает `img`; повторный `dispose()` безопасен, новый `set()` явно запрещён.

Не освобождайте URL сразу после присваивания `src`, пока потребитель ещё должен читать его. Даже успешная загрузка изображения не всегда означает конец использования: пользователь может сохранять или открывать его. Для этого примера граница — замена либо закрытие предпросмотра. Загрузки файлов и несколько потребителей требуют собственного договора времени жизни, а не универсального `setTimeout(revoke, 0)`.

Освобождение регистрации не обещает немедленного уменьшения памяти процесса: декодированное изображение и другие ссылки могут жить отдельно.

### 🎯 15. Чем пик памяти отличается от настоящей утечки?

**Пик памяти (memory peak)** — временный максимум. Например, одновременно существуют исходные данные, их копия и результат преобразования. После работы все три больше не нужны, но GC и возврат памяти операционной системе не обязаны совпасть с концом операции.

**Утечка памяти (memory leak)** в прикладном смысле — ненужные данные продолжают удерживаться после своего логического завершения. Она может расти при повторении сценария. Даже одна навсегда удержанная крупная панель уже может быть ошибкой; бесконечный рост не обязателен.

**Избыточное потребление** — данные нужны, но их слишком много. Например, оправданный кеш разрешает слишком большой бюджет. **Частые выделения** — много короткоживущих объектов и нагрузка на GC, даже если итоговое количество стабильно.

Это разные гипотезы и разные исправления: ограничить одновременные копии; убрать лишний путь; уменьшить бюджет; сократить ненужные выделения. Один высокий показатель памяти процесса не выбирает гипотезу за нас. JS-куча, DOM, изображения, внешние буферы и память процесса — разные области измерения.

### 🎯 16. С чего начать исследование кучи?

**Снимок кучи (heap snapshot)** показывает объекты и связи в конкретном наблюдении. Здесь нужен короткий вход в диагностику, а не полный курс профилировщика.

1. Задайте повторяемый сценарий: открыть панель, использовать, закрыть; одинаковые входы и число циклов.
2. Прогрейте приложение отдельно, затем снимите исходное состояние.
3. Повторите сценарий и сравните снимки после завершения работы, а не во время пика.
4. Найдите растущую группу объектов и откройте удерживающие связи (**retainers**).
5. Пройдите до владельца: например, массив закрытых панелей или обработчик в `window`.
6. Исправьте этот путь и повторите тот же сценарий в свежем сравнимом состоянии.

**Собственный размер (shallow size)** относится к самому объекту. **Удерживаемый размер (retained size)** помогает оценить данные, которые стали бы недостижимыми вместе с ним. Если у зависимых объектов остаётся другой путь от корня, их нельзя целиком приписать этому владельцу. Размер маленькой функции поэтому может скрывать большой удерживаемый граф.

DevTools сам способен удерживать выбранные или выведенные объекты. Не сохраняйте подозреваемые объекты в консоли и тестовом массиве, если проверяете их исчезновение. Снимок Chrome запускает диагностическую сборку, но это наблюдение данного инструмента, а не гарантия GC для приложения.

Продолжение: [8.3. Browser Memory](../08-browser-internals-and-web-apis/03-browser-memory.md) — DOM и браузерные ресурсы; [19.2. Diagnostic Tools](../19-debugging-code-review-and-interview-communication/02-diagnostic-tools.md) — методика инструментов. Это будущие главы; их заглушки этот цикл не заполняет.

### 🎯 17. Кто должен отвечать за завершение ресурса?

Тот, кто приобрёл ресурс, должен явно передать или выполнить обязанность его завершить. Для небольшой панели удобно вернуть единую функцию `dispose()`: она снимает обработчики, отменяет таймеры, отписывается, очищает принадлежащие панели записи и освобождает URL.

У такого договора есть несколько важных свойств:

- повторное завершение безопасно;
- после завершения новые регистрации запрещены или явно обрабатываются;
- если создание упало посередине, уже приобретённые ресурсы освобождаются;
- поздний обработчик не обращается к закрытому интерфейсу;
- ресурс другого владельца не закрывается случайно.

Это похоже на получение нескольких ключей под расписку: если третий ключ не выдали, первые два всё равно нужно вернуть. Порядок освобождения часто обратен приобретению. Не нужен универсальный фреймворк: в [комплексной задаче](../../exercises/prompts/by-domain/01-javascript-and-async-programming.md#js-memory-ex08) достаточно небольшого списка операций и `try/catch` из 1.7.

### 🎯 18. Как проверить исправление, если нельзя назначить момент GC?

Разделите договор своего кода и наблюдение движка. В договоре детерминированны число подписок, наличие записей, работа обработчика после завершения и вызов освобождения URL. Их можно проверить без ожидания GC.

Для браузерных API нужен настоящий браузер: отправить событие до и после очистки, проверить замену и отзыв URL, повторить создание и завершение. Подставной источник полезен для счётчиков и ошибки частичной инициализации, но не доказывает поведение DOM или хранилища URL.

После этого проведите сравнимое исследование удержания: исчез ли прежний путь, перестали ли накапливаться объекты конкретного сценария? Это сильнее предположения по одному графику. Ни точное количество освободившихся байтов, ни вызов финализатора не должны быть условием успешного теста жизненного цикла.

## Краткий справочник

| Наблюдение | Что проверить |
|---|---|
| `value = null`, объект остался | Другие имена, коллекции, замыкания и связи среды |
| Панель удалена из документа | Внешние обработчики, реестры, сохранённые функции завершения |
| Таймер больше не нужен | `clearTimeout` / `clearInterval`, отдельно — начатые операции |
| Подписка больше не нужна | Возвращённая отписка, сигнал или метод закрытия источника |
| Кеш растёт | Ключи, бюджет, вытеснение, реальная очистка просроченных записей |
| Старый `blob:` больше не нужен | `URL.revokeObjectURL` после конца использования всеми потребителями |
| Высокая память | Сопоставимость сценария, пик, прогрев, бюджет, удерживающий путь |

## Типичные ошибки

- Считать, что конец функции освобождает все созданные ею данные.
- Обнулять локальную переменную, сохраняя объект в долгоживущем реестре.
- Удалять DOM-узел, оставляя использующий его обработчик в `window`.
- Пытаться снять обработчик новой стрелкой или новым `bind()`.
- Считать `once` гарантированным завершением, даже если события не было.
- Удалять строку URL вместо отзыва регистрации или отзывать URL до конца чтения.
- Лечить любой рост памяти слабыми ссылками и финализаторами.

## Ловушки на интервью

- Цикл ссылок не равен пути от корня.
- Достижимый объект может быть бесполезен приложению; GC не знает намерений.
- `dispose()` может сам удерживать данные, если его сохранить после вызова.
- Удаление одной записи не устраняет независимые пути.
- Ограниченный кеш может потреблять слишком много памяти; TTL без очистки не ограничивает хранение.
- Устойчивый высокий уровень памяти и повторное накопление завершённых объектов — разные свидетельства.

## Практические рекомендации

Начинайте с владельца и времени жизни, а не с ручного обнуления всех переменных. Для каждого приобретения найдите симметричное завершение. Сохраняйте идентичность обработчиков; группируйте поддерживающие сигнал операции; остальные завершайте явно. Задавайте бюджет долгоживущих коллекций и отдельно думайте о тяжёлых ресурсах вне JS-кучи.

Текущая рекомендация — явная очистка и измерение повторяемого сценария. Слабые ссылки здесь имеют обзорную глубину и ссылаются на 1.6. Подсчёт ссылок как объяснение современных утечек — legacy-ловушка. Экспериментальные API измерения памяти в маршрут не добавлены; поддержка конкретной целевой среды проверяется отдельно от локального Chromium.

## Как объяснить тему на интервью за 30–60 секунд

### Достижимость и GC

> Я представляю объекты графом и ищу пути от доступных корней. Пока есть сильный путь, данные могут оставаться нужны программе. Присваивание `null` убирает только одну ссылку, а цикл внутри недостижимого графа сам по себе не создаёт утечку. Сборка недетерминирована: я могу убрать причину удержания, но не обещать момент освобождения памяти.

### Жизненный цикл интерфейса

> Закрыть панель — значит завершить её ресурсы, а не только удалить узел. Обработчик в `window`, интервал или подписка способны удерживать замыкание с состоянием панели. Я задаю владельца и возвращаю явное завершение: снять обработчики, отменить таймеры, отписаться, очистить записи. Повторное завершение и ошибка посреди создания тоже должны быть безопасны.

### Объектный URL

> `createObjectURL` создаёт регистрацию в браузере, поэтому забытая строка не является её очисткой. У предпросмотра должен быть владелец URL. Он отзывает старый адрес при замене и текущий при закрытии, когда использование закончено. Немедленный отзыв после установки `src` может сломать чтение; финализатор не даёт нужной гарантии завершения.

### Диагностика

> Сначала воспроизвожу одинаковые циклы работы и сравниваю завершённые состояния после прогрева. Отличаю временный пик, слишком большой кеш и накопление ненужных объектов. В снимке ищу конкретную группу и её путь удержания, исправляю владельца и повторяю эксперимент. Успех теста очистки определяю по ресурсам и поведению, а не по моменту GC или точным байтам.
