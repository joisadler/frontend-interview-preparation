## Ментальная модель

Представьте импорт настроек приложения. Один модуль принимает текст, другой проверяет форму данных, третий решает, что показать пользователю при ошибке. Здесь три разных договора:

| Граница | Что нужно решить |
|---|---|
| Модуль → модуль | Какие имена доступны и когда готово их значение |
| Вызов → вызывающий код | Как передать неуспех и сохранить исходную причину |
| Значение → текст → значение | Какие данные поддерживает внешний формат и что проверять после чтения |

Экспорт не делает имя глобальным. `catch` не исправляет ошибку самим фактом перехвата. Успешный `JSON.parse` не доказывает, что объект подходит приложению. Дальше последовательно восстановим каждый договор и соединим их на границе импорта данных.

## Связное объяснение в формате вопросов и ответов

### 🎯 1. Что даёт модуль помимо отдельного файла?

ES-модуль (ECMAScript module, ESM) имеет собственную область видимости (module scope) и явный публичный интерфейс. Объявленные имена видны внутри модуля; наружу доступны только экспорты. Модули выполняются в строгом режиме, а `this` на верхнем уровне равен `undefined`. Это правила языка; способ найти и загрузить файл определяет среда.

Набор `scope`, Node.js, запуск `node main.mjs`:

```js
// file: settings.mjs
const token = "private";
export const theme = "light";
export function hasToken() { return token.length > 0; }
```

```js
// file: main.mjs
import { theme, hasToken } from "./settings.mjs";
console.log(theme, hasToken(), this); // "light", true, undefined
console.log(Object.hasOwn(globalThis, "theme")); // false
```

Модуль похож на мастерскую с выдачей через окно: внутренние инструменты остаются внутри. Аналогия объясняет доступность имён, но не обещает изоляции процессов или защиты секретов. Код и экспортируемые объекты всё ещё работают в одной среде.

### 🎯 2. Как различить именованный экспорт, экспорт по умолчанию и пространство имён?

Именованный экспорт (named export) выбирают по точному внешнему имени, при желании переименовывая локально через `as`. У экспорта по умолчанию (default export) внешнее имя — `default`, а локальное имя при импорте выбирает потребитель. `import * as api` даёт объект пространства имён модуля (module namespace object), включая свойство `default`, если оно есть.

Набор `forms`, Node.js, запуск `node main.mjs`:

```js
// file: math.mjs
export const step = 2;
export default function add(a, b) { return a + b; }
```

```js
// file: main.mjs
import sum, { step as delta } from "./math.mjs";
import * as math from "./math.mjs";
console.log(sum(delta, 3), math.default === sum); // 5, true
```

Фигурные скобки в `import` — часть синтаксиса импорта, а не деструктуризация обычного объекта. Переэкспорт `export { step } from "./math.mjs"` передаёт имя дальше, но не создаёт локального `step`. `export * from ...` не включает `default`; его передают явно. Если два звёздочных переэкспорта дают конфликтующее имя, нужен явный выбор источника.

### 🎯 3. Почему статический импорт работает до строки с `import`?

Статические `import`/`export` находятся на верхнем уровне и задают известные заранее связи. До выполнения тела среда может загрузить зависимости и связать экспортируемые и импортируемые имена. Для обычного ациклического графа без top-level `await` зависимости выполняются до тела потребителя.

Набор `order`, Node.js, запуск `node main.mjs`:

```js
// file: dependency.mjs
console.log("dependency");
export const value = 3;
```

```js
// file: main.mjs
console.log("main");
import { value } from "./dependency.mjs";
console.log(value); // общий порядок: "dependency", "main", 3
```

Модель: **загрузка → связывание → выполнение**. Это не буквальное перемещение строк. Нельзя поместить статический `import` в `if`. Для выбора во время работы есть `import()`.

Браузер получает точку входа через `<script type="module" src="./main.mjs"></script>`. Обычный такой скрипт без `async` отложен; импортируемые имена не становятся свойствами `window`. Нужны HTTP-сервер, корректный JavaScript MIME type и разрешённая CORS-загрузка для другого origin. Браузер сам не ищет npm-пакеты в `node_modules`: для коротких имён нужны, например, import maps или сборщик. Это поведение среды, не обещание спецификации о файловой системе.

### 🎯 4. Импорт копирует значение или продолжает видеть изменения?

ESM связывает импорт с экспортируемым именем. Такая живая привязка (live binding) при чтении показывает текущее значение у источника. Потребитель не может присвоить новое значение импортированному имени, даже если источник экспортировал `let`.

Набор `live`, Node.js, запуск `node main.mjs`:

```js
// file: counter.mjs
export let count = 0;
export const state = { clicks: 0 };
export function increment() { count++; }
```

```js
// file: main.mjs
import { count, state, increment } from "./counter.mjs";
const snapshot = count;
increment();
state.clicks++;
console.log(count, snapshot, state.clicks); // 1, 0, 1
try { count = 9; } catch (error) { console.log(error.name); } // "TypeError"
```

Табло обновляет показание, а записанное на бумаге число остаётся прежним: так можно запомнить разницу между привязкой и `const snapshot = count`. Объект `state` при этом не заморожен: запрет переназначения импортированного имени не запрещает менять свойства объекта. Если модуль должен владеть состоянием, экспортируйте операции над ним.

### 🔬 5. Всегда ли `export default` сохраняет живую связь с локальным именем?

Важна форма записи. `export default value` вычисляет выражение и сохраняет его результат как экспорт по умолчанию. `export { value as default }` экспортирует привязку `value`.

Набор `default`, Node.js, запуск `node main.mjs`:

```js
// file: source.mjs
let value = 1;
export default value;
export { value as current };
value = 2;
```

```js
// file: main.mjs
import initial, { current } from "./source.mjs";
console.log(initial, current); // 1, 2
```

Не обобщайте это до «default всегда копия»: именованная функция в `export default function named() {}` — другая синтаксическая форма. Для практической задачи сначала прочитайте точную запись экспорта.

### 🎯 6. Почему циклический импорт иногда работает, а иногда падает?

Цикл зависимостей допустим. Опасность возникает, если модуль читает чужую привязку до её инициализации. Например, `const` ещё находится во временной мёртвой зоне (TDZ).

Набор `cycle-bad`, Node.js, запуск `node a.mjs`, ожидается `ReferenceError`:

```js
// file: a.mjs
import { b } from "./b.mjs";
export const a = 1;
console.log(b);
```

```js
// file: b.mjs
import { a } from "./a.mjs";
export const b = a + 1; // a ещё не инициализирована
```

Если `b` вместо немедленного чтения экспортирует `function readA() { return a; }`, а `a` вызывает её после `export const a = 1`, этот конкретный цикл работает. Причина — момент чтения. Для исправления архитектуры чаще полезнее вынести общий договор в третий модуль или передать зависимость параметром. Переставить строки импорта обычно недостаточно: связи существуют до выполнения тела.

### 🎯 7. Когда нужен `import()` и что он возвращает?

Динамический импорт (dynamic import) — выражение. Его можно вызвать условно, внутри функции и с вычисляемым путём. Он возвращает обещание пространства имён после успешной загрузки и выполнения модуля. Ошибка поиска, разбора или выполнения приводит к отклонению этого обещания.

Набор `dynamic`, Node.js, запуск `node main.mjs`:

```js
// file: formatter.mjs
export default (value) => `[${value}]`;
```

```js
// file: main.mjs
const api = await import("./formatter.mjs");
const again = await import("./formatter.mjs");
console.log(api.default(7), api === again); // "[7]", true
try { await import("./missing.mjs"); }
catch (error) { console.log(error.code); } // "ERR_MODULE_NOT_FOUND" в Node.js
```

Для одного разрешённого модуля в этом процессе повторный импорт использует тот же экземпляр. Разные URL, параметры запроса или пути, разрешившиеся по-разному, могут означать разные экземпляры. Нельзя выводить из кеширования правило «любой файл везде выполняется только один раз».

Сборщик часто использует `import()` как границу отдельной части сборки (code splitting). Язык обещает динамическую загрузку, но не конкретное число файлов на выходе. Произвольный путь может мешать сборщику перечислить зависимости; в приложении удобнее явный список разрешённых загрузчиков.

### 🎯 8. Что меняет `await` на верхнем уровне модуля?

Top-level `await` (TLA) разрешён в ESM и позволяет приостановить выполнение модуля до готовности его зависимости. Потребитель не начнёт своё тело, пока нужная ему асинхронная зависимость не завершится. Это не останавливает весь процесс или все независимые ветки графа.

Набор `tla`, Node.js, запуск `node main.mjs`:

```js
// file: config.mjs
export const config = await Promise.resolve({ theme: "dark" });
```

```js
// file: main.mjs
import { config } from "./config.mjs";
console.log(config.theme); // "dark"
```

TLA полезен для обязательной инициализации, но делает готовность модуля зависимой от внешней операции. Ошибка отклоняет выполнение, а взаимное ожидание в цикле может оставить граф без завершения. Для необязательных данных часто яснее экспортировать `loadConfig()` с явным вызовом. В обычном `.cjs` top-level `await` — синтаксическая ошибка. Координацию обещаний и расписание задач разбираем в 1.9–1.11.

### 🎯 9. Как статический граф связан с удалением неиспользуемого кода?

Удаление неиспользуемого кода (tree shaking) — работа сборщика. Статические связи ESM позволяют проследить используемые экспорты без запуска приложения. Но нужно ещё сохранить наблюдаемые побочные эффекты (side effects): регистрацию обработчика, изменение глобального состояния или подключение стилей.

Набор `shake`, Rollup 4.52.5, команда `rollup main.mjs --format esm --file bundle.mjs`; затем `node bundle.mjs`:

```js
// file: library.mjs
console.log("registered");
export const used = 7;
export function unused() { return "UNUSED_MARKER"; }
```

```js
// file: main.mjs
import { used } from "./library.mjs";
console.log(used); // "registered", затем 7
```

Минимальная сборка удаляет `unused`, но сохраняет журнал регистрации. Сам Node.js без сборки выполняет тело импортированного модуля; удаление экспортов не является его стандартным режимом исполнения.

В webpack `usedExports` и поле пакета `sideEffects` решают связанные, но разные задачи. Ложное `sideEffects: false` разрешает исключить нужную инициализацию или CSS. Именованный импорт сам по себе не гарантирует маленькую сборку; проверяйте результат и правильность приложения. Подробная конфигурация относится к домену 14.

### 🎯 10. Как Node.js выбирает ESM и CommonJS?

Для воспроизводимых примеров задавайте формат явно: `.mjs` — ESM, `.cjs` — CommonJS. Для `.js` существенны ближайший `package.json` с `"type": "module"` или `"type": "commonjs"` и правила конкретной версии Node.js. Современное распознавание синтаксиса в неоднозначных файлах не заменяет явного договора пакета.

| Слой | Что он определяет |
|---|---|
| ECMAScript | Синтаксис, привязки, связывание и выполнение ESM |
| Node.js | Расширения, `type`, поиск пакетов, `exports`, ESM/CJS interop |
| Браузер | Module scripts, URL, MIME type, CORS, import maps |
| Сборщик | Преобразование форматов, части сборки, tree shaking |

**🧓 Legacy.** CommonJS (CJS) — формат, который важно читать в существующем Node.js-коде и зависимостях. `require()` возвращает экспорт синхронно. В Node.js CommonJS оборачивается функцией и имеет собственные `module`, `exports`, `require`. В нативном браузерном модуле этих имён нет. Для нового переносимого кода ориентируйтесь на ESM, учитывая ограничения конкретного проекта.

### 🎯 11. Чем `exports` отличается от `module.exports`?

В начале CommonJS-модуля `exports` указывает на тот же объект, что `module.exports`. Присваивание свойства через `exports.name` меняет этот объект. Присваивание самой переменной `exports` только переставляет локальную ссылку. Возвращаемый экспорт задаёт `module.exports`.

Набор `cjs`, Node.js, запуск `node main.cjs`:

```js
// file: legacy.cjs
exports.value = 1;
exports = { value: 2 }; // локальная ссылка отделилась от module.exports
```

```js
// file: main.cjs
const api = require("./legacy.cjs");
const { value } = api;
api.value = 3;
console.log(value, require("./legacy.cjs").value); // 1, 3
```

Деструктуризация здесь снимает значение свойства в данный момент. Это не живая ESM-привязка. Сам экспортируемый объект может оставаться общим. При цикле CJS потребитель способен получить ещё не законченный объект экспортов, поэтому правила ESM о TDZ нельзя механически переносить на CJS.

### 🎯 12. Как импортировать CommonJS из ESM?

В Node.js импорт по умолчанию надёжно даёт `module.exports`. Часть именованных экспортов Node.js пытается обнаружить статически, но это эвристика с ограничениями. Такие автоматически выделенные значения не обновляются как живые ESM-привязки.

Набор `interop`, Node.js, запуск `node main.mjs`:

```js
// file: legacy.cjs
exports.count = 0;
exports.increment = () => { exports.count++; };
```

```js
// file: main.mjs
import api, { count } from "./legacy.cjs";
api.increment();
console.log(api.count, count); // 1, 0 в проверенных версиях Node.js
```

В другом CJS-пакете именованный импорт может вообще не обнаружиться. При сомнении импортируйте объект по умолчанию и читайте его свойства. Обратный переносимый асинхронный мост из CJS в ESM — `import()` внутри функции. Поведение транспилятора или сборщика с «синтетическим default» проверяйте отдельно от нативного Node.js.

### 🔬 13. Правда ли, что `require()` никогда не умеет загружать ESM?

Для современных Node.js это устаревшее обобщение. `require(esm)` может синхронно вернуть пространство имён, если загружаемый граф не содержит TLA. Даже `await Promise.resolve(...)` считается TLA; важно наличие конструкции, а не скорость ожидания.

| Проверенная сборка, без дополнительных флагов | Синхронный `.mjs` | `.mjs` с TLA, в том числе в зависимости |
|---|---|---|
| Node.js 20.18.2 | `ERR_REQUIRE_ESM` | `ERR_REQUIRE_ESM` |
| Node.js 22.13.1 | Пространство имён | `ERR_REQUIRE_ASYNC_MODULE` |
| Node.js 24.21.0 | Пространство имён | `ERR_REQUIRE_ASYNC_MODULE` |
| Node.js 26.4.0 | Пространство имён | `ERR_REQUIRE_ASYNC_MODULE` |

В документации 22.13.1 механизм отмечен как release candidate; с 22.12.0 он доступен без флага, с 22.13.0 нет предупреждения по умолчанию. Это не таблица всех патчей ветки 20 и не рекомендация внедрять старые версии. Для совместимости проверяйте точную сборку, формат пакета и весь граф. Если допускается асинхронный интерфейс, `import()` снимает ограничение синхронного `require()` на TLA.

### 🔬 14. Зачем условные `exports` и откуда берётся двойное состояние пакета?

Условные точки входа (conditional exports) в Node.js выбирают файл по условиям загрузки. Например, разные пути для `import` и `require`. Это договор загрузчика пакетов, а не синтаксис ESM.

Фрагмент `node_modules/demo/package.json`:

```json
{
  "name": "demo",
  "exports": {
    ".": {
      "import": "./index.mjs",
      "require": "./index.cjs",
      "default": "./index.mjs"
    }
  }
}
```

Здесь пути начинаются с `./`, а `default` стоит последним: при выборе имеют значение порядок и подходящее условие. Условие `import` означает способ загрузки, а не обязательно формат целевого файла. `exports` также задаёт публичные подпути; импорт закрытого подпути пакета может дать `ERR_PACKAGE_PATH_NOT_EXPORTED`.

Если обе точки входа независимо создают реестр, кеш или класс, приложение может загрузить два состояния. Это ловушка двойного пакета (dual-package hazard): запись через одну точку входа не видна другой, а `instanceof` может сравнивать разные конструкторы. Само наличие двух форматов ещё не создаёт проблему — существенна независимость экземпляров. При необходимости совместимости можно дать обеим оболочкам общую реализацию или явно изолировать состояние. Проверяйте оба способа загрузки в одном процессе. Браузер напрямую это поле не интерпретирует; сборщики применяют собственные условия разрешения.

### 🎯 15. Что происходит после `throw`?

`throw` прерывает обычный ход выполнения. Ошибка проходит вверх по активным вызовам до подходящего `catch`; при раскрутке выполняются встреченные `finally`. Инструкции после места выброса пропускаются. Выбросить можно любое значение, но `Error` даёт понятное сообщение и обычную поддержку диагностического стека в среде.

```js
const events = [];
function parse() {
  events.push("parse");
  throw new Error("bad input");
}
try {
  parse();
  events.push("after");
} catch (error) {
  events.push(error.message);
} finally {
  events.push("cleanup");
}
console.log(events); // ["parse", "bad input", "cleanup"]
```

`catch` получает именно выброшенное значение. Если чужой код выбросил `null`, чтение `error.message` само упадёт. Для доверенной внутренней операции можно договориться об `Error`; на внешней границе нужна проверка типа.

### 🎯 16. Почему `return` в `finally` опасен?

`finally` выполняется перед уходом из `try`/`catch`, в том числе при `return` и `throw`. Если он заканчивается обычно, прежний результат или ошибка продолжают путь. Его собственный `return` или `throw` заменяет предыдущий исход.

```js
function hiddenFailure() {
  try { throw new Error("lost"); }
  finally { return "ok"; }
}
function valueBeforeCleanup() {
  let value = 1;
  try { return value; }
  finally { value = 2; }
}
console.log(hiddenFailure(), valueBeforeCleanup()); // "ok", 1
```

Выражение возвращаемого значения вычисляется до `finally`. Для возвращаемого объекта изменение его свойств всё ещё видно через ту же ссылку. В `finally` обычно освобождают ресурс без смены результата. Если сама очистка может упасть, заранее решите, как сохранить обе причины; молчаливое замещение первой ошибки затрудняет диагностику. «Всегда» относится к обычному управлению потоком, а не к принудительному завершению процесса.

### 🎯 17. Почему окружающий `try` не ловит любую будущую ошибку?

`try` ловит исключения, возникшие, пока выполняется его блок. Отложенная функция (callback) выполняется позже, когда этот блок уже завершён. Аналогично, возвращённое обещание не превращается в синхронное исключение. Чтобы перехватить его отклонение в асинхронной функции, нужно дождаться его внутри `try`.

```js
async function read() {
  try { return await Promise.reject(new Error("bad")); }
  catch (error) { return error.message; }
}
console.log(await read()); // "bad"
```

С `return Promise.reject(...)` без `await` этот `catch` не обработал бы отклонение. Внешний вызывающий код должен был бы его наблюдать. Здесь важна граница распространения ошибки; подробные цепочки обещаний остаются в 1.10.

### 🎯 18. Как добавить контекст и не потерять исходную причину?

Если текущий слой может назвать операцию понятнее, создайте ошибку с причиной (`cause`). Вложенная причина сохраняет исходное значение, включая его собственный стек, когда оно является `Error`. Если нового контекста нет, `throw error` сохраняет тот же экземпляр.

```js
class ConfigError extends Error {
  constructor(message, options) {
    super(message, options);
    this.name = "ConfigError";
    this.code = "INVALID_CONFIG";
  }
}
try {
  try { JSON.parse("{"); }
  catch (cause) { throw new ConfigError("Cannot read settings", { cause }); }
} catch (error) {
  console.log(error.name, error.code, error.cause instanceof SyntaxError);
  // "ConfigError", "INVALID_CONFIG", true
}
```

Это как сопроводительная записка к сломанной детали: записка объясняет, на какой операции возник сбой, а исходная деталь остаётся для исследования. `cause` может быть любым значением; формат объединённого стека и автоматический вывод причины зависят от среды. `message`, `cause` и диагностический стек не следует бездумно отправлять пользователю или сериализовать вместе с секретами.

### 🎯 19. Где перехватывать ошибку и что делать с неизвестной?

Перехватывайте там, где есть осмысленное действие: исправить вход, выбрать допустимый запасной путь, добавить контекст или показать состояние ошибки. Если конкретный тип здесь не обрабатывается, передайте его выше.

```js
function readOptional(text) {
  try { return JSON.parse(text); }
  catch (error) {
    if (error instanceof SyntaxError) return { theme: "light" };
    throw error;
  }
}
console.log(readOptional("{").theme); // "light"
```

Этот запасной путь допустим только если продукт действительно разрешает отсутствие настройки. Для обязательного импорта молчаливое `{}` скроет потерю данных. Не определяйте тип ошибки по подстроке сообщения: формулировки различаются. `instanceof` удобен внутри одного окружения; между разными окружениями выполнения (realm) или экземплярами пакета нужен явно согласованный и проверяемый договор. Логировать ошибку обычно лучше один раз на границе, где известна операция.

### 🎯 20. Какие значения способен представить JSON?

JSON — текстовый формат: объекты со строковыми именами полей, массивы, строки, числа, `true`, `false`, `null`. Корневое значение не обязано быть объектом: `JSON.parse("42")` даёт число. Комментарии, одинарные кавычки и завершающие запятые не входят в JSON.

| Исходное значение при обычном `JSON.stringify`, без переопределений | Результат |
|---|---|
| `undefined`, функция, символ в свойстве объекта | Свойство пропущено |
| Те же значения или пустой слот в массиве | `null` на этой позиции |
| Корневой `undefined`, функция или символ | Возвращается `undefined`, не JSON-строка |
| `NaN`, `Infinity`, `-Infinity` | `null` |
| `BigInt` | `TypeError` без пользовательского преобразования |
| Циклическая ссылка | `TypeError` без пользовательского преобразования |
| `Date` | Обычно строка через `toJSON` |
| Обычный `Map` или `Set` без добавленных свойств | `"{}"` |

По умолчанию обходятся собственные перечисляемые строковые свойства объекта. Символьные ключи не включаются. У объекта могут сработать `toJSON` и getters; сериализация не обязана быть без побочных эффектов.

```js
const value = { missing: undefined, invalid: NaN, list: [undefined, , 3] };
console.log(JSON.stringify(value)); // '{"invalid":null,"list":[null,null,3]}'
console.log(JSON.stringify(undefined) === undefined); // true
```

Задача этой главы — договор передачи данных. Почему JSON не является общей глубокой копией, разобрано в [1.5](05-arrays-transformations-and-copying.md). Здесь вместо сохранения произвольного графа выбираем явное представление: например, дату как ISO-строку и большой идентификатор как строку десятичных цифр.

### 🎯 21. Как `replacer` и `toJSON` влияют на запись?

Второй аргумент `JSON.stringify` — функция преобразования (`replacer`) или массив разрешённых имён свойств. Функция вызывается и для корня с ключом `""`; затем для посещаемых значений. Возвращённый `undefined` исключает поле объекта, но оставляет `null` на позиции массива. Если корень заменён на `undefined`, JSON-строки не будет.

```js
const text = JSON.stringify({ id: 12n, secret: "token", rows: [undefined] },
  (key, value) => {
    if (key === "secret") return undefined;
    return typeof value === "bigint" ? value.toString() : value;
  });
console.log(text); // '{"id":"12","rows":[null]}'
console.log(JSON.stringify({ user: { id: 7, name: "Ada" }, id: 1 }, ["user", "id"]));
// '{"user":{"id":7},"id":1}'
```

Массив имён действует и на вложенные объекты, а не выбирает пути. Для даты `toJSON` вызывается до функции `replacer`, поэтому та обычно видит уже строку. Нельзя надёжно помечать все даты проверкой `value instanceof Date` внутри такого преобразования. Если типы важны, лучше до сериализации собрать объект передачи данных (Data Transfer Object, DTO) с явными полями и версией формата.

### 🎯 22. Как `reviver` восстанавливает значения и почему это ещё не проверка схемы?

Второй аргумент `JSON.parse` — функция восстановления (`reviver`). Дочерние значения посещаются до родительского. Возвращённое значение заменяет прочитанное, а `undefined` удаляет свойство. Для массива удаление создаёт пустой слот, не сдвиг. В конце посещается корень с ключом `""`; отсутствие общего `return value` может превратить весь результат в `undefined`.

```js
const visits = [];
const value = JSON.parse('{"count":2,"obsolete":true}', (key, item) => {
  visits.push(key);
  if (key === "obsolete") return undefined;
  return item;
});
console.log(value.count, Object.hasOwn(value, "obsolete")); // 2, false
console.log(visits); // ["count", "obsolete", ""]
```

Для восстановления даты нужен договор о конкретном поле или метке и проверка допустимого значения. Превращать каждую строку, похожую на дату, опасно: это может быть обычный текст. Функция восстановления тоже способна выбросить ошибку. При `JSON.parse(text, reviver)` перехваченный `SyntaxError` мог прийти из пользовательской функции, а не из синтаксического анализатора. Если нужно различать этапы, разделите чистый разбор и последующее преобразование.

**🔬 Точность чисел.** После чтения как `Number` целое за безопасным диапазоном уже может потерять цифры. Обычный `BigInt(value)` их не восстановит. В опубликованном ECMAScript 2026 у `reviver` есть третий аргумент `context`; для исходного примитива `context.source` позволяет прочитать исходную запись. Это не универсальный источник текста для родительских объектов. Во всех трёх проверенных сборках Node.js 22.13.1/24.21.0/26.4.0 аргумент доступен. Для внешних больших ID всё равно проще согласовать строковое представление; поддержку в целевых браузерах проверяйте отдельно.

### 🎯 23. Почему успешного разбора недостаточно и как проверить схему?

`JSON.parse` отвечает на вопрос о синтаксисе. Проверка схемы (schema validation) отвечает на вопрос приложения: объект ли это, какие поля разрешены, какие типы, диапазоны и версии допустимы? `null`, массив и строка — корректный JSON, но могут быть неверными настройками.

Следующий самостоятельный файл `.mjs` проверяет схему без библиотеки. Договор: ровно поля `version: 1` и `theme: "light" | "dark"`. Разбор и проверка разделены, поэтому тип `SyntaxError` имеет ясный источник.

```js
class SettingsError extends Error {
  constructor(code, message, options) {
    super(message, options);
    this.name = "SettingsError";
    this.code = code;
  }
}
function readSettings(text) {
  if (typeof text !== "string") throw new TypeError("Expected text");
  let value;
  try { value = JSON.parse(text); }
  catch (cause) {
    if (!(cause instanceof SyntaxError)) throw cause;
    throw new SettingsError("SYNTAX", "Settings are not JSON", { cause });
  }
  if (value === null || typeof value !== "object" || Array.isArray(value) ||
      !Object.hasOwn(value, "version") || !Object.hasOwn(value, "theme") ||
      Object.keys(value).length !== 2 || value.version !== 1 ||
      !["light", "dark"].includes(value.theme)) {
    throw new SettingsError("SCHEMA", "Unsupported settings");
  }
  return { version: 1, theme: value.theme };
}
console.log(readSettings('{"version":1,"theme":"dark"}').theme); // "dark"
```

Разрешённые поля переносятся в новый DTO явно. Строка `"version": "1"` не равна числу `1`; политика преобразований должна быть отдельным решением. Можно использовать библиотеку схем, но её типы и подробная конфигурация относятся к домену TypeScript. Здесь важна сама граница доверия: разобрать → проверить → использовать.

### 🎯 24. Как соединить модули, ошибки и JSON в одном понятном API?

Разделите ответственность по причинам изменения: модуль формата знает версию и схему; модуль импорта добавляет контекст операции; интерфейс решает, как показать отказ. Для необязательного загрузчика можно использовать `import()`, но не смешивать отсутствие модуля с неверными данными.

Удобный договор импорта: принять строку → разобрать синтаксис → проверить версию и форму → создать согласованное значение → вернуть его либо передать ошибку с сохранённой причиной. Ошибки схемы не следует превращать в успешный пустой результат. На выходе сериализуйте только разрешённые поля, чтобы формат не зависел от внутреннего устройства объекта.

Проверьте три независимых случая: модуль не загрузился, строка не является JSON, JSON корректен, но схема неверна. Четвёртый случай — успешный результат. Эти проверки дают больше пользы, чем один тест с «хорошими данными». Полный договор с несколькими файлами реализуется в комплексном упражнении.

## Типичные ошибки

- Приравнивать ESM к «асинхронному `require`» и смешивать связывание с выполнением.
- Ожидать, что `import { count }` и `const { count } = require(...)` одинаково отражают обновления.
- Считать `sideEffects: false` безобидной настройкой размера.
- В каждом слое перехватывать и заново создавать ошибку только из её сообщения.
- Делать `return` из `finally`, скрывая неуспешную операцию.
- Принимать `{}` как универсальное восстановление после неверного JSON.
- Удалять поле через `reviver`, забыв вернуть корень, или превращать любой текст в дату.

## Ловушки на интервью

- Цикл ESM допустим; момент чтения определяет, возникнет ли TDZ.
- `export default value` и `export { value as default }` имеют разный договор с локальным именем.
- `require(esm)` зависит от версии Node.js и TLA во всём графе.
- `finally` сохраняет прежний исход лишь при обычном завершении самого блока.
- `JSON.stringify(undefined)` возвращает `undefined`; это не строка `"undefined"`.
- `JSON.parse("null")` успешен, хотя схема настроек может запрещать `null`.

## Практические рекомендации

Задавайте формат модулей явно. Для состояния предпочитайте операции с ясным владельцем. Сокращайте циклы, когда они затрудняют инициализацию. На пакетной границе проверяйте оба пути загрузки и идентичность состояния. Удаление кода подтверждайте результатом сборки, а не формой строки импорта.

Держите перехват ошибки рядом с действием, которое он оправдывает. Сохраняйте причину при добавлении контекста, разделяйте сообщение для человека и устойчивый код ошибки. На JSON-границе документируйте версию, допустимые поля, неизвестные поля и представление дат и больших чисел. Предсказуемый формат полезнее попытки сериализовать любой объект.

## Как объяснить тему на интервью за 30–60 секунд

### Модульные границы

> ESM задаёт статические импорты и экспорты, собственную область видимости и живые привязки. Связи устанавливаются до выполнения тела. В цикле важно, успело ли экспортируемое имя инициализироваться к моменту чтения. Для условной загрузки есть `import()`, возвращающий обещание пространства имён. CommonJS нужно знать для совместимости: он возвращает `module.exports`, а поведение его взаимодействия с ESM зависит от Node.js или сборщика.

### Граф и сборка

> Статическая структура ESM помогает сборщику увидеть используемые экспорты. Но tree shaking должен сохранить побочные эффекты. Поэтому именованный импорт не гарантирует уменьшение результата, а неверное `sideEffects: false` может удалить нужную инициализацию. Я проверю итог сборки и поведение приложения. Top-level await влияет на готовность зависимых модулей; для `require(esm)` в проверенных современных Node.js весь граф должен обходиться без него.

### Ошибки

> `throw` передаёт неуспех ближайшему активному обработчику. `finally` нужен для освобождения ресурсов; собственный `return` или `throw` в нём заменит прежний исход. Перехватываю там, где могу обработать ошибку или добавить полезный контекст. Для обёртки сохраняю исходное значение в `cause`, неизвестные ошибки передаю дальше. Отклонение обещания перехватываю через `await` внутри `try` или через обработчик обещания.

### JSON-граница

> JSON сохраняет ограниченный набор данных, поэтому я сначала задаю внешний формат. `replacer` управляет записью, `reviver` — восстановлением, но ни один автоматически не доказывает корректность данных для приложения. Сначала разбираю синтаксис, затем проверяю тип корня, версию, поля и диапазоны. Синтаксическая ошибка и ошибка схемы различаются, а большая числовая строка не должна случайно пройти через неточный `Number`.
