Эта глава нужна не для заучивания терминов, а для ответа на три практических вопроса:

1. **Где имя видно?**
2. **С какого момента его можно читать и изменять?**
3. **Какое состояние выполнения активно в данный момент?**

Начнём с привычных слов — «переменная», «объявление», «область видимости» — и шаг за шагом соберём из них цельную картину. Точные термины спецификации тоже будут, но только после простого объяснения и только там, где они помогают понять результат кода.

Главная цель: не просто узнать знакомые слова, а суметь посмотреть на фрагмент кода и спокойно объяснить, **какое имя будет найдено, доступно ли оно сейчас и что произойдёт дальше**.

Полный разбор функций и замыканий будет в разделе 1.3, модулей — в 1.7, цикла событий (event loop) — в 1.9. Здесь мы берём из этих тем только то, что необходимо для понимания объявлений и области видимости (scope).

Основная часть идёт от простого к сложному. Каждый следующий вопрос опирается на предыдущий:

### Два режима чтения

**🎯 Первый проход — интервью-ядро.** Прочитайте вопросы 1–5, 8–11 и 13–15. ## Ментальная модель

Сначала — вся тема в семи строках:

1. Объявление сообщает JavaScript: «в этой области будет такое имя».
2. Для имени создаётся **привязка (binding)** — связь имени с состоянием и значением.
3. До выполнения обычных строк JavaScript уже подготавливает объявления текущей выполняемой части кода.
4. `var`, `let`, `const` и `function` подготавливаются по-разному.
5. При чтении имени поиск начинается в текущей области и идёт наружу.
6. Ближайшее совпадающее имя останавливает поиск, даже если оно пока находится в TDZ.
7. Вызов функции создаёт новый контекст выполнения; обычный блок `{ ... }` может создать область, но не новый вызов.

Важно: JavaScript не переносит строки объявлений вверх файла. **Подъём объявлений (hoisting)** — название наблюдаемого поведения, а не операция «вырезать строку и вставить наверх».

### Три ориентира перед началом

- **Имя → привязка → значение** похоже на имя контакта → запись контакта → текущий номер.
- **Поиск имени наружу** похож на поиск настройки: сначала локальная, затем родительская.
- **Стек вызовов** похож на рецепт с подрецептом: основной шаг ждёт, пока закончится вложенный.

Это три отдельные подсказки, а не одна модель движка. Ниже каждая будет объяснена только там, где она действительно подходит.

## Связное объяснение в формате вопросов и ответов

### 1. Что в JavaScript называют переменной?

В повседневной разработке **переменной (variable)** называют имя, через которое код читает значение и, если разрешено, заменяет его другим. Для большинства разговоров этого достаточно.

Чтобы понять scope, TDZ и `const`, нужно один раз разделить три близких понятия:

- **идентификатор (identifier)** — имя в исходном коде, например `count`;
- **привязка имени (binding)** — связь этого имени с состоянием и текущим значением;
- **значение (value)** — например число `1`, строка или объект.

```js
let count = 1;
```

Здесь:

- `count` — идентификатор;
- `let count` объявляет привязку;
- `1` — значение, которым привязка инициализируется.

Условно привязку можно записать так:

```text
имя: count
состояние: инициализирована
текущее значение: 1
можно присвоить другое значение: да
```

Метафора «переменная — коробка» годится для самого начала, но не объясняет TDZ, затенение и поведение `const`. Модель «имя → привязка → значение» для этой темы надёжнее.

#### Почему `const` всё равно часто называют переменной?

Да, в обычной речи `const` тоже называют переменной. Точнее: `const` создаёт привязку, которую после инициализации нельзя перенаправить на другое значение.

```js
const user = { name: "Ada" };

user.name = "Grace"; // допустимо: объект изменяется
// user = {};         // TypeError: привязку нельзя переназначить
```

`const` не делает объект неизменяемым. Он запрещает повторное присваивание самой привязке.

### 2. Чем отличаются объявление, создание привязки, инициализация и присваивание?

Эти слова часто смешивают, из-за чего TDZ кажется магией. На самом деле это четыре разных события:

```js
let count = 1;
count = 2;
```

1. **Объявление (declaration)** — запись `let count`, которая сообщает: «в этой области есть имя `count`».
2. **Создание привязки (binding creation)** — JavaScript подготавливает внутреннюю запись для имени.
3. **Инициализация (initialization)** — привязка впервые становится доступной и получает значение. Здесь это `1`.
4. **Присваивание (assignment)** — уже работающая изменяемая привязка получает новое значение. Здесь это `2`.

```text
declaration → binding создан → initialization → дальнейшие assignment
                    └ TDZ ───┘          (TDZ: let / const / class)
```

Представьте банковский счёт, который уже зарегистрирован в системе, но ещё не активирован. Система знает, какой это счёт, однако пользоваться им пока нельзя. Активация похожа на initialization; последующие переводы меняют баланс, как assignment меняет значение. Аналогия объясняет именно состояние «существует, но недоступно», а не все правила переменных.

#### Почему нельзя считать инициализацию обычным первым присваиванием?

До инициализации лексическая привязка уже существует, но читать её нельзя. После инициализации она переходит в обычное рабочее состояние. Эта граница и создаёт TDZ.

Сравним несколько форм:

```js
let a;        // при выполнении этой строки a инициализируется значением undefined
const b = 1;  // b должна получить значение сразу
var c;        // свежая var-привязка уже была инициализирована undefined раньше
```

Обычное объявление `const` требует **инициализатор (initializer)** — выражение справа от `=`:

```js
// const token; // SyntaxError
const token = "abc";
```

#### Важное уточнение про `var`

У нового имени `var` привязка получает `undefined` ещё до обычного выполнения строк. Но повторное совместимое объявление `var` использует ту же привязку и не стирает уже записанное значение.

```js
var score = 10;
var score;

console.log(score); // 10, не undefined
```

### 3. Чем отличаются `var`, `let` и `const`?

Главная ошибка — сравнивать их только по правилу «можно или нельзя менять значение». На интервью лучше пройтись по четырём вопросам:

1. Где имя видно?
2. Что произойдёт при чтении до строки объявления?
3. Можно ли присвоить другое значение?
4. Можно ли ещё раз объявить то же имя в этой области?

| Свойство | `var` | `let` | `const` |
|---|---|---|---|
| Основная область | ближайшая функция или верхний уровень скрипта/модуля | лексическая, обычно блок | лексическая, обычно блок |
| До выполнения строки | свежая привязка уже содержит `undefined` | привязка не инициализирована, действует TDZ | привязка не инициализирована, действует TDZ |
| Нужен инициализатор в обычном объявлении | нет | нет | да |
| Повторное присваивание | да | да | нет |
| Повторное объявление тем же видом в одной области | обычно да | нет | нет |
| Современная рекомендация | знать для legacy-кода и интервью | использовать при намеренном повторном присваивании | выбор по умолчанию |

#### `var` не имеет обычной блочной области

```js
function readLegacyValue() {
  if (true) {
    var message = "готово";
  }

  console.log(message); // "готово"
}
```

`message` принадлежит всей функции, а не только блоку `if`. Фигурные скобки `if` для `var` не становятся забором.

#### `let` и `const` ограничены блоком

```js
function readModernValue() {
  if (true) {
    const message = "готово";
    console.log(message); // "готово"
  }

  console.log(message); // ReferenceError
}
```

#### Как выбирать в рабочем коде?

- **`const` по умолчанию.** Он сразу показывает читателю: это имя не будет переназначено.
- **`let`, если переназначение действительно нужно.** Например, для счётчика или значения, которое вычисляется по шагам.
- **Новый `var` — только по конкретной причине.** Обычно такой причины нет.
- **Старый `var` нужно понимать.** Он всё ещё встречается в legacy-коде, сторонних скриптах и интервью-задачах.

Механическая замена `var` на `let` или `const` не всегда безопасна. Она может изменить область видимости, поведение до строки объявления, правила повторного объявления и работу обратных вызовов (callbacks) в цикле.

### 4. Что такое область видимости и какие области бывают?

**Область видимости (scope)** определяет, где конкретное имя относится к конкретной привязке. Проще говоря, она отвечает на вопрос:

> Если в этой строке написать `name`, какую именно переменную имеет в виду JavaScript?

Важная деталь: «имя относится к привязке» ещё не означает «значение уже можно прочитать». В TDZ поиск уже находит нужную привязку, но чтение запрещено.

#### Глобальная область видимости (global scope)

**Глобальная область (global scope)** — самый внешний уровень для данного скрипта и его окружения. Глобальные имена обычно доступны из вложенного кода, если внутри нет своего имени с таким же названием.

```js
const applicationName = "Dashboard";

function printName() {
  console.log(applicationName);
}
```

Точное поведение глобальных объявлений зависит от среды запуска. Мы вернёмся к этому в вопросе 12.

#### Функциональная область видимости (function scope)

**Функциональная область (function scope)** принадлежит телу функции. В ней находятся параметры и локальные имена. `var` останавливается на границе ближайшей функции, но не на границе `if`, `for` или простого блока внутри неё.

```js
function calculate(price) {
  var tax = price * 0.17;
  const total = price + tax;
  return total;
}

// price, tax и total здесь недоступны
```

Важно: одна функция может быть вызвана много раз, и каждый вызов получает свой набор параметров и локальных привязок:

```js
function addOne(value) {
  let result = value + 1;
  return result;
}

addOne(1);  // один набор value/result
addOne(10); // другой набор value/result
```

#### Блочная область видимости (block scope)

**Блочная область (block scope)** ограничивает `let`, `const` и `class` ближайшей подходящей лексической границей. Чаще всего это фигурные скобки блока.

```js
if (true) {
  let state = "inside";
  const ready = true;
}

// state и ready здесь недоступны
```

Такие границы встречаются не только в отдельном `{ ... }`:

- обычных блоках `{ ... }`, в том числе используемых как тела `if`, `while` и `try`;
- заголовке `for` с `let`/`const` и создаваемых циклом привязках итераций;
- параметре `catch` и его блоке;
- едином `CaseBlock`, содержащем все `case` одного `switch`.

Объектный литерал `{ name: "Ada" }` лишь похож на блок фигурными скобками. Это объект, и новую область видимости он не создаёт.

#### Модульная область видимости (module scope)

**Модульная область (module scope)** — верхний уровень конкретного ES module:

```js
// settings.js, загруженный как ES module
const token = "module-only";
var retries = 3;
```

Оба имени видны внутри модуля, но не становятся автоматически свойствами глобального объекта.

#### Что такое лексическая область видимости?

**Лексическая область видимости (lexical scope)** означает: связь функции с внешними областями определяется тем, **где функция написана**, а не тем, откуда её потом вызвали.

Это не пятый вид области рядом с global/function/block/module. Это общее правило, которое связывает вложенный код с внешним.

```js
const level = "global";

function outer() {
  const level = "outer";

  function inner() {
    console.log(level);
  }

  inner();
}
```

`inner` написана внутри `outer`, поэтому её ближайшая внешняя область — `outer`. Именно там она находит `level`.

#### Может ли внешняя область читать локальные имена внутренней?

Нет. Вложенный код может смотреть наружу, но внешний код не получает доступ к локальным именам вложенной функции.

```js
function createMessage() {
  const secret = "local";
  return secret;
}

console.log(secret); // ReferenceError
```

### 5. Как JavaScript решает, к какой переменной относится имя?

Этот поиск называется **разрешением идентификатора (identifier resolution)**.

Упрощённый алгоритм:

1. проверить текущую область;
2. если имени нет — перейти во внешнюю область;
3. продолжать до глобальной области;
4. если привязка нигде не найдена — обычное чтение бросит `ReferenceError`.

Путь от текущей области к внешним часто называют **цепочкой областей видимости (scope chain)**.

Полезная аналогия — настройки с наследованием. Представьте компонент, который ищет настройку `theme`: сначала свою, затем настройку родителя, потом настройку всего приложения. Как только значение найдено, поиск прекращается. JavaScript делает похожий поиск для имён; только вместо настроек у него привязки.

```js
const source = "global";

function outer() {
  const source = "outer";

  function inner() {
    const suffix = "!";
    console.log(source + suffix);
  }

  inner();
}

outer(); // "outer!"
```

Для `source` внутри `inner` поиск выглядит так:

```text
область inner: source нет
  ↓
область outer: source найден → "outer"
  ↓
дальше искать не нужно
```

Для `suffix` имя находится сразу в `inner`.

#### Что такое затенение?

**Затенение (shadowing)** — ситуация, когда во внутренней области есть собственная привязка с тем же именем, что и снаружи.

```js
const label = "outer";

{
  const label = "inner";
  console.log(label); // "inner"
}

console.log(label); // "outer"
```

Внутренняя привязка не меняет и не удаляет внешнюю. Она просто находится первой, поэтому внутри блока внешняя временно «не видна» под этим именем.

#### Место вызова функции меняет поиск имён?

Нет. В JavaScript важнее место, где функция **определена**, а не место, где её **вызвали**.

```js
const role = "guest";

function createReader() {
  const role = "admin";
  return () => role;
}

function run(reader) {
  const role = "operator";
  return reader();
}

console.log(run(createReader())); // "admin"
```

Возвращённая функция была создана внутри `createReader`, поэтому ищет `role` через эту область и получает `"admin"`. Локальная `role` из `run` не вклинивается в эту цепочку только потому, что `run` вызвала функцию.

Это необходимое для этой главы следствие **замыкания (closure)**: функция сохраняет доступ к привязкам из места определения. Полная тема замыканий будет в разделе 1.3.

#### Имя и свойство объекта — это один и тот же поиск?

Нет.

```js
console.log(missingName); // ReferenceError
```

```js
const config = {};
console.log(config.missingName); // undefined
```

Это два разных механизма. В первом примере JavaScript не нашёл саму привязку `missingName`, поэтому возник `ReferenceError`. Во втором привязка `config` существует; уже после этого JavaScript ищет свойство объекта и, не найдя его, возвращает `undefined`.

### 6. Что происходит до выполнения первой строки?

JavaScript не начинает выполнять текущую часть кода совершенно вслепую с первой строки. Сначала он подготавливает её объявления, а уже потом выполняет инструкции.

```text
1. подготовка объявлений
   определить области, проверить конфликты, подготовить привязки

2. выполнение (evaluation)
   выполнять инструкции по порядку
```

Представьте театральный спектакль. До поднятия занавеса организаторы уже знают список ролей и реквизита. Но готовность разная: актёр для объявления функции (function declaration) уже на месте; для `var` выделено пустое место с `undefined`; место для `let`/`const` зарезервировано, но реквизит ещё нельзя брать. Во время спектакля действия всё равно идут в написанном порядке — сцены физически не переставляли.

Это только аналогия готовности объявлений. Она не означает, что движок буквально делает два прохода по файлу или хранит «список реквизита» как обычный объект.

#### Зачем вообще нужна подготовка объявлений?

Благодаря подготовке JavaScript уже знает:

- какие имена принадлежат текущей области;
- какие объявления конфликтуют;
- в каком начальном состоянии находится каждая привязка;
- какие объявления функций уже должны ссылаться на готовые функции.

```js
console.log("начало");
let id;
let id; // SyntaxError
```

Здесь два `let id` конфликтуют. Это **ранняя статическая ошибка (Early Error)**: весь этот скрипт не допускается к обычному выполнению, поэтому даже предыдущая строка `"начало"` не выводится.

<details>
<summary>🔬 Точная деталь: это не одна универсальная «фаза создания»</summary>

Подготовка происходит не один раз на весь файл и не одним общим алгоритмом для любого кода:

- скрипт проходит `GlobalDeclarationInstantiation` перед выполнением своих инструкций;
- `FunctionDeclarationInstantiation` происходит при каждом вызове функции;
- `BlockDeclarationInstantiation` происходит при входе в выполняемый непустой блок;
- у модулей есть собственные шаги связывания и выполнения.

Поэтому фраза «сначала creation phase, потом execution phase» — удобная interview-модель, а не точное название единого алгоритма ECMAScript. На интервью важнее правильно предсказать состояние привязок, чем перечислить эти названия.

</details>

### 7. Что такое контекст выполнения, стек вызовов и лексическое окружение?

Эти понятия описывают разные вещи. Короткая версия:

| Понятие | Простой вопрос |
|---|---|
| Область видимости (scope) | Где в исходном коде видно это имя? |
| Контекст выполнения (execution context) | Какой код сейчас выполняется и какое состояние ему нужно? |
| Стек вызовов (call stack) | Какие вызовы ещё не закончились и к какому вернуться? |
| Лексическое окружение (lexical environment) | Где во время выполнения искать привязки текущей области и её родителей? |

#### Контекст выполнения

**Контекст выполнения (execution context)** — рабочее состояние, которое нужно JavaScript для выполнения конкретного скрипта, модуля, вызова функции или `eval`-кода.

Когда функция вызывается, JavaScript создаёт контекст именно для этого вызова. Поэтому два одновременных или последовательных вызова одной функции не делят один набор параметров и локальных переменных.

```js
const rate = 2;

function calculate(base) {
  const result = base * rate;
  return result;
}

calculate(5);
```

Практическая трассировка:

```text
1. выполняется исходный контекст
2. вызов calculate(5) создаёт контекст выполнения функции
3. base и result находятся локально
4. rate находится во внешней области
5. return завершает вызов
6. управление возвращается в исходный контекст
```

#### Стек вызовов

**Стек вызовов (call stack)** показывает порядок незавершённых вызовов. Последняя вызванная функция должна завершиться первой, чтобы программа могла вернуться в точку, где её вызвали.

Это похоже на рецепт с подрецептами: основной рецепт остановился на шаге «приготовить соус», рецепт соуса — на шаге «смешать заправку». Сначала заканчивается заправка, затем соус, затем основное блюдо.

```js
function first() {
  second();
}

function second() {
  third();
}

function third() {
  return "done";
}

first();
```

В самый глубокий момент:

```text
third
second
first
entry
```

После `return` вызовы завершаются в обратном порядке: `third` → `second` → `first`.

#### Обычный блок создаёт новый кадр стека (stack frame)?

Нет.

```js
function render() {
  const mode = "full";

  if (mode === "full") {
    const label = "Details";
    console.log(label);
  }
}
```

`render()` — вызов функции, поэтому он добавляет кадр в стек. `if` — только часть уже выполняемой функции. Он создаёт отдельную область для `label`, но не вызывает функцию и не добавляет новый кадр стека.

#### Что такое лексическое окружение?

**Лексическое окружение (lexical environment)** можно понимать как текущий набор привязок плюс связь с внешним набором. Именно по этой связи поиск имени идёт наружу.

Если вернуться к аналогии с наследуемыми настройками: Environment Record — это набор настроек одного уровня, а `[[OuterEnv]]` — ссылка на родительский уровень.

<details>
<summary>🔬 Точная деталь: Environment Record, LexicalEnvironment и VariableEnvironment</summary>

В современной терминологии спецификации сами привязки представляет **запись окружения (Environment Record)**. У неё есть внешняя ссылка `[[OuterEnv]]`, по которой выполняется поиск имени.

```text
Environment Record текущей области
├─ локальные привязки
└─ [[OuterEnv]] → Environment Record внешней области
                       └─ [[OuterEnv]] → ...
```

В контексте выполнения есть ссылки:

```text
Execution Context
├─ LexicalEnvironment  → текущая Environment Record для поиска имён
└─ VariableEnvironment → Environment Record для var-scoped объявлений
```

При входе в обычный непустой блок текущая `LexicalEnvironment` временно указывает на новую блочную Environment Record. Это не превращает `var` в объявление с блочной областью: `var` всё равно относится к своей VariableEnvironment.

Реальный движок может оптимизировать эти структуры. Не нужно утверждать, что каждая Environment Record обязательно существует в памяти как обычный JavaScript-объект.

</details>

Итого: scope — карта видимости в коде; Environment Record — точная модель набора привязок; execution context — состояние активного выполнения; call stack — порядок незавершённых вызовов. Это связанные, но не взаимозаменяемые понятия.

### 8. Что на интервью называют подъёмом объявлений (hoisting)?

**Подъём объявлений (hoisting)** — неформальное название эффекта, при котором объявление влияет на код ещё до строки, где оно написано. Причина: привязка подготавливается до обычного выполнения инструкций.

Строки не перемещаются, и движок не переписывает исходник. В театральной аналогии роли и реквизит подготовили до занавеса, но порядок сцен остался прежним.

#### Почему `var` до инициализатора даёт `undefined`?

```js
console.log(total); // undefined
var total = 3;
```

До выполнения инструкций свежая `var`-привязка уже существует и содержит `undefined`. Поэтому происходит следующее:

1. `console.log` читает `undefined`;
2. инициализатор `= 3` выполняет присваивание.

Полезная схема:

```text
подготовка: привязка total → undefined
выполнение: console.log(total)
выполнение: total = 3
```

Это временная схема происходящего, а не «эквивалентный переписанный код».

#### Поднимаются ли `let` и `const`?

Их привязки тоже создаются заранее. Разница в том, что они **не получают `undefined`** и остаются неинициализированными. Поэтому фраза «`let` и `const` не поднимаются» слишком грубая и приводит к ошибкам.

```js
console.log(total); // ReferenceError
let total = 3;
```

Поиск уже находит именно эту `total`, но значение ещё нельзя прочитать.

#### Что происходит с объявлением функции?

```js
ready(); // работает

function ready() {
  return true;
}
```

Привязка объявления функции обычно сразу получает объект функции во время подготовки объявлений. Поэтому функцию можно вызвать раньше строки, где она написана.

#### Сводная картина

| Объявление | Состояние до текстовой позиции |
|---|---|
| `var value` | свежая привязка инициализирована `undefined` |
| `let value` | привязка существует, но не инициализирована |
| `const value = ...` | привязка существует, но не инициализирована |
| `class Value {}` | привязка существует, но не инициализирована |
| `function value() {}` | привязка обычно уже содержит функцию |
| `var value = function () {}` | `value === undefined`; выражение ещё не вычислено |
| `const value = function () {}` | `value` находится в TDZ |

#### Что важно сказать на интервью?

> Hoisting — результат подготовки объявлений до выполнения строк, а не перенос кода. У `var` заранее есть `undefined`, `let`/`const` существуют, но находятся в TDZ, а function declaration обычно уже содержит функцию.

### 9. Что такое TDZ и почему это не просто «строки выше объявления»?

**Временная мёртвая зона (Temporal Dead Zone, TDZ)** — время от входа в лексическую область до инициализации конкретной привязки `let`, `const` или `class`. Привязка уже создана, но любое чтение пока приводит к `ReferenceError`.

```js
{
  // TDZ для user уже началась
  const user = { id: 1 }; // здесь инициализация завершает TDZ
  console.log(user.id);
}
```

Полезная аналогия — зарегистрированный, но ещё не активированный пропуск. Сотрудник уже есть в системе: запрос по имени находит именно его запись. Но турникет не пропускает до активации. Так же TDZ означает «binding найден, но ещё не готов», а не «такого имени пока нет».

TDZ — это период выполнения, а не просто «все строки выше объявления». Например, при каждом новом входе в блок начинается новый жизненный цикл его привязок.

#### Почему внутренняя привязка скрывает внешнюю ещё до своей строки?

```js
const state = "outer";

{
  console.log(state); // ReferenceError
  const state = "inner";
}
```

При входе в блок внутренняя `state` уже создана. Поиск находит её первой и останавливается. JavaScript не перескакивает к внешней `state` только потому, что внутренняя ещё не инициализирована.

#### Что происходит с `let name;` без инициализатора?

```js
{
  // console.log(name); // ReferenceError: TDZ
  let name;
  console.log(name); // undefined
}
```

Когда выполнение доходит до `let name;`, привязка инициализируется значением `undefined`, и TDZ заканчивается. Значит, `let` без `=` всё равно имеет точку инициализации.

#### Почему `typeof` иногда безопасен, а иногда нет?

```js
console.log(typeof neverDeclared); // "undefined"
```

Здесь никакой привязки `neverDeclared` нет. Только для такого неразрешимого идентификатора у `typeof` есть специальный безопасный результат.

```js
console.log(typeof later); // ReferenceError
let later = 1;
```

Здесь привязка `later` существует, но ещё не инициализирована. `typeof` не является обходом TDZ.

#### Почему self-reference падает?

```js
let value = value; // ReferenceError
```

Правая `value` уже относится к создаваемой локальной привязке, а не к возможной внешней. Но локальная привязка ещё в TDZ, поэтому инициализировать её «самой собой» нельзя.

#### Простое правило

> Если поиск уже выбрал `let`/`const`/`class`-привязку, а её initialization ещё не произошла, чтение заканчивается `ReferenceError`. Поиск не продолжается наружу.

### 10. Почему объявление функции и функциональное выражение ведут себя по-разному до своей строки?

Похожий внешний вид скрывает разные механизмы:

- **объявление функции (function declaration)** само объявляет имя функции;
- **функциональное выражение (function expression)** создаёт значение-функцию, которое затем кладут в `var`, `let` или `const`.

Поэтому для раннего вызова важно не только «это функция», а **как и когда готовится содержащая её привязка**.

#### Объявление функции

```js
ready(); // работает

function ready() {
  return "ok";
}
```

Во время подготовки объявлений привязка `ready` уже получила объект функции. В театральной аналогии актёр уже на сцене до начала первой реплики.

#### Функциональное выражение в `var`

```js
ready(); // TypeError: ready is not a function

var ready = function () {
  return "ok";
};
```

Имя `ready` успешно найдено, но пока содержит `undefined`. Ошибка возникает не при поиске имени: JavaScript пытается вызвать найденное значение и получает `TypeError`, потому что `undefined` — не функция.

#### Функциональное выражение в `const`

```js
ready(); // ReferenceError

const ready = function () {
  return "ok";
};
```

Привязка `ready` находится в TDZ, поэтому чтение сразу даёт `ReferenceError`. До создания самой функции выполнение ещё не дошло.

#### А что с именованным функциональным выражением?

```js
const factorial = function calculate(n) {
  return n <= 1 ? 1 : n * calculate(n - 1);
};
```

Внешнее имя здесь — `factorial`. Имя `calculate` доступно самой функции, например для рекурсии, но не создаёт обычную внешнюю переменную `calculate`.

Полные различия форм функций относятся к разделу 1.3. Здесь важен только момент готовности привязки.

### 11. Чем затенение отличается от повторного объявления и что называют illegal shadowing?

Сначала простое различие:

- **затенение (shadowing)** — одинаковые имена принадлежат **разным** вложенным областям;
- **повторное объявление (redeclaration)** — два объявления пытаются занять одно имя в **одной и той же** эффективной области;
- **illegal shadowing** — распространённое interview-название некоторых конфликтов, которые выглядят как затенение, но отдельной внутренней привязки на самом деле не получается.

Как два списка команд могут содержать своего Алекса, так разные области могут содержать своё `mode`. Две записи с одним именем в одной области уже конфликтуют. Конкретные правила зависят от `var`/`let`/`const`.

#### Повторное объявление

Здесь оба `mode` относятся к одной блочной области, поэтому второй `let` запрещён:

```js
let mode = "a";
let mode = "b"; // SyntaxError
```

#### Почему внешний `var` + внутренний `let` допустимы?

```js
var mode = "outer";

{
  let mode = "inner";
  console.log(mode);
}
```

`var mode` принадлежит внешней области, а `let mode` — отдельному блоку. Поэтому существуют две разные привязки, и это обычное допустимое shadowing.

#### Почему внешний `let` + `var` во внутреннем блоке недопустимы?

```js
let mode = "outer";

{
  var mode = "inner";
}
```

`var` игнорирует границу обычного блока. Он пытается объявить `mode` в окружающей функциональной или глобальной `var`-области — там же, где уже находится внешний `let mode`. Получается не две вложенные привязки, а конфликт в одной эффективной области.

На интервью это часто называют **недопустимым затенением (illegal shadowing)**. Более точная формулировка: «`var` выходит из блока и конфликтует с лексическим объявлением; отдельная внутренняя привязка не создаётся».

#### Базовая матрица для одной области

| Уже объявлено | новый `var` | новый `let` | новый `const` | новое объявление функции |
|---|---:|---:|---:|---:|
| `var` | обычно допустимо | ошибка | ошибка | зависит от контекста; лучше не полагаться |
| `let` | ошибка | ошибка | ошибка | ошибка |
| `const` | ошибка | ошибка | ошибка | ошибка |

Комбинации с параметрами, прямым `eval` и устаревшими block functions имеют дополнительные правила. Для обычного интервью важнее безошибочно применять таблицу выше, а редкие исключения рассматривать только в конкретном коде.

#### Почему одинаковые `let` в разных `case` конфликтуют?

Внешне `case` похожи на отдельные ветки, но все они принадлежат одному общему лексическому блоку `switch` (`CaseBlock`). Поэтому одинаковые `let`/`const` конфликтуют ещё до выбора ветки.

```js
const status = "idle";

switch (status) {
  case "idle":
    let message = "Waiting";
    break;
  case "done":
    let message = "Complete"; // SyntaxError
    break;
}
```

Чтобы у каждой ветки была своя область, добавьте блоки явно:

```js
const status = "idle";

switch (status) {
  case "idle": {
    const message = "Waiting";
    break;
  }
  case "done": {
    const message = "Complete";
    break;
  }
}
```

#### Выполнятся ли строки перед конфликтом?

Если конфликт является Early Error внутри одного скрипта, модуля или тела функции, вся эта единица кода отвергается до выполнения инструкций.

```js
console.log("не выполнится");
const key = "a";
var key = "b"; // SyntaxError до выполнения инструкций
```

### 12. Почему глобальная переменная не всегда является свойством `globalThis`?

Короткий ответ: потому что «видно глобально» и «лежит как свойство глобального объекта» — не одно и то же. Кроме того, результат зависит от способа запуска кода.

Перед ответом на задачу о верхнем уровне всегда уточняйте среду:

- classic script в браузере;
- ES module в браузере;
- ES module в Node.js;
- CommonJS-файл в Node.js;
- интерактивная консоль, у которой могут быть свои правила.

Сначала разделим язык и окружение.

#### Что определяет ECMAScript, а что предоставляет среда выполнения?

**ECMAScript** — сам язык: его синтаксис, объявления, функции, объекты, привязки и правила выполнения.

**Среда выполнения (host environment)** — браузер, Node.js или другая система, которая запускает язык и добавляет свои API:

| Язык ECMAScript | Среда выполнения |
|---|---|
| `let`, `const`, `var`, функции, promises | DOM, `window`, браузерные timers |
| правила областей и поиска имён | файлы, `process`, загрузка модулей Node.js |
| стандартные встроенные объекты | способы загрузки скриптов/модулей и глобальные имена среды выполнения |

Например, `setTimeout` знаком почти каждому JavaScript-разработчику, но это API среды выполнения, а не часть самого ECMAScript.

#### Что такое глобальный объект?

**Глобальный объект (global object)** — объект среды, в свойствах которого находятся многие глобальные API и значения. `globalThis` — стандартный переносимый способ получить доступ к соответствующему глобальному значению `this`.

`window` подходит только для определённых браузерных контекстов. Его нет, например, в Web Worker и Node.js.

Но это не контейнер вообще для всех имён верхнего уровня:

> Глобальная привязка и свойство глобального объекта — не всегда одно и то же.

#### Классический браузерный скрипт (classic script)

```html
<script>
  var legacyGlobal = 1;
  let lexicalGlobal = 2;

  console.log(globalThis.legacyGlobal); // 1
  console.log(globalThis.lexicalGlobal); // undefined в чистой среде
</script>
```

В classic script верхнеуровневый `var` обычно связан со свойством глобального объекта, а `let`/`const` — нет. При этом `lexicalGlobal` всё равно является глобальной привязкой для classic scripts той же изолированной среды; просто читать её через `globalThis.lexicalGlobal` нельзя.

<details>
<summary>🔬 Почему так: две части Global Environment Record</summary>

Классические скрипты одной изолированной среды JavaScript (**realm**) используют общую составную **Global Environment Record**:

- **Object Environment Record** связана с глобальным объектом. Через неё участвуют подходящие `var` и function declarations верхнего уровня, свойства среды и случайно созданные глобальные свойства;
- **Declarative Environment Record** хранит глобальные `let`, `const` и `class`.

Это модель спецификации, а не требование реализовать две части как два обычных JavaScript-объекта.

</details>

#### Браузерный ES module

```html
<script type="module">
  var moduleVar = 1;
  const moduleConst = 2;

  console.log(globalThis.moduleVar);   // обычно undefined
  console.log(globalThis.moduleConst); // обычно undefined
</script>
```

В ES module все объявления верхнего уровня, включая `var`, остаются внутри модуля. Модуль не публикует их на `globalThis`, а его код автоматически строгий.

Это не значит, что модуль вообще не видит глобальные API. Если имя не найдено внутри модуля, поиск может продолжиться во внешней глобальной среде — поэтому, например, браузерный модуль видит `document`.

<details>
<summary>🔬 Точная деталь: внешняя связь Module Environment Record</summary>

Внешней для **Module Environment Record** остаётся глобальная среда. Поэтому обычный поиск может найти уже существующую глобальную привязку или свойство, доступное через объектную часть глобальной среды. Но локальные объявления модуля ничего глобально не публикуют.

</details>

#### Node.js

- **Node.js ES module:** верхний уровень принадлежит модулю, код автоматически строгий.
- **Node.js CommonJS:** Node.js оборачивает файл в функцию, поэтому верхнеуровневый `var` локален для файла-модуля. Строгий режим для всего файла автоматически не включается.
- **REPL и DevTools:** интерактивные консоли могут сохранять имена по особым правилам и не всегда повторяют поведение обычного файла.

#### Сравнительная таблица

| Среда | `var` верхнего уровня | `let`/`const` верхнего уровня | Автоматический строгий режим |
|---|---|---|---|
| Классический браузерный скрипт | часто свойство глобального объекта | глобальная лексическая привязка, не свойство | нет |
| Браузерный ES-модуль | область модуля | область модуля | да |
| ES-модуль Node.js | область модуля | область модуля | да |
| Файл CommonJS в Node.js | локален для функции-обёртки | локален для функции-обёртки | не автоматически для всего файла |

Таблица предполагает чистую среду без одноимённых свойств, заранее созданных хостом.

#### Несколько классических скриптов на одной странице

Каждый classic script подготавливает свои объявления непосредственно перед собственным выполнением. Объявление из будущего скрипта не может «подняться назад» в уже выполняющийся скрипт. Реальный порядок запуска определяют HTML и атрибуты вроде `async`/`defer`. После выполнения первого скрипта его глобальная лексическая привязка может быть видна следующим classic scripts той же realm.

Если более поздний classic script пытается объявить несовместимое глобальное имя, подготовка его объявлений может завершиться `SyntaxError`. Ни одна его инструкция не выполнится.

<details>
<summary>🔬 Точная классификация межскриптового конфликта</summary>

Такой конфликт обнаруживается во время `GlobalDeclarationInstantiation`. По наблюдаемому поведению ошибка возникает до инструкций скрипта, но формально это не Early Error этапа `ParseScript`, потому что конфликт зависит от глобального состояния, созданного другим скриптом.

</details>

Поэтому в задаче о глобальных именах сначала уточняйте среду: классический браузерный скрипт, браузерный модуль, ES-модуль Node.js или CommonJS.

### 13. Что меняет строгий режим (strict mode) и что на самом деле удаляет `delete`?

**Строгий режим (strict mode)** отключает часть старого опасного поведения JavaScript и превращает некоторые скрытые ошибки в явные исключения. Его можно представить как защитный режим: сомнительная операция не «как-нибудь срабатывает», а сразу останавливается с понятной ошибкой.

Классический скрипт может включить его директивой в начале файла или функции:

```js
"use strict";
```

ES-модули работают в строгом режиме автоматически.

#### Что такое случайное глобальное свойство (accidental global)?

В нестрогом классическом скрипте присваивание в неразрешимое имя может создать свойство глобального объекта:

```js
function save(items) {
  total = items.length; // объявления нет
}

save(["a", "b"]);
console.log(globalThis.total); // 2 в нестрогом классическом скрипте
```

Из-за пропущенного `const`/`let` опечатка превращается в запись общего состояния. Это не обычная объявленная локальная переменная, а случайное свойство глобального объекта (**accidental global**), которое затем может участвовать в поиске имени.

В строгом коде:

```js
"use strict";

function save(items) {
  total = items.length; // ReferenceError
}

save(["a", "b"]); // ReferenceError
```

Исправление:

```js
function save(items) {
  const total = items.length;
  return total;
}
```

Если значение нужно снаружи, верните его из функции или передайте владельцу явно.

#### Что делает `delete`?

Оператор `delete` работает с **ячейкой-свойством объекта**, а не с объявленным именем. Это важное различие:

```js
const config = { debug: true };
delete config.debug;

console.log(config.debug); // undefined
```

Локальную привязку `let`, `const` или `var` таким способом удалить нельзя.

#### Почему глобальный `var` и случайное глобальное свойство удаляются по-разному?

Предположим чистую изолированную среду браузера без одноимённых существующих свойств и нестрогий классический скрипт:

```js
var declared = 1;
accidental = 2;

delete globalThis.declared;   // false
delete globalThis.accidental; // true
```

Свойство, связанное с верхнеуровневым `var`, обычно ненастраиваемое (**non-configurable**), поэтому удалить его нельзя. Случайное глобальное свойство обычно создаётся настраиваемым (**configurable**) и удаляется.

В строгом коде явное `delete globalThis.declared` пытается удалить то же неконфигурируемое свойство и бросает `TypeError`, а не возвращает `false`. Конфигурируемое свойство по-прежнему можно удалить через выражение доступа к свойству.

#### Что происходит с `delete identifier`?

```js
"use strict";
delete declaredName; // SyntaxError
```

В строгом исходном коде это ранняя синтаксическая ошибка. Пишите `delete object.property`, когда действительно нужно удалить свойство.

#### Современная рабочая рекомендация

- используйте ES modules там, где это уместно;
- включайте правила линтера вроде `no-undef` и `no-var`;
- не создавайте состояние через неявные глобальные имена;
- обозначайте владельца общего состояния явно;
- не используйте `delete` как мысленную модель для переменных.

### 14. Какие практические последствия особенно часто проверяют на интервью?

#### Почему обратные вызовы после `for (var ...)` видят одно значение?

```js
const readers = [];

for (var i = 0; i < 3; i += 1) {
  readers.push(() => i);
}

console.log(readers.map((read) => read())); // [3, 3, 3]
```

Цикл использует **одну общую** `var`-привязку `i`. Все три функции запоминают не три числа, а доступ к одной и той же привязке. После цикла в ней уже лежит `3`, поэтому каждая функция читает `3`.

Аналогия: все три человека получили ссылку на одну общую доску. Во время цикла число на доске менялось `0 → 1 → 2 → 3`. Когда людей спросили после цикла, каждый посмотрел на ту же доску и увидел `3`.

Это может быть привязка функциональной области внутри функции, глобальная привязка классического скрипта или локальная привязка модуля на его верхнем уровне.

#### Почему `for (let ...)` работает иначе?

```js
const readers = [];

for (let i = 0; i < 3; i += 1) {
  readers.push(() => i);
}

console.log(readers.map((read) => read())); // [0, 1, 2]
```

`for (let ...)` создаёт отдельную привязку для каждой итерации. Поэтому каждая функция сохраняет доступ к своей `i`: первая к `0`, вторая к `1`, третья к `2`.

В аналогии каждый человек получает свою карточку с числом, а не ссылку на общую доску.

Точная формулировка: замыкание сохраняет доступ к привязке. В `for (let ...)` сам цикл создаёт отдельные привязки итераций; это не замыкание волшебным образом копирует числа.

<details>
<summary>🧓 Какие legacy-исключения достаточно узнавать?</summary>

- `with` и прямой `eval` усложняют статическое рассуждение об областях; `with` запрещён в строгом режиме.
- Объявление функции внутри блока имеет стандартную блочную область в строгом коде и модулях, но нестрогие классические браузерные скрипты могут применять правила совместимости из Annex B.
- Статический блок класса создаёт отдельную область для `var`; это специфическое для классов исключение подробно рассматривается в разделе 1.4.

Для новой архитектуры эти механизмы не нужны. Здесь достаточно узнавать их как опасные особенности устаревшего кода и не переносить их правила на обычный код.

</details>

#### Современная рекомендация в одной таблице

| Ситуация | Рекомендация |
|---|---|
| Привязка не переназначается | `const` |
| Привязка намеренно меняется | `let` |
| Legacy-код использует `var` | проанализировать функциональную/глобальную область перед рефакторингом |
| Несколько компонентов делят состояние | явный контракт модуля или API |
| Нужно временное имя | минимально возможная блочная область |
| Затенение ухудшает читаемость | переименовать, даже если оно легально |

### 15. Как системно разбирать задачу на результат или ошибку области видимости?

Главная привычка: **не бегите по строкам сразу**. Сначала составьте карту областей и привязок. Иначе легко решить, что внешний `count` доступен, хотя поиск уже остановился на внутреннем `count` в TDZ.

Относитесь к задаче как к расследованию: сначала установить место действия и участников, затем восстановить порядок событий.

#### Шаг 1. Назовите среду запуска

- классический браузерный скрипт;
- браузерный ES module;
- Node.js ES module;
- Node.js CommonJS;
- функция внутри одной из этих сред.

Без этого нельзя надёжно определить поведение имён верхнего уровня.

#### Шаг 2. Определите разбираемую единицу и возможные статические конфликты

Сначала проверьте, допустим ли код вообще: нет ли повторных `let`/`const`, конфликта `var` с лексическим объявлением или одинаковых имён в общем `CaseBlock` у `switch`. При Early Error выполнять строки по очереди уже не нужно — выполнение не начнётся.

#### Шаг 3. Нарисуйте границы областей

Отметьте global/module scope, каждую функцию и каждый значимый блок. Сразу проведите `var` через обычные блоки до ближайшей функции или верхнего уровня; `let`/`const` оставьте в их лексической области.

#### Шаг 4. Выпишите привязки и их начальное состояние

Для каждой привязки укажите:

- область видимости;
- создана ли она заново или переиспользована;
- инициализирована ли она;
- начальное значение;
- возможность повторного присваивания.

#### Шаг 5. Для каждого чтения выполните поиск имени

Для каждого чтения идите от текущей области наружу и остановитесь на первом совпадении. Если найденная привязка в TDZ, результат — `ReferenceError`; переходить к внешнему одноимённому binding нельзя.

#### Шаг 6. Только теперь выполняйте инструкции по порядку

Теперь двигайтесь по строкам, учитывая вызовы, `return`, initialization и assignment.

#### Шаг 7. Классифицируйте результат

- конкретное значение;
- `undefined`;
- `ReferenceError`;
- `TypeError`;
- `SyntaxError` до выполнения инструкций.

#### Сквозной пример

```js
const status = "global";

function inspect(enabled) {
  var count = 1;

  if (enabled) {
    const status = "block";
    console.log(status); // "block"
    console.log(count);  // ReferenceError
    let count = 2;
  }
}

inspect(true);
```

Разбор:

1. Код допустим: внутренний `let count` находится в отдельном блоке и может затенить функциональный `var count`.
2. Вызов `inspect(true)` создаёт контекст выполнения функции.
3. Функциональный `count` после `var count = 1` содержит `1`.
4. При входе в `if` уже существует блочная `count`, но она в TDZ до строки `let count = 2`.
5. Блочная `status` уже инициализирована, поэтому первый `console.log` выводит `"block"`.
6. Во втором `console.log` поиск сразу находит блочную `count`. Он не идёт к внешней `var count`.
7. Найденная `count` ещё в TDZ, поэтому возникает `ReferenceError`.
8. После исключения строка `let count = 2` не выполняется.

Этот алгоритм надёжнее, чем попытка вспомнить лозунги вроде «`let` не поднимается».

## Краткий справочник терминов

| Термин | Короткое определение |
|---|---|
| Идентификатор (identifier) | Имя в исходном коде, которое JavaScript должен разрешить. |
| Привязка (binding) | Связь имени с состоянием и текущим значением. |
| Объявление (declaration) | Синтаксис, вводящий имя в область видимости. |
| Инициализация (initialization) | Первый перевод привязки в инициализированное состояние с некоторым значением. |
| Присваивание (assignment) | Позднейшая запись нового значения в изменяемую привязку. |
| Область видимости (scope) | Область исходного кода, где идентификатор относится к конкретной привязке. |
| Лексическая область (lexical scope) | Правило, по которому вложенность областей определяется структурой исходного кода. |
| Цепочка областей (scope chain) | Неформальное название поиска привязки от текущей области наружу. |
| Контекст выполнения (execution context) | Состояние, необходимое для выполнения скрипта, модуля, функции или `eval`-кода. |
| Стек вызовов (call stack) | Порядок активных контекстов и вызовов функций. |
| Запись окружения (Environment Record) | Модель спецификации для хранения и разрешения привязок. |
| Подъём объявлений (hoisting) | Неформальное описание эффекта предварительной обработки объявлений. |
| Временная мёртвая зона (TDZ) | Период, когда лексическая привязка уже существует, но ещё не инициализирована. |
| Затенение (shadowing) | Внутренняя привязка с тем же именем скрывает внешнюю. |
| Повторное объявление (redeclaration) | Повторное объявление имени в той же эффективной области. |
| Ранняя статическая ошибка (Early Error) | Статическая ошибка единицы кода, обнаруженная до её выполнения. |

## Типичные ошибки

1. **«Движок переносит объявления вверх».** Точнее: привязки подготавливаются до выполнения инструкций.
2. **«`let` и `const` не поднимаются».** Их привязки существуют, но находятся в TDZ.
3. **«Область видимости и контекст выполнения — одно и то же».** Блок может создать область без вызова функции.
4. **«TDZ — это строки над `let`».** TDZ длится от входа в область до инициализации.
5. **«`const` делает объект неизменяемым».** `const` запрещает повторное присваивание, а не изменение объекта.
6. **«Любая глобальная переменная — это `window.name`».** Глобальные лексические и модульные привязки могут не быть свойствами объекта.
7. **«Консоль DevTools точно моделирует обычный скрипт».** У консоли есть особое поведение, заданное средой выполнения.
8. **«Любое одинаковое имя — затенение».** В одной области это может быть конфликт повторного объявления.
9. **«`delete` удаляет переменные».** `delete` работает со свойствами объектов.
10. **«Замыкание сохраняет копию значения».** Замыкание сохраняет доступ к привязке.

## Ловушки на интервью

### `typeof` не является универсальной проверкой безопасности

```js
typeof absent; // "undefined"
typeof later;  // ReferenceError
let later;
```

Сначала определите: идентификатор отсутствует полностью или лексическая привязка существует в TDZ?

### Внутреннее объявление скрывает внешнюю привязку до своей строки

Контрольный вопрос: какую привязку найдёт поиск имени до `let count` — внешнюю или уже существующую внутреннюю в TDZ?

### Функциональное выражение наследует жизненный цикл содержащей его привязки

- `var fn = ...`: ранний вызов находит `undefined` и даёт `TypeError`;
- `const fn = ...`: раннее чтение попадает в TDZ и даёт `ReferenceError`;
- `function fn() {}`: привязка обычно уже содержит функцию.

### Ответ про глобальные имена без названия среды неполон

Всегда уточняйте: классический браузерный скрипт, браузерный модуль, ES-модуль Node.js или CommonJS.

### При Early Error предыдущий `console.log` не спасает

## Как объяснить тему на интервью за 30–60 секунд

### `var`, `let` и `const`

> Я сравниваю их по scope и жизненному циклу. `var` ограничен ближайшей функцией, но не обычным блоком, и заранее получает `undefined`. `let` и `const` обычно ограничены блоком и до инициализации находятся в TDZ. `let` можно переназначить, `const` — нельзя, хотя сам объект внутри `const` всё ещё может меняться. В новом коде я начинаю с `const`, беру `let`, когда нужно переназначение, а `var` в основном встречаю в legacy-коде.

### Hoisting и TDZ

> Hoisting не означает, что движок переносит строки вверх. До выполнения инструкций JavaScript уже подготавливает объявления. Новый `var` в этот момент содержит `undefined`; `let` и `const` уже существуют, но находятся в TDZ; function declaration обычно уже содержит функцию. Поэтому я спрашиваю не «поднялось ли имя», а «в каком состоянии его binding сейчас».

### Область видимости, контекст выполнения и поиск имени

> Scope отвечает, где конкретное имя видно, и определяется структурой исходного кода. При чтении имени JavaScript ищет binding сначала в текущей области, затем идёт наружу. Вызов функции создаёт execution context и кадр в call stack. Обычный блок может создать новую область для `let` и `const`, но функции он не вызывает, поэтому нового кадра стека нет.

### Глобальные имена браузера и модули

> Сначала я уточняю среду запуска. В classic browser script верхнеуровневый `var` обычно связан со свойством `globalThis`, а `let` и `const` — нет. В ES module все эти объявления остаются внутри модуля, а код автоматически строгий. В Node.js CommonJS файл обёрнут функцией, поэтому его верхний уровень тоже не равен браузерному глобальному уровню.
