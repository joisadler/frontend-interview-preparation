Обещание помогает получить один будущий результат, но само по себе не решает, кто запустил работу, кто обязан заметить ошибку и кому ещё разрешено применить результат. Эта глава связывает четыре вопроса: **исход → зависимость → обработка отказа → актуальность результата**.

## Как читать эту главу

**🎯 Interview core:** вопросы 1–5, 7–25, 27–28. **🔬 Optional precision:** вопросы 6 и 26. Точные детали усвоения чужого `then` и объединения сигналов полезны вторым проходом, после основной модели.

```text
операция → Promise её результата → новая цепочка из return / throw
  → await или комбинатор → решение об ошибке → проверка актуальности → применение
```

Каждый блок независим. Переносимый код запускайте отдельным `.mjs` в Node.js; в браузере — отдельным модулем или внутри асинхронной функции. Если есть верхнеуровневый `await`, обычный классический скрипт не подходит. Функции с параметрами вызываются с указанными входами. Блок с необработанным отказом явно помечен и запускается отдельно: ошибка в нём намеренная. Остальные отказы наблюдаются через `catch`, `await` или комбинатор.

Цикл событий уже разобран в [1.9](09-event-loop-and-scheduling.md). Здесь не воспроизводим его целиком: главное — зависимости и исходы. После главы используйте отдельные [вопросы](../../question-bank/by-domain/01-javascript-and-async-programming.md#110-promises--asyncawait) и [условия упражнений](../../exercises/prompts/by-domain/01-javascript-and-async-programming.md#110-promises--asyncawait), не открывая решения до попытки.

## Ментальная модель

Обещание (**Promise**) похоже на квитанцию на один результат. Квитанция может ещё ждать, подтвердить получение или сообщить отказ. Копия ссылки на квитанцию не запускает доставку повторно; новая цепочка обработки создаёт свою квитанцию следующего результата.

Полезно разделить три слоя:

- **Операция:** сеть, таймер, чтение или уже начатое вычисление.
- **Обещание:** объект, через который наблюдаем один исход.
- **Владелец:** код, решающий, когда остановить работу и применим ли результат сейчас.

Аналогия не делает Promise отменяемым поручением. Даже если перестать смотреть на квитанцию, доставка может продолжаться. И даже успешная доставка может уже не относиться к текущему запросу пользователя.

## Связное объяснение в формате вопросов и ответов

### 🎯 1. Promise — это операция или её результат?

Promise представляет возможный будущий результат, а не обязательную инструкцию «начать работу потом». Например, вызов `fetch()` обычно начинает работу при вызове; передача возвращённого обещания в `Promise.all()` не является её первым запуском.

Одно обещание можно наблюдать несколько раз. Это не повторяет исходную операцию и не потребляет значение как одноразовый итератор.

```js
const ready = Promise.resolve(4);
const first = ready.then(value => value + 1);
const second = ready.then(value => value * 2);
console.log(await first, await second); // 5, 8
```

`first` и `second` — независимые ветви от общего результата. Именно ветвление позже объяснит, почему обработка ошибки одной ветви не обязательно защищает другую.

### 🎯 2. Какие у Promise состояния и чем resolved отличается от fulfilled?

Состояний три: **ожидает (pending)**, **успешно выполнено (fulfilled)**, **отклонено (rejected)**. Последние два называют **завершёнными (settled)**. После окончательного исхода он не меняется.

Слово **resolved** точнее понимать как «решение уже зафиксировано»: обещание либо завершено, либо связано с исходом другого обещания. Оно ещё может ждать этот исход.

```js
let release;
const inner = new Promise(resolve => { release = resolve; });
const outer = new Promise((resolve, reject) => {
  resolve(inner);
  reject(new Error("too late"));
});
release(7);
console.log(await outer); // 7
```

После `resolve(inner)` решение `outer` уже связано с `inner`, но до `release` результат ещё ожидается. Последующий `reject` не заменяет принятое решение. Поэтому `resolve` не всегда означает «сейчас успешно завершилось».

### 🎯 3. Что выполняется внутри конструктора и что делает первый resolve?

Исполнитель конструктора (**executor**) вызывается синхронно. Вызовы `resolve` и `reject` определяют исход, но не прекращают обычное выполнение тела.

```js
const log = [];
const promise = new Promise((resolve, reject) => {
  log.push("executor");
  resolve(1);
  log.push("after resolve");
  reject(new Error("ignored"));
});
log.push("outside");
log.push(await promise);
console.log(log); // ["executor", "after resolve", "outside", 1]
```

Синхронное исключение из исполнителя отклоняет ещё не решённое обещание; после принятого решения уже не заменяет его. Значение `return` исполнителя не является результатом обещания.

Не оборачивайте уже обещающий API в лишний `new Promise`. Особенно опасен `async`-исполнитель: его возвращённое обещание конструктор не присоединяет; ошибка после `await` может стать отдельным отказом, пока внешнее обещание ждёт.

### 🎯 4. Что создаёт then и как return управляет новой цепочкой?

`.then(onFulfilled, onRejected)` сразу возвращает **новое обещание**. Когда выбранный обработчик позже выполнится, его исход определит это новое обещание.

| Исход обработчика | Что получает следующая часть |
|---|---|
| `return value` | Успех с этим значением |
| Нет `return` | Успех с `undefined` |
| `throw error` | Отказ с выброшенным значением |
| Возвращено обещание или объект с вызываемым `then` | Ожидание его результата |
| Подходящий обработчик отсутствует | Исход проходит дальше |

```js
const base = Promise.resolve(2);
const next = base.then(value => value + 3);
console.log(base === next, await next); // false, 5
```

Это не изменение `base` на месте. Даже если исходное обещание уже завершено, обработчик не вызывается прямо внутри `.then()`.

### 🎯 5. Почему результат возвращённого обещания не остаётся вложенным?

Цепочка присоединяет итог возвращённого обещания. Это часто называют **разворачиванием результата (flattening)**: потребитель ждёт окончательное значение, а не получает обязательную ступень `Promise<Promise<T>>`.

```js
const result = Promise.resolve(2)
  .then(value => Promise.resolve(value * 3))
  .then(value => value + 1);
console.log(await result); // 7
```

`Promise.resolve(value)` также принимает обычное значение, обещание или совместимый объект с `then`. Для обычного собственного Promise с тем же конструктором он может вернуть сам объект; обёртка через `async` при этом возвращает другое обещание.

Переход к результату не означает глубокое разворачивание содержимого объектов и массивов. `Promise.resolve([promise])` даёт массив, внутри которого по-прежнему лежит обещание; для массива результатов нужен комбинатор.

### 🔬 6. Что такое thenable и где граница синхронности?

**Thenable** — объект с вызываемым свойством `then`, с которым Promise умеет согласовать результат. Получение свойства может выполнить синхронный getter. Вызов найденного метода для усвоения результата планируется отдельным заданием языка.

```js
const log = [];
const foreign = {
  get then() {
    log.push("get then");
    return resolve => { log.push("call then"); resolve(9); };
  },
};
const result = Promise.resolve(foreign);
log.push("after resolve");
console.log(await result, log); // 9, ["get then", "after resolve", "call then"]
```

Механизм называется **усвоением thenable (thenable assimilation)**. Исключение getter даёт отказ; невызываемое `then` оставляет обычное значение. Повторные вызовы `resolve`/`reject` не меняют уже принятое решение. Возвращение из обработчика того же нового обещания, которое этот обработчик определяет, приводит к `TypeError`.

Точные внутренние имена алгоритмов знать необязательно. Важнее не считать чтение чужого свойства безусловно чистой операцией и не реализовывать усвоение одной проверкой `instanceof Promise`.

### 🎯 7. Что ломается, когда забыли вернуть обещание?

Следующая часть цепочки больше не ждёт начатую работу. Результат обработчика без `return` — `undefined`, а внутренний отказ может уйти в отдельную ненаблюдаемую ветвь.

```js
async function readAfter(load) {
  return Promise.resolve()
    .then(() => load())
    .then(value => ({ value }));
}
```

Здесь `load()` возвращён и его исход присоединён. Замена тела на `{ load(); }` теряет связь. Аналогично `void operation()` только отбрасывает значение выражения; обработчик отказа от этого не появляется.

Если работа должна жить отдельно, у неё всё равно должен быть владелец завершения и ошибки. Название «запустили в фоне» не является обработкой отказа.

### 🎯 8. Как ошибка распространяется и когда catch восстанавливает успех?

Отказ проходит через звенья без подходящего обработчика. `.catch(fn)` соответствует обработчику отказа через `.then(undefined, fn)`. Если обработчик нормально возвращает значение, следующая часть получает успех; если выбрасывает — отказ продолжается.

```js
const value = await Promise.reject(new Error("missing"))
  .catch(() => 10)
  .then(number => number + 1);
console.log(value); // 11
```

Такой запасной результат оправдан только договором. Молчаливый `catch(() => undefined)` способен превратить реальную ошибку в успешное отсутствие данных.

Если нужно добавить контекст, сохраняйте исходную причину в `cause`, как в 1.7. Не перехватывайте ошибку в каждом слое только ради вывода одного и того же сообщения.

### 🎯 9. Почему второй аргумент then не ловит ошибку первого?

Эти два обработчика — альтернативы исхода **предыдущего** обещания. Исключение из `onFulfilled` становится отказом нового обещания; соседний `onRejected` его не обрабатывает.

```js
const log = [];
await Promise.resolve(1)
  .then(() => { throw new Error("from success"); }, () => log.push("sibling"))
  .catch(error => log.push(error.message));
console.log(log); // ["from success"]
```

Именно поэтому расположение `catch` определяет границу обработки. Если ошибка возникла и в самом `catch`, нужен наблюдатель следующего обещания, а не предположение, что слово `catch` однажды защитило весь граф навсегда.

### 🎯 10. Что сохраняет finally и когда оно меняет исход?

`.finally(fn)` вызывается без результата/причины и обычно сохраняет исходную успешность или ошибку. Обычное возвращённое значение не подменяет исход. Но исключение или возвращённое отклонённое обещание заменяют его; обещание очистки нужно дождаться.

```js
console.log(await Promise.resolve(5).finally(() => 99)); // 5
try {
  await Promise.resolve(5).finally(() => Promise.reject(new Error("cleanup")));
} catch (error) {
  console.log(error.message); // "cleanup"
}
```

Возвращайте очистку из `finally`, если цепочка обязана её дождаться. Вызов очистки без `return` создаёт отдельную ветвь. Это отличается от `return` в обычном блоке `try/finally`, где возврат сам может заменить исход; механика исключений разобрана в 1.7.

### 🎯 11. Почему необработанный отказ относится к конкретному обещанию?

У каждой ветви свой исход. Наблюдение исходного обещания не обязательно наблюдает новое обещание от `.then()` или `.finally()`. Это **необработанный отказ (unhandled rejection)**, когда среда не видит своевременно присоединённого обработчика у отклонённой ветви.

Намеренно ошибочный самостоятельный блок. Запускать отдельно; в Node.js 22.13.1 без специальных обработчиков/флагов процесс завершается с ошибкой. В браузере наблюдается событие `unhandledrejection`.

```js
Promise.resolve().then(() => { throw new Error("DETACHED_BRANCH"); });
```

Браузер и Node.js имеют разные механизмы сообщения о таких ошибках. Глобальное наблюдение полезно для диагностики, но не заменяет прикладную обработку. Своевременный обработчик, присоединённый в той же контрольной точке, отличается от позднего `catch` после уведомления среды.

Не полагайтесь на один запуск из консоли: инструменты могут менять наблюдение. В этом комплекте ошибочный Node-пример проверяется отдельным процессом, браузерный — через настоящее событие среды.

### 🎯 12. Что возвращает async-функция и что выполняется до первого await?

Вызов `async`-функции возвращает обещание. Её тело начинается синхронно и работает до приостановки; обычный `return` становится успехом, исключение — отказом возвращённого обещания.

```js
const original = Promise.resolve(3);
async function read() { return original; }
console.log(read() === original); // false
console.log(await read()); // 3
```

Обещание `read()` принимает тот же результат, но не обязано сохранять идентичность объекта `original`. `async` не переносит тяжёлое синхронное вычисление на другой поток.

### 🎯 13. Что именно приостанавливает await?

`await` приостанавливает дальнейшее выполнение текущей асинхронной функции до результата. Успешное значение становится значением выражения; отказ превращается в выброс в этой функции. Остальная среда не блокируется ожиданием, но синхронная работа до/после него по-прежнему занимает поток.

```js
const log = [];
async function run() {
  log.push("before");
  const value = await 4;
  log.push(value);
}
const done = run();
log.push("outside");
await done;
console.log(log); // ["before", "outside", 4]
```

Даже обычное значение проходит отложенное продолжение. Это не обещание выделить время кадру: цепочка продолжений на готовых результатах может оставаться в микрозадачах, как показано в 1.9.

### 🎯 14. Всегда ли return await лишний?

Нет. Важны границы локального `try/catch/finally`. Возвращённое без ожидания обещание будет принято вызывающим кодом, но локальный `catch` уже не окружает его будущий отказ.

```js
async function withoutAwait() {
  try { return Promise.reject(new Error("later")); }
  catch { return "recovered"; }
}
async function withAwait() {
  try { return await Promise.reject(new Error("later")); }
  catch { return "recovered"; }
}
console.log(await withoutAwait().catch(error => error.message)); // "later"
console.log(await withAwait()); // "recovered"
```

Аналогично локальное освобождение ресурса в `finally` может быть слишком ранним, если операция просто возвращена. Решайте по требуемому времени жизни и перехвату, а не по лозунгу «всегда удалить await». Точные дополнительные микрошаги и стоимость зависят от реализации, поэтому оптимизацию нельзя выводить из числа ключевых слов.

### 🎯 15. Почему forEach с async не ждёт все результаты?

`forEach` не собирает возвращённые обещания. `map` собирает массив возвращённых значений, но если функция `async`, это массив обещаний, а не готовых данных. `await` обычного массива не ждёт его элементы.

```js
const pending = [1, 2].map(async value => value * 2);
console.log((await pending) === pending); // true
console.log(await Promise.all(pending)); // [2, 4]
```

Для последовательной зависимости подходит цикл с `await`; для независимых операций — запустить и сразу присоединить наблюдение через комбинатор. Предикат `async` в `filter` тоже не превращает его в асинхронный фильтр: обычные методы не знают такого договора.

### 🎯 16. Когда последовательное ожидание правильно?

Когда следующая операция требует результат предыдущей или договор специально требует порядок. Например, сначала получаем пользователя, затем его документы по выданному идентификатору.

```js
async function loadDocuments(api) {
  const user = await api.getUser();
  const documents = await api.getDocuments(user.id);
  return { user, documents };
}
```

`api` предоставляет указанные обещающие методы. Здесь вторую операцию нельзя просто начать заранее без её входных данных. Последовательность сама по себе не ошибка; ошибка — не заметить отсутствующую зависимость и ждать независимую работу зря.

### 🎯 17. Как убрать случайный каскад ожиданий?

**Каскад ожиданий (async waterfall)** появляется, когда независимая операция начинается лишь после чужого результата без необходимости. Запускайте независимые операции до общего ожидания и сразу наблюдайте их исходы.

```js
async function loadDashboard(api) {
  const [profile, settings] = await Promise.all([
    api.getProfile(),
    api.getSettings(),
  ]);
  return { profile, settings };
}
```

Обе функции вызываются при построении массива; комбинатор не запускает их с нуля. Это перекрытие ожидания, не параллельное выполнение тяжёлого JavaScript в одном потоке.

Опасен компромисс: запустить `second`, долго ждать `first`, и только потом присоединить обработчик `second`. Быстрый отказ второй операции может оказаться временно необработанным. Если результаты нужны вместе, соедините их сразу. Ограничение числа одновременных запросов — отдельный договор 1.11.

### 🎯 18. Что гарантирует Promise.all и чего он не отменяет?

`Promise.all(iterable)` ждёт все успешные результаты и сохраняет **порядок входа**, а не завершения. При первом наблюдаемом отказе его результат отклоняется, не ожидая остальных успехов. Это ранний отказ (**fail-fast**).

```js
const values = await Promise.all([Promise.resolve("A"), 2]);
console.log(values); // ["A", 2]
```

`all` не останавливает проигравшие операции. Их эффекты могут продолжиться после отказа агрегата. Общая отмена требует сигналов, владельца и подходящей политики завершения.

Обычные функции во входном массиве не вызываются: они являются значениями. Синхронное исключение при построении массива или вызове фабрики также происходит до передачи готового набора комбинатору. Для смешанных синхронных/асинхронных фабрик можно сознательно нормализовать вызов через `Promise.resolve().then(factory)`, учитывая перенос его старта в микрозадачу.

### 🎯 19. Когда нужен allSettled?

Когда частичный успех полезен и нужен отчёт по каждой операции. `Promise.allSettled` ждёт завершения всех входов и возвращает записи `{ status: "fulfilled", value }` или `{ status: "rejected", reason }` в порядке входа.

```js
const report = await Promise.allSettled([
  Promise.resolve("saved"),
  Promise.reject(new Error("offline")),
]);
console.log(report.map(item => item.status)); // ["fulfilled", "rejected"]
```

При обычном корректном наборе отказ отдельного входа становится записью отчёта. Это не гарантия «никогда не отклоняется»: некорректный iterable или ошибка его обхода — отдельная ошибка самого вызова/агрегации. Отчёт ещё нужно прочитать и принять прикладное решение, а не считать наличие массива общим успехом.

### 🎯 20. Когда race полезен и почему тайм-аут не равен отмене?

`Promise.race` принимает первый окончательный исход: успех или отказ. Даже готовый обычный вход не вызывает обработчик синхронно внутри регистрации.

```js
console.log(await Promise.race([Promise.resolve("cached"), new Promise(() => {})])); // "cached"
```

Если состязать запрос и таймер отказа, выбор таймера завершит только агрегат. Запрос не отменится сам; таймер тоже нужно убрать, если первым завершился запрос. Сигнал отмены и срок ожидания — связанные, но разные обязанности.

`race` также не отписывает автоматически свои реакции от незавершённых обещаний. Поэтому бесконечно состязать один вечный Promise с короткими таймерами — плохая универсальная схема ожидания.

### 🎯 21. Чем any отличается от race?

`Promise.any` ищет **первый успех**. Отдельные отказы не мешают ждать другие варианты. Если все отклонены, результат — отказ `AggregateError`; массив `errors` соответствует порядку входа, а не времени ошибок.

```js
console.log(await Promise.any([
  Promise.reject(new Error("first failed")),
  Promise.resolve("available"),
])); // "available"
try {
  await Promise.any([Promise.reject("A"), Promise.reject("B")]);
} catch (error) {
  console.log(error instanceof AggregateError, error.errors); // true, ["A", "B"]
}
```

Это удобно для взаимозаменяемых источников, если допускаются их одновременные эффекты. Первый успех не отменяет остальные источники. Выбор нескольких платных или изменяющих состояние операций требует отдельного решения о допустимости такого состязания.

### 🎯 22. Как ведут себя комбинаторы на пустом наборе?

| Выражение | Состояние результата для обычного Promise |
|---|---|
| `Promise.all([])` | Успех с `[]` |
| `Promise.allSettled([])` | Успех с `[]` |
| `Promise.any([])` | Отказ `AggregateError` с пустым `errors` |
| `Promise.race([])` | Продолжает ждать; входов для завершения нет |

Даже если пустой `all` уже успешен, его `.then()` выполняется позже. Не путайте состояние обещания и синхронный вызов обработчика.

```js
console.log(await Promise.all([]), await Promise.allSettled([])); // [], []
try { await Promise.any([]); }
catch (error) { console.log(error.errors); } // []
```

Не ставьте `await Promise.race([])` в последовательный учебный запуск: продолжения не будет. Короткое наблюдение «пока не завершился» не доказывает вечность ожидания; отсутствие исхода следует из договора пустого состязания.

### 🎯 23. Что отменяет AbortController?

`AbortController` передаёт **сигнал отмены (AbortSignal)** поддерживающим его операциям. Promise не получает нового состояния «отменено»: конкретный API обычно завершает его отказом. Код без поддержки сигнала продолжит работу.

```js
const controller = new AbortController();
const reason = new Error("Closed by owner");
controller.abort(reason);
console.log(controller.signal.aborted, controller.signal.reason === reason); // true, true
try { controller.signal.throwIfAborted(); }
catch (error) { console.log(error === reason); } // true
```

Контроллер одноразовый. Повторный `abort` не создаёт новый цикл и не заменяет первую причину. Без явной причины используется `DOMException` с именем `AbortError`; явная причина может быть любым значением, включая `null`. Проверка только `error.name === "AbortError"` не описывает все варианты отмены.

Отмена — кооперативный договор. Она не прерывает занятый синхронный JavaScript посреди инструкции и не откатывает уже выполненную запись на сервере.

### 🎯 24. Как написать обещающий таймер с отменой?

Нужно учесть уже отменённый сигнал, убрать таймер при отмене и снять обработчик при обычном завершении. Причину отказа сохраняем как есть.

```js
function abortableDelay(ms, { signal } = {}) {
  return new Promise((resolve, reject) => {
    if (!Number.isFinite(ms) || ms < 0) {
      reject(new RangeError("Nonnegative finite delay required"));
      return;
    }
    if (signal?.aborted) { reject(signal.reason); return; }
    let timer = null;
    function onAbort() {
      if (timer !== null) clearTimeout(timer);
      timer = null;
      signal.removeEventListener("abort", onAbort);
      reject(signal.reason);
    }
    timer = setTimeout(() => {
      timer = null;
      signal?.removeEventListener("abort", onAbort);
      resolve();
    }, ms);
    signal?.addEventListener("abort", onAbort, { once: true });
  });
}
```

`signal`, если передан, должен быть настоящим AbortSignal. Первый исход победит и при тесном соседстве событий; тесту не нужно угадывать точную миллисекунду. Этот код задаёт отменяемый таймер, а не механизм повторных попыток или ограничитель параллелизма.

### 🎯 25. Чем отказ fetch отличается от HTTP-ошибки и чтения тела?

Браузерный `fetch` обычно успешно выдаёт `Response` и для статуса `404` или `503`. Прикладной код сам проверяет `ok`/`status`. Чтение и разбор тела — следующая асинхронная операция, которая тоже может завершиться ошибкой.

Браузер; `url` указывает на JSON-ресурс:

```js
async function getJson(url, { signal } = {}) {
  const response = await fetch(url, { signal });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const value = await response.json();
  signal?.throwIfAborted();
  return value;
}
```

Один сигнал передаётся вниз. Если отмена пришла после получения заголовков, чтение ещё не завершённого тела также может отказать. Последняя проверка полезна как граница применения результата; это всё ещё не проверка его актуальности относительно другого запроса.

В реальном API после разбора проверьте схему данных, как в 1.7. Не превращайте любой отказ в пустой объект. Не представляйте отмену запроса как гарантию, что сервер не выполнил действие.

### 🔬 26. Как совместить срок ожидания и отмену владельца?

В поддерживающей среде `AbortSignal.any` объединяет сигналы, а `AbortSignal.timeout` создаёт сигнал срока ожидания. Первый источник отмены определяет причину объединённого сигнала.

```js
const owner = new AbortController();
const combined = AbortSignal.any([owner.signal, AbortSignal.timeout(1000)]);
owner.abort(new Error("Owner closed"));
console.log(combined.aborted, combined.reason === owner.signal.reason); // true, true
```

Эти API проверены в указанных локальных средах; совместимость старой целевой среды проверяйте отдельно. В браузере срок `AbortSignal.timeout` связан с активным временем и может приостанавливаться вместе с документом/рабочим потоком в предусмотренных состояниях. Это не универсальный календарный дедлайн, продолжающийся независимо от жизни страницы.

Отмена владельца не означает ручную отмену самого внутреннего таймера `AbortSignal.timeout`: отдельного метода остановки у этого сигнала нет. Управление временем и распространение отмены для более сложных сценариев остаются в 1.11.

### 🎯 27. Почему поздний ответ может испортить интерфейс без параллельных потоков?

Пользователь начал запрос A, затем B; B завершился раньше. Если после этого применить A, экран покажет старое намерение. Это **логическая гонка (race condition)**: проблема порядка событий, а не обязательного одновременного исполнения инструкций.

Правило **«последний запрос побеждает» (latest-request-wins)** требует проверки версии перед применением и обработкой ошибки. Отмена предыдущей операции экономит ресурсы, но источник может её проигнорировать.

Переносимая логика поверх поддерживаемых AbortController. `load(key, { signal })` возвращает данные или обещание; `apply` и `reportError` — короткие синхронные функции без исключений.

```js
function createLatestLoader(load, apply, reportError) {
  let version = 0;
  let current = null;
  let disposed = false;
  async function run(key) {
    if (disposed) return;
    const ownVersion = ++version;
    const previous = current;
    const controller = new AbortController();
    current = controller;
    previous?.abort();
    if (disposed || ownVersion !== version) return;
    try {
      const value = await load(key, { signal: controller.signal });
      if (!disposed && ownVersion === version && !controller.signal.aborted) {
        apply(value);
      }
    } catch (error) {
      if (!disposed && ownVersion === version && !controller.signal.aborted) {
        reportError(error);
      }
    } finally {
      if (ownVersion === version) current = null;
    }
  }
  function dispose() {
    if (disposed) return;
    disposed = true;
    version += 1;
    const previous = current;
    current = null;
    previous?.abort();
    load = null; apply = null; reportError = null;
  }
  return { run, dispose };
}
```

Проверяем и успех, и отказ. Старый `finally` не стирает контроллер нового запроса. После завершения владельца нельзя применять даже самый свежий результат. Повторный `dispose` безопасен; новый `run` после него ничего не запускает.

Здесь нет политики кеша, повторов или ограничения параллелизма. В задаче с отправкой платежей простое игнорирование ответа не решает бизнес-гонку; для изменяющих состояние запросов нужны соответствующие серверные договоры.

### 🎯 28. Как проверять весь договор без ненадёжных задержек?

Управляйте завершением операций явно: создайте обещания, чьи `resolve` и `reject` доступны тесту. Запускайте A и B, завершайте B раньше A и проверяйте, что применяется только B. Повторите со старой ошибкой, текущей ошибкой и закрытием до ответа.

Для комбинаторов фиксируйте не только значения, но и момент допустимого результата: `all`/`race` могут завершиться раньше проигравших, `allSettled` ждёт всех, `any` пропускает отдельные отказы. Пустой `race` не нужно бесконечно ожидать в тесте.

Чистые управляемые источники проверяют порядок и владение. Настоящий браузерный Fetch отдельно проверяет HTTP-статус, ошибку JSON, отмену до ответа и во время чтения тела. Наблюдение `unhandledrejection` тоже должно исходить от среды, а не от ручного `dispatchEvent` с таким именем.

В [комплексной задаче](../../exercises/prompts/by-domain/01-javascript-and-async-programming.md#js-promise-ex12) эти слои соединяются без отдельного приложения: общий результат данных, частичный отказ необязательной части, отмена и проверка актуальности.

| Можно ли применить результат? | Проверить сигнал, версию запроса и жизнь владельца |

## Типичные ошибки

- Приравнивать `resolved` к `fulfilled`, а Promise — к ленивой функции запуска.
- Забывать `return` или использовать `async`-исполнитель конструктора.
- Считать `catch` универсальной защитой всех ветвей и проглатывать отказ без решения.
- Не возвращать очистку из `.finally()` или путать её с обычным блоком `finally`.
- Делать `await` массива обещаний или `forEach(async ...)` вместо общего ожидания.
- Создавать случайный каскад независимых запросов или поздно наблюдать уже запущенную ветвь.
- Считать тайм-аут состязания отменой запроса и успешный Fetch доказательством статуса 200.
- Применять старый результат/ошибку или сбрасывать новый индикатор загрузки из старого `finally`.

## Ловушки на интервью

- `resolve(otherPromise)` может зафиксировать решение, пока результат ещё ожидается.
- `.then` всегда создаёт новое обещание; `async`-обёртка не обязана сохранить идентичность исходного.
- Отсутствующий обработчик и обработчик, возвращающий `undefined`, имеют разные последствия для отказа.
- Значения и функции во входах комбинатора не означают автоматический вызов фабрик.
- `AggregateError.errors` и отчёт `allSettled` следуют порядку входа.
- `race([])` не завершается, хотя `all([])` уже успешен; их реакции всё равно не выполняются синхронно.
- Сигнал одноразовый, причина отмены может не иметь поля `name`, а проигравший запрос способен продолжаться.

Для независимых запросов сначала проверьте допустимость одновременного запуска и побочных эффектов. Комбинатор не является ограничителем запросов. ## Как объяснить тему на интервью за 30–60 секунд

### Исход и цепочка

> Promise представляет один исход операции: ожидающий, успешный или отклонённый. Resolve может связать его с другим обещанием, поэтому не всегда означает готовый успех. Каждый then создаёт новое обещание; return передаёт значение или ожидание дальше, throw создаёт отказ. Если забыть вернуть начатую работу, цепочка перестанет её ждать.

### Ошибки

> Ошибка принадлежит конкретной ветви. Catch может восстановить успешный результат или передать отказ дальше; соседний обработчик then не ловит исключение первого. Finally обычно сохраняет исход, но ждёт возвращённую очистку и принимает её отказ. Я наблюдаю все запущенные ветви сразу и не считаю глобальное сообщение об ошибке прикладной обработкой.

### Совместное ожидание

> Последовательно жду настоящие зависимости. Независимые операции запускаю до общего ожидания, чтобы не получить лишний каскад. All нужен для всех успехов, allSettled — для полного отчёта, race — для первого исхода, any — для первого успеха. Раннее завершение агрегата не отменяет остальные операции; это обязанность владельца.

### Отмена и актуальность

> AbortController передаёт поддерживаемую отмену, но не меняет Promise в особое состояние и не откатывает серверные эффекты. Даже отменяемый запрос может дать поздний результат, поэтому перед применением проверяю версию и жизнь владельца. Ошибки старого запроса тоже не должны менять новый экран. Проверяю обратный порядок ответов управляемыми обещаниями, а Fetch — отдельно в браузере.

## Источники
