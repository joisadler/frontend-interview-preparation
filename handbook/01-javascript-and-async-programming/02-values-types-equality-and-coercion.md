Эта глава отвечает на один большой вопрос: **что именно находится в переменной и что JavaScript делает с этим значением, когда мы копируем, сравниваем или используем его не в том типе?**

Из него вырастают почти все типичные ловушки темы:

- почему `const`-объект можно изменить;
- почему два одинаково выглядящих объекта не равны;
- почему функция может изменить переданный объект, но не переназначить переменную вызывающего кода;
- почему `0 || 10` и `0 ?? 10` дают разные результаты;
- почему `NaN !== NaN`, а `new Set([NaN, NaN]).size === 1`;
- почему `0.1 + 0.2 !== 0.3`;
- почему оператор `+` иногда складывает, а иногда склеивает строки.

Мы начнём со значений и идентичности объектов, затем перейдём к проверке типов и особым числам. После этого разберём логические контексты, выбор значений по умолчанию и опциональные цепочки. Только когда эта база будет готова, сравним четыре семантики равенства и построим практическую модель преобразования типов.

Полные темы копирования массивов и глубокого копирования остаются в 1.5, общеизвестные символы (well-known symbols) и протоколы итерации — в 1.6, свойства и прототипы — в 1.4. Здесь берём ровно столько, сколько нужно для идентичности объектов, общих ссылок и преобразования объектов в примитивы.

## Ментальная модель

Сначала вся тема в девяти строках:

1. В JavaScript **тип есть у значения**, а переменная хранит текущее значение и может позже получить значение другого типа.
2. Примитивное значение (primitive value) — самостоятельное неизменяемое значение; значение-объект (object value) имеет идентичность (identity) и изменяемое содержимое.
3. Присваивание всегда копирует значение. Для объекта копируется значение, позволяющее обратиться к тому же самому объекту.
4. Поэтому две переменные могут разделять один объект, а поверхностная копия разрывает только верхнюю ссылку.
5. JavaScript передаёт аргументы **по значению (pass-by-value)** — в том числе значение ссылки на объект.
6. Логический контекст делит значения на истинные (truthy) и ложные (falsy); nullish — более узкая группа: только `null` и `undefined`.
7. `===`, `Object.is` и SameValueZero не выполняют общего глубокого сравнения объектов: для объектов важна идентичность.
8. Преобразование типов (coercion) сначала может превратить объект в примитив, а затем — примитив в нужный контексту тип.
9. У `+` две роли: после `ToPrimitive` он выбирает конкатенацию строк либо сложение чисел.

Три полезные аналогии:

- **Примитив как напечатанное число на карточке:** копия карточки несёт то же значение, но карточку нельзя «изменить изнутри» — можно только заменить её другой.
- **Идентичность объекта как общий документ по одной ссылке:** два человека могут открыть один документ; правка видна обоим, но создание копии верхней страницы не копирует вложенные приложения.
- **Преобразование типов как переходник:** контекст просит значение нужной формы. Иногда переходник очевиден (`Number("42")`), иногда язык подключает его скрыто (`"5" * 2`).

Аналогии помогают помнить поведение, но спецификация не требует хранить ссылку на объект как видимый адрес памяти и не превращает примитивы в реальные бумажные карточки.

## Связное объяснение в формате вопросов и ответов

### 🎯 1. Что такое значение и где у него тип?

**Значение (value)** — данные, с которыми работает программа: `42`, `"hello"`, `null`, `1n`, объект пользователя или функция. **Тип (type)** описывает набор возможных значений и правила операций над ними.

В JavaScript тип относится к текущему значению, а не навсегда к имени переменной:

```js
let result = 42;
console.log(typeof result); // "number"

result = "done";
console.log(typeof result); // "string"
```

Это не значит, что «переменная сама стала строковой коробкой». Привязка `result` сначала хранила числовое значение, затем получила строковое. Статическая система TypeScript может отдельно ограничить допустимые присваивания, но JavaScript во время выполнения видит реальные значения.

#### Какие категории значений есть в JavaScript?

На уровне языка удобно начать с двух групп:

| Группа | Значения |
|---|---|
| Примитивные значения | `undefined`, `null`, `boolean`, `number`, `bigint`, `string`, `symbol` |
| Значения-объекты | обычные объекты, массивы, функции, даты, регулярные выражения и другие объекты |

Функция — значение-объект с внутренней способностью быть вызванной. Поэтому `typeof function () {}` возвращает специальную строку `"function"`, хотя функция остаётся объектом в более широкой классификации языка.

#### Тип значения и возможность переназначить переменную — разные оси

```js
const count = 1;
// count = 2; // TypeError: assignment to constant variable
```

`count` хранит примитивное числовое значение. Запрет появился не потому, что число неизменяемо, а потому, что `const` запрещает переназначить привязку.

```js
let user = { name: "Ada" };
user = { name: "Grace" };
```

`user` хранит значение-объект, а `let` разрешает заменить его другим значением-объектом. Тип значения не определяет, можно ли переназначать привязку; это определяет форма объявления.

### 🎯 2. Чем примитивное значение отличается от значения-объекта?

Главные различия для этой темы — **неизменяемость значения** и **идентичность**.

#### Примитивы неизменяемы

**Неизменяемость (immutability)** примитива означает: само примитивное значение нельзя изменить изнутри. Операция создаёт другое значение.

```js
let text = "cat";
text.toUpperCase();

console.log(text); // "cat"

text = text.toUpperCase();
console.log(text); // "CAT"
```

Метод `toUpperCase()` не меняет исходную строку. Он возвращает новую строку. Чтобы `text` показывал новое значение, привязку нужно переназначить.

Попытка записать символ внутрь строки тоже не меняет строковое значение:

```js
"use strict";

const code = "cat";
// code[0] = "b"; // TypeError в strict mode; строка остаётся "cat"
```

Число, логическое значение, `null`, `undefined`, `bigint` и `symbol` так же не имеют изменяемых внутренних полей, доступных как у обычного объекта.

#### У объектов есть идентичность

У значения-объекта есть **идентичность**: конкретный объект остаётся тем же объектом, даже когда его содержимое меняется.

```js
const user = { name: "Ada" };
const sameUser = user;

user.name = "Grace";

console.log(sameUser.name); // "Grace"
console.log(user === sameUser); // true
```

`user` и `sameUser` содержат копии одного и того же значения, которое ведёт к одному и тому же объекту. Мы не создали второго пользователя.

Два отдельно созданных объекта имеют разную идентичность, даже если их свойства выглядят одинаково:

```js
console.log({ id: 1 } === { id: 1 }); // false
console.log([1, 2] === [1, 2]);       // false
```

Оператор не выполняет глубокого сравнения содержимого. Он спрашивает: «Это один и тот же объект?»

<details>
<summary>🔬 Точная деталь: «ссылка» (reference) — полезная модель, но не отдельный тип значений языка</summary>

В разговорной речи объекты называют «ссылочными типами» (reference types). Для интервью безопаснее сказать:

> У значения-объекта есть идентичность, а переменная содержит значение, через которое код обращается к этому объекту.

Спецификация не добавляет в список типов значений языка ECMAScript отдельный тип `Reference` для пользовательских значений. Reference Record существует как внутренний спецификационный тип для операций вроде доступа к переменной или свойству, но это не значение, которое можно получить через `typeof` или сохранить в массив.

Фраза «переменная хранит ссылку» остаётся хорошей практической моделью, если не превращать её в утверждение о видимом адресе памяти.

### 🎯 3. Чем мутация отличается от переназначения и почему появляется общее состояние?

- **Переназначение (reassignment)** меняет значение в привязке.
- **Мутация (mutation)** меняет состояние уже существующего объекта.

```js
let profile = { theme: "light" };

profile.theme = "dark";          // mutation: тот же object identity
profile = { theme: "contrast" }; // reassignment: другой object value
```

`const` запрещает только второй шаг:

```js
const settings = { compact: false };

settings.compact = true; // допустимая mutation
// settings = {};        // TypeError: reassignment запрещён
```

#### Общие ссылки

**Разделяемая ссылка (shared reference)** возникает, когда несколько привязок ведут к одному объекту:

```js
const defaults = { nested: { retries: 2 } };
const requestOptions = defaults;

requestOptions.nested.retries = 5;
console.log(defaults.nested.retries); // 5
```

Это не особое копирование «по ссылке». Обычное присваивание скопировало значение-объект, и обе копии обозначают один и тот же объект.

Аналогия с общим документом полезна здесь: два ярлыка открывают один файл. Переименование одного ярлыка не меняет другую привязку, но редактирование самого файла видно через оба ярлыка.

#### Где помогает поверхностная копия?

**Поверхностная копия (shallow copy)** создаёт новый внешний объект, но вложенные значения-объекты остаются общими:

```js
const defaults = {
  theme: "light",
  network: { retries: 2 },
};

const options = { ...defaults };

console.log(options === defaults); // false
console.log(options.network === defaults.network); // true

options.theme = "dark";
options.network.retries = 5;

console.log(defaults.theme); // "light"
console.log(defaults.network.retries); // 5
```

Распространение свойств (spread) устранило общую ссылку на верхнем уровне, но не скопировало вложенный `network`. Полная тема поверхностного и глубокого копирования, `structuredClone` и циклов будет в 1.5. Для 1.2 достаточно правила:

> Новый внешний объект не означает новый граф объектов.

### 🎯 4. JavaScript передаёт объекты по значению или по ссылке?

Короткий точный ответ: **JavaScript передаёт аргументы по значению**. Если аргумент — объект, параметр получает копию значения, которое ведёт к тому же объекту.

```js
function update(user) {
  user.name = "Grace";       // mutation общего объекта
  user = { name: "Lin" };    // reassignment только локального параметра
}

const original = { name: "Ada" };
update(original);

console.log(original); // { name: "Grace" }
```

Пошагово:

1. Привязка `original` содержит значение-объект.
2. При вызове это значение копируется в новую локальную привязку параметра `user`.
3. Оба значения обозначают один и тот же объект, поэтому `user.name = ...` меняет общий объект.
4. `user = ...` заменяет только значение локальной привязки `user`.
5. Привязка `original` вызывающего кода не переназначается.

#### Почему это не передача по ссылке (pass-by-reference)?

При настоящей передаче переменной по ссылке функция могла бы переназначить привязку вызывающего кода. Здесь не может:

```js
function replace(value) {
  value = { replaced: true };
}

let item = { replaced: false };
replace(item);

console.log(item.replaced); // false
```

Поэтому фраза «примитивы передаются по значению, объекты — по ссылке» создаёт неправильную модель. Лучше сказать:

> Всё передаётся по значению. Для аргумента-объекта скопированное значение сохраняет доступ к тому же самому объекту.

Если функция должна «заменить значение у вызывающего кода», она обычно возвращает новое значение, а вызывающий код явно присваивает его:

```js
function replace(value) {
  return { ...value, replaced: true };
}

item = replace(item);
```

### 🎯 5. Что показывает `typeof` и где он вводит в заблуждение?

`typeof` возвращает строку с грубой классификацией значения во время выполнения:

| Значение | `typeof` |
|---|---|
| `undefined` | `"undefined"` |
| `null` | `"object"` — историческая ошибка |
| `true` | `"boolean"` |
| `42`, `NaN`, `Infinity` | `"number"` |
| `42n` | `"bigint"` |
| `"hello"` | `"string"` |
| `Symbol("id")` | `"symbol"` |
| `function () {}` | `"function"` |
| массив, дата, регулярное выражение, обычный объект | `"object"` |

```js
typeof NaN;          // "number"
typeof [];           // "object"
typeof null;         // "object"
typeof (() => {});   // "function"
```

`typeof` хорошо отвечает на вопрос «примитив какого базового вида передо мной?» и умеет отдельно узнавать вызываемые объекты. Но он не различает массив, дату и обычный объект.

Для точной проверки нужен подходящий контракту инструмент:

```js
Array.isArray(value);
value === null;
Number.isNaN(value);
```

Проверка класса через `instanceof` имеет отдельные ограничения, включая разные среды выполнения (realms), и относится к объектной модели из 1.4.

#### Почему `typeof null === "object"`?

Это историческая несовместимость, сохранённая ради совместимости с существующим веб-кодом. `null` — отдельное примитивное значение, а не объект. В первой реализации JavaScript его внутреннее представление пересеклось с меткой объектов; исправление позже сломало бы существующий код.

Правило для интервью:

> Список примитивов определяет семантику; `typeof` — оператор с историческими особенностями, а не идеальная функция `getExactType`.

#### `undefined` и `null`

Оба значения часто обозначают отсутствие, но их происхождение и контракт обычно различаются:

- `undefined` часто появляется как «значение не было предоставлено»: отсутствующий аргумент, отсутствующее свойство, `let value;`, функция без явного `return`;
- `null` обычно записывают намеренно как «значения сейчас нет» или «результат отсутствует» по контракту API.

```js
function findUser() {
  return null; // намеренно: пользователь не найден
}

const config = {};
console.log(config.timeout); // undefined: свойства нет
```

Это соглашение, а не автоматическая гарантия языка. В реальном API нужно документировать, может ли поле отсутствовать, иметь значение `undefined`, `null` или допускать несколько этих вариантов сразу.

#### Проверка необъявленного идентификатора

У `typeof` есть специальное поведение:

```js
typeof neverDeclared; // "undefined"
```

Обычное чтение `neverDeclared` дало бы `ReferenceError`, но `typeof` позволяет проверить действительно необъявленное имя. При этом результат не отличает его от объявленной переменной со значением `undefined`:

```js
let declared;

typeof declared;      // "undefined"
typeof neverDeclared; // "undefined"
```

Для свойств объекта это вообще не проверка существования. Если важно отличить отсутствующее собственное свойство от существующего со значением `undefined`, используйте `Object.hasOwn(object, key)`.

Связь с 1.1: `typeof` **не обходит TDZ**:

```js
// Намеренно ошибочный пример: чтение binding в TDZ.
typeof later; // ReferenceError
let later;
```

### 🔬 6. Зачем нужны `Symbol` и `BigInt`?

Оба — примитивные типы, но решают разные задачи.

#### `Symbol`: уникальное примитивное значение

Каждый обычный вызов `Symbol(description)` создаёт новое уникальное значение:

```js
const first = Symbol("id");
const second = Symbol("id");

console.log(first === second); // false
console.log(typeof first);     // "symbol"
```

Описание помогает отладке, но не определяет идентичность. Символы могут быть ключами свойств и помогают избежать случайного совпадения строковых имён:

```js
const cacheKey = Symbol("cache");
const record = { [cacheKey]: "ready" };

console.log(record[cacheKey]); // "ready"
```

`Symbol.for("key")` — отдельный API глобального реестра символов (symbol registry): повторный вызов с тем же ключом возвращает тот же символ. Общеизвестные символы вроде `Symbol.iterator` будут подробно рассмотрены в 1.6.

Для строкового представления символа используйте явный `String(symbol)`:

```js
const token = Symbol("token");

String(token); // "Symbol(token)"
// `${token}`; // TypeError: implicit string coercion Symbol запрещена
```

#### `BigInt`: целые числа произвольной величины

`BigInt` хранит целые числа за пределами безопасного диапазона целых у `Number`:

```js
const exact = 9_007_199_254_740_993n;

typeof exact; // "bigint"
```

`BigInt` не является «более точным `Number` для всего». Он не хранит дроби:

```js
5n / 2n; // 2n — дробная часть отбрасывается к нулю
```

Большинство арифметических операций не разрешает смешивать `BigInt` и `Number`:

```js
// Намеренно ошибочный пример: mixed numeric types.
1n + 1; // TypeError
```

Сначала нужно принять явное решение о типе результата:

```js
1n + BigInt(1); // 2n
Number(1n) + 1; // 2, но большое BigInt может потерять точность
```

Сравнения имеют свои правила:

```js
0n === 0; // false: разные types
0n == 0;  // true: loose equality допускает математическое сравнение
1n < 2;   // true: relational comparison умеет сравнить значения
```

Практическое правило: внутри одной арифметической модели держите один числовой тип. Используйте `BigInt` для целых значений, которые могут выйти за безопасный диапазон целых, а не для обычных дробных вычислений.

### 🎯 7. Что особенного в `NaN`, `Infinity` и `-0`?

Все три относятся к типу `number`:

```js
typeof NaN;       // "number"
typeof Infinity;  // "number"
typeof -0;        // "number"
```

#### `NaN`

`NaN` означает, что числовая операция не дала осмысленного числового результата. Например:

```js
Number("not a number"); // NaN
0 / 0;                  // NaN
```

`NaN` распространяется по многим вычислениям:

```js
NaN + 10; // NaN
```

Главная ловушка:

```js
NaN === NaN; // false
NaN !== NaN; // true
```

Проверяйте его через `Number.isNaN()`:

```js
Number.isNaN(NaN);     // true
Number.isNaN("hello"); // false
```

Глобальная функция `isNaN()` сначала выполняет преобразование к числу:

```js
isNaN("hello"); // true: Number("hello") → NaN
isNaN("");      // false: Number("") → 0
```

Поэтому она отвечает на запутанный вопрос «станет ли аргумент `NaN` после преобразования к `Number`?», а не «является ли значение самим `NaN`». В новом коде почти всегда нужен `Number.isNaN()`.

#### `Infinity` и `-Infinity`

Это числовые значения для положительной и отрицательной бесконечности:

```js
1 / 0;  // Infinity
-1 / 0; // -Infinity

Infinity + 1;        // Infinity
Infinity - Infinity; // NaN
```

Если внешний ввод должен быть обычным конечным числом, одной проверки `!Number.isNaN(value)` недостаточно: `Infinity` не является `NaN`. Используйте `Number.isFinite(value)`.

```js
Number.isFinite(42);       // true
Number.isFinite(Infinity); // false
Number.isFinite("42");    // false, без coercion
```

Глобальная `isFinite()` тоже выполняет преобразование типов, поэтому для валидации типизированного значения обычно хуже.

#### `-0`

IEEE 754 хранит положительный и отрицательный ноль:

```js
0 === -0;          // true
Object.is(0, -0);  // false
1 / 0;             // Infinity
1 / -0;            // -Infinity
```

В большинстве бизнес-задач знак нуля не важен. Он становится наблюдаемым в отдельных математических вычислениях, визуализации направлений и API, где знак предельного значения несёт смысл. Не нужно заменять каждый `===` на `Object.is`; сначала определите требования.

### 🔬 8. Почему `0.1 + 0.2 !== 0.3` и как сравнивать дроби?

JavaScript `Number` использует 64-битный двоичный формат с плавающей точкой (binary floating point) IEEE 754. Некоторые простые десятичные дроби не имеют конечного двоичного представления, поэтому сохраняются ближайшим доступным значением:

```js
0.1 + 0.2;         // 0.30000000000000004
0.1 + 0.2 === 0.3; // false
```

Это не «ошибка JavaScript» в смысле неправильной реализации. Это ограничение конечного представления с плавающей точкой, знакомое многим языкам.

#### Почему одного `Number.EPSILON` недостаточно?

`Number.EPSILON` — расстояние между `1` и следующим представимым числом. Оно полезно около величины `1`, но абсолютная точность меняется вместе с масштабом числа.

Плохое универсальное правило:

```js
Math.abs(a - b) < Number.EPSILON;
```

Оно может быть слишком строгим для больших значений и слишком щедрым или бессмысленным для требований конкретного домена.

Практическая функция сочетает абсолютный допуск для чисел около нуля и относительный допуск для масштаба:

```js
function nearlyEqual(
  left,
  right,
  { relativeTolerance = 1e-12, absoluteTolerance = Number.EPSILON } = {},
) {
  if (left === right) {
    return true; // одинаковые finite values, zero и одинаковая Infinity
  }

  if (!Number.isFinite(left) || !Number.isFinite(right)) {
    return false;
  }

  const difference = Math.abs(left - right);
  const scale = Math.max(Math.abs(left), Math.abs(right));

  return difference <= Math.max(
    absoluteTolerance,
    relativeTolerance * scale,
  );
}
```

Числа `1e-12` и `Number.EPSILON` здесь не универсальная истина. Допуски должны идти из требований: пиксели, физические измерения, проценты и научные расчёты имеют разные допустимые ошибки.

#### Как безопаснее работать с деньгами?

Для валютной суммы с фиксированным масштабом часто хранят целое число минимальных денежных единиц:

```js
const priceInCents = 1_099;
const quantity = 3;
const totalInCents = priceInCents * quantity; // 3297
```

Но нужен явный контракт:

- какая валюта и сколько у неё минимальных денежных единиц;
- когда и как округлять налоги, скидки и распределения;
- остаются ли целые значения в пределах проверки `Number.isSafeInteger()`;
- как сериализуется и валидируется значение на границе API.

Если суммы могут выйти за безопасный диапазон целых, рассмотрите `BigInt` для целого числа минимальных денежных единиц. Если нужны точные правила десятичных вычислений с дробным масштабом, процентами и регуляторным округлением, используйте согласованный контракт с сервером и проверенную библиотеку десятичной арифметики или арифметики с фиксированной точкой. Не округляйте каждую промежуточную операцию «на глаз» через `toFixed()` — он возвращает строку и не определяет вашу бизнес-политику округления.

### 🎯 9. Что такое истинные, ложные и nullish-значения?

В логическом контексте JavaScript выполняет преобразование к логическому типу. **Ложные значения** дают `false`; остальные значения — **истинные**.

Полный практический список ложных значений:

| Ложное значение | Замечание |
|---|---|
| `false` | логическое `false` |
| `0`, `-0` | оба знака нуля |
| `0n` | ноль типа `BigInt` |
| `NaN` | некорректный числовой результат |
| `""` | пустая строка |
| `null` | намеренное отсутствие |
| `undefined` | отсутствие значения |

```js
Boolean(0);          // false
Boolean("0");        // true
Boolean([]);         // true
Boolean({});         // true
Boolean("false");    // true
```

Объекты всегда истинны, даже пустой массив и объект-обёртка вокруг `false`:

```js
Boolean(new Boolean(false)); // true: это object
```

**Nullish-значения** — только `null` и `undefined`. Это не синоним ложных значений:

```text
falsy   = false, 0, -0, 0n, NaN, "", null, undefined
nullish =                              null, undefined
```

Различие важно для значений по умолчанию: `0`, `false` и `""` часто являются валидными данными, а не отсутствием.

### 🎯 10. Что значит вычисление с коротким замыканием и что возвращают `||`, `&&`, `??`?

**Короткое замыкание вычисления (short-circuit evaluation)** означает: правый операнд вычисляется только тогда, когда он нужен для результата.

Важно: логические операторы возвращают один из операндов, а не обязательно логическое значение.

#### `||`: первое истинное или последнее значение

```js
"Ada" || "Anonymous"; // "Ada"
"" || "Anonymous";    // "Anonymous"
0 || 10;              // 10
```

Если левый операнд истинен, `||` возвращает его и не вычисляет правый. Иначе вычисляет и возвращает правый.

```js
let calls = 0;

function fallback() {
  calls += 1;
  return "default";
}

"ready" || fallback();
console.log(calls); // 0
```

`||` подходит, когда **любое ложное значение действительно означает отсутствие или отказ**. Например, выбрать первую непустую подпись. Для числового нуля, `false` или пустой строки как валидных данных он часто неверен.

#### `&&`: первое ложное или последнее значение

```js
true && "render"; // "render"
0 && expensive(); // 0; expensive() не вызывается
```

`&&` полезен для условного вычисления, но длинные цепочки могут скрывать бизнес-условие. В рабочем коде иногда ясный `if` лучше компактности.

#### `??`: правый операнд только для nullish-значения

```js
0 ?? 10;          // 0
false ?? true;    // false
"" ?? "default"; // ""
null ?? "default";      // "default"
undefined ?? "default"; // "default"
```

Поэтому для значения по умолчанию вопрос звучит так:

```text
||  → считать отсутствием любое falsy?
??  → считать отсутствием только null / undefined?
```

Реальная ошибка:

```js
function normalizeSettings(input) {
  return {
    retries: input.retries || 3,
    animations: input.animations || true,
  };
}

normalizeSettings({ retries: 0, animations: false });
// Ошибка: { retries: 3, animations: true }
```

Исправление:

```js
function normalizeSettings(input) {
  return {
    retries: input.retries ?? 3,
    animations: input.animations ?? true,
  };
}
```

<details>
<summary>🔬 Точная деталь: смешивание <code>??</code> с <code>||</code>/<code>&amp;&amp;</code></summary>

JavaScript запрещает смешивать `??` с `||` или `&&` в одной цепочке без явных скобок:

```js
// Намеренно ошибочный пример: SyntaxError.
const value = left ?? middle || fallback;
```

Нужно обозначить предполагаемую группировку:

```js
const firstValue = (left ?? middle) || fallback;
// или
const secondValue = left ?? (middle || fallback);
```

Это не просто вопрос приоритета операций: синтаксический запрет заставляет автора сделать неоднозначное намерение видимым.

</details>

Операторы `||=` и `??=` применяют те же критерии к условному присваиванию. Используйте их только если изменение привязки или свойства соответствует контракту.

### 🎯 11. Что делает опциональная цепочка и где прекращается защита?

**Опциональная цепочка (optional chaining)** `?.` останавливает непрерывную цепочку доступа, если значение слева равно `null` или `undefined`, и возвращает `undefined` вместо ошибки.

```js
const city = user?.address?.city;
const firstItem = response?.items?.[0];
const result = callbacks.onDone?.();
```

Это не «подавить любую ошибку». `?.` проверяет только конкретное значение слева на `null` или `undefined`.

#### Ловушка 1: каждый потенциально отсутствующий шаг должен быть защищён

```js
const user = { profile: null };

user?.profile.name;  // TypeError: profile существует как null,
                     // а перед .name нет ?.
user?.profile?.name; // undefined
```

В выражении `base?.a.b` короткое замыкание первого `?.` распространяется по непрерывной цепочке, если `base` равен `null` или `undefined`. Но если `base` существует, а `a` равен `null` или `undefined`, обычный `.b` всё равно бросит ошибку.

#### Ловушка 2: группировка разрывает непрерывную цепочку

```js
const data = null;

data?.a.b;       // undefined: вся непрерывная цепочка остановлена на data
(data?.a).b;     // TypeError: результат undefined, затем отдельный .b
```

Скобки здесь логически создают промежуточный результат и следующий обычный доступ.

#### Ловушка 3: опциональный вызов проверяет отсутствие, но не возможность вызова

```js
const api = { onDone: "not a function" };

api.onDone?.(); // TypeError: свойство существует, но не callable
```

Также важно различать:

```js
api?.onDone();  // проверяет api; существующий api без onDone даст TypeError
api.onDone?.(); // проверяет onDone; undefined вернёт undefined
```

#### Ловушка 4: корневой идентификатор всё равно должен разрешиться

```js
// Намеренно ошибочный пример: identifier не объявлен.
undeclaredRoot?.value; // ReferenceError
```

Опциональная цепочка не заменяет `typeof undeclaredRoot` и не обходит TDZ.

#### Ловушка 5: короткое замыкание пропускает побочные эффекты только внутри цепочки

```js
let index = 0;
const items = null;

items?.[index++];
console.log(index); // 0
```

Вычисляемый ключ не вычисляется, потому что цепочка остановилась. Это полезно, но скрытые побочные эффекты внутри доступа к свойствам обычно ухудшают читаемость.

#### Ловушка 6: не все позиции синтаксически допустимы

Опциональную цепочку нельзя использовать как цель присваивания; `new` и шаблонные строки с тегом (tagged templates) имеют отдельные запреты:

```js
// Намеренно ошибочные примеры: SyntaxError.
user?.name = "Ada";
new Constructor?.();
tag?.`text`;
```

#### Что `?.` не ловит?

- исключение геттера;
- ошибку внутри реально вызванной функции;
- неверный тип существующего метода;
- отсутствие обязательных данных, которое должно считаться ошибкой контракта.

Практическая рекомендация: используйте `?.` для действительно необязательных данных на границах доступа. Если поле обязано существовать, явная ошибка или валидация часто полезнее тихого `undefined`.

### 🎯 12. Какие семантики равенства есть в JavaScript?

Для интервью удобно сравнивать четыре алгоритма:

| Семантика | Доступ | Преобразование типов | `NaN` с `NaN` | `+0` с `-0` | Объекты |
|---|---|---:|---:|---:|---|
| Нестрогое равенство (loose equality) | `==` | да | false | true | одна идентичность после возможного ToPrimitive |
| Строгое равенство (strict equality) | `===` | нет | false | true | одна идентичность |
| SameValue | `Object.is()` | нет | true | false | одна идентичность |
| SameValueZero | встроенные средства языка | нет | true | true | одна идентичность |

#### `===`: современный выбор по умолчанию

Строгое равенство не преобразует разные типы:

```js
0 === "0";          // false
null === undefined; // false
```

Для одинаковых примитивных типов сравниваются значения с особыми правилами для чисел. Для объектов — идентичность:

```js
const first = { id: 1 };
const alias = first;

first === alias;       // true
first === { id: 1 };   // false
```

#### `Object.is()`: SameValue

`Object.is()` совпадает с `===` в большинстве обычных случаев, но меняет два граничных числовых случая:

```js
Object.is(NaN, NaN); // true
Object.is(0, -0);    // false
```

Используйте его, когда эти различия соответствуют нужной семантике. Это не глубокое равенство.

#### SameValueZero

SameValueZero считает `NaN` равным самому себе, но не различает знаки нуля:

```js
[NaN].includes(NaN); // true
new Set([NaN, NaN]).size; // 1
```

Эту семантику используют:

- `Array.prototype.includes()` и `TypedArray.prototype.includes()`;
- ключи в `Map`;
- значения в `Set`.

Для контраста `indexOf()` использует сравнение по правилам строгого равенства и не находит `NaN`:

```js
[NaN].indexOf(NaN); // -1
```

Практическая карта:

```text
обычное сравнение в приложении → ===
нужно NaN == NaN и различать signed zero → Object.is
поиск/ключи built-in коллекций → знать SameValueZero
структурное сравнение objects → отдельный доменный алгоритм, не один из этих operators
```

### 🎯 13. Когда `==` преобразует типы и можно ли его использовать осознанно?

**Нестрогое равенство** пытается привести операнды к совместимой форме по конкретному алгоритму. Оно не означает «сравнить после простого `Number()` для всего».

Примеры:

```js
"5" == 5;            // true
false == 0;          // true
null == undefined;   // true
null == 0;           // false
0n == 0;             // true
```

Практическая модель для распространённых случаев:

1. Одинаковые типы сравниваются почти как `===`.
2. `null` нестрого равен только `undefined` (и редкому устаревшему веб-объекту `document.all`).
3. Логическое значение превращается в число: `false → 0`, `true → 1`.
4. Строка рядом с числом преобразуется к числу.
5. Объект рядом с примитивом проходит `ToPrimitive`, затем сравнение продолжается.
6. Символ не превращается автоматически в другую категорию примитивов для равенства.

#### Осознанный `value == null`

Один распространённый намеренный шаблон:

```js
if (value == null) {
  // value — null или undefined
}
```

Он компактен и точно использует специальное правило `null`/`undefined`. Но команда должна считать такое исключение читаемым и закрепить его в правилах линтера. Если неоднозначность нежелательна, пишите явно:

```js
if (value === null || value === undefined) {
  // ...
}
```

Практическая рекомендация: используйте `===` по умолчанию. `==` оставляйте для редкого осознанного контракта, а не для случайного удобства.

<details>
<summary>🧓 Legacy: <code>document.all</code></summary>

Браузеры сохраняют необычное поведение `document.all` ради совместимости: он ложен в логическом контексте, `typeof document.all === "undefined"` и он нестрого равен `null`/`undefined`, хотя технически это специальный объект среды выполнения (host object).

Это нужно узнавать как историческую особенность веб-платформы, но нельзя использовать как подход для нового кода или переносить на обычные объекты.

</details>

### 🎯 14. Что такое явное и неявное преобразование типов?

**Преобразование типов (type coercion)** — получение значения другого типа по правилам языка.

- **Явное преобразование (explicit coercion)** прямо видно в коде: `Boolean(value)`, `Number(text)`, `String(id)`.
- **Неявное преобразование (implicit coercion)** запускает оператор или контекст: `if (value)`, `"5" * 2`, `value == 0`.

Явное преобразование не автоматически безопасно, а неявное не автоматически плохо. Важнее, очевиден ли контракт и обработаны ли ошибки.

#### Преобразование к логическому типу

```js
Boolean("");   // false
Boolean("0");  // true
Boolean(0);    // false
Boolean([]);   // true
```

`Boolean(value)` и `!!value` дают одно и то же примитивное логическое значение. В коде `Boolean()` обычно яснее при преобразовании данных; `!!` часто встречается как короткая идиома.

Преобразование к логическому типу не вызывает `valueOf()` или `toString()` у объекта. Любой обычный объект истинен независимо от содержимого.

#### Преобразование к `Number`

| Вход | `Number(input)` |
|---|---:|
| `undefined` | `NaN` |
| `null` | `0` |
| `true` / `false` | `1` / `0` |
| `"42"` | `42` |
| `""` или строка только из пробельных символов | `0` |
| `"42px"` | `NaN` |
| `1n` | `1`, с риском потери точности для больших значений `BigInt` |
| `Symbol()` | `TypeError` |

```js
Number(" 42 "); // 42
Number("");     // 0
Number("42px"); // NaN
```

Унарный плюс обычно выполняет такое же преобразование к числу, но не принимает `BigInt`:

```js
+"42"; // 42
// +1n; // TypeError
```

Для пользовательского ввода сначала определите, разрешены ли пустая строка, пробельные символы, десятичный формат, знаки и `Infinity`. Слепой `Number(input)` может принять больше, чем разрешает ваш продукт.

#### Преобразование к `String`

```js
String(null);        // "null"
String(undefined);   // "undefined"
String(42);          // "42"
String(1n);          // "1"
String(Symbol("x")); // "Symbol(x)"
```

`String(value)` полезен именно тем, что намерение видно и символ обрабатывается безопасно. Не используйте `"" + value` как универсальную функцию преобразования: оператор `+` сначала выполняет преобразование к примитиву и может вести себя иначе для объектов и символов.

### 🎯 15. Почему оператор `+` особенно опасен для ментальной модели?

У бинарного `+` две роли:

1. конкатенация строк;
2. сложение чисел: двух значений `Number` или двух значений `BigInt`.

Упрощённый алгоритм:

```text
left  → ToPrimitive
right → ToPrimitive
если хотя бы один primitive — String → оба к String → concatenation
иначе оба к numeric type
  два Number → number addition
  два BigInt → bigint addition
  смесь Number / BigInt → TypeError
```

Примеры:

```js
1 + 2;          // 3
"1" + 2;        // "12"
1 + "2";        // "12"
true + 1;       // 2
null + 1;       // 1
undefined + 1;  // NaN
1n + 2n;        // 3n
"1" + 2n;       // "12"
// 1n + 2;      // TypeError
```

Порядок и группировка важны:

```js
1 + 2 + "3"; // "33": сначала 3, затем concatenation
"1" + 2 + 3; // "123": после первой строки дальше concatenation
```

Другие арифметические операторы обычно требуют преобразования к числовому типу:

```js
"5" - 2; // 3
"5" * 2; // 10
"5" / 2; // 2.5
```

Это одна из причин не использовать неявное преобразование типов как форматирование данных. Явное `Number(input)` или `String(value)` делает границу преобразования видимой.

### 🎯 16. Как работают сравнения `<`, `>`, `<=`, `>=` с разными типами?

Сравнение порядка (relational comparison) — не `==` с другим знаком. Оно сначала получает примитивные значения. Если оба примитива — строки, выполняется лексикографическое сравнение последовательностей кодовых единиц UTF-16. Иначе используется числовое сравнение с правилами для `Number`/`BigInt`.

```js
"2" < "10"; // false: сравниваются строки, "2" идёт после "1"
"2" < 10;   // true: string преобразуется к number
2n < 2.5;   // true: relational comparison разрешает Number/BigInt
```

Знаменитая ловушка показывает, что равенство и порядок идут разными путями:

```js
null == 0;  // false
null > 0;   // false
null >= 0;  // true
```

Для `>=` сравнение порядка приводит `null` к `0`; для `==` специальное правило `null` не считает его равным числовому нулю.

С `NaN` сравнения не дают обычного порядка:

```js
NaN < 1;  // false
NaN > 1;  // false
NaN === NaN; // false
```

Практические рекомендации:

- нормализуйте данные на границе системы;
- не смешивайте числовые строки и числа глубоко внутри бизнес-логики;
- для сортировки явно документируйте функцию сравнения и поведение некорректных значений;
- не выводите смысл из одной проверки вроде `value >= 0`, если `value` мог быть `null` или строкой.

### 🔬 17. Как `ToPrimitive`, `valueOf()` и `toString()` связаны с преобразованием типов?

Когда оператору нужен примитив, а он получает объект, запускается абстрактная операция **`ToPrimitive`**.

Практическая модель:

1. Если у объекта есть метод `[Symbol.toPrimitive]`, он получает подсказку (hint) `"string"`, `"number"` или `"default"`.
2. Иначе язык пробует обычные методы в порядке, зависящем от подсказки.
3. Результат должен быть примитивом; возвращённый объект не завершает преобразование.
4. Полученный примитив затем может пройти `ToString`, `ToNumber` или другую операцию контекста.

| Контекст | Подсказка / обычный порядок |
|---|---|
| преобразование к строке | `"string"`: `toString()` → `valueOf()` |
| преобразование к числу | `"number"`: `valueOf()` → `toString()` |
| бинарный `+`, объект в `==` | `"default"`: обычно как для числа; `Date` — особый случай, как для строки |

#### Обычный объект

```js
const amount = {
  valueOf() {
    return 7;
  },
  toString() {
    return "seven";
  },
};

Number(amount); // 7: number hint → valueOf first
String(amount); // "seven": string hint → toString first
amount + 1;     // 8: default hint, valueOf returns 7
```

#### `[Symbol.toPrimitive]` имеет приоритет

```js
const value = {
  [Symbol.toPrimitive](hint) {
    if (hint === "number") return 10;
    if (hint === "string") return "ten";
    return 20;
  },
};

+value;         // 10
String(value);  // "ten"
value + 1;      // 21
```

Если `[Symbol.toPrimitive]` возвращает объект, возникает `TypeError`.

#### Почему `[] == ![]` даёт `true`?

Это умеренно полезная проверка модели на интервью, но плохой стиль для рабочего кода:

```js
[] == ![]; // true
```

Разбор:

1. `[]` — истинный в логическом контексте объект, поэтому `![]` даёт `false`.
2. В нестрогом равенстве логическое `false` превращается в число `0`.
3. Левый массив рядом с примитивом проходит `ToPrimitive`: пустой массив через `toString()` даёт `""`.
4. `""` рядом с числом превращается в `0`.
5. `0 == 0` → `true`.

Ценность головоломки — проверить последовательность преобразований. В реальном коде не нужно писать выражения, правильность которых зависит от пяти скрытых шагов.

### 🎯 18. Как системно решать задачи на предсказание результата для значений и преобразования типов?

Не пытайтесь помнить все головоломки как отдельные факты. Для каждого оператора задайте один и тот же набор вопросов.

#### Шаг 1. Выпишите исходные типы и идентичности объектов

```js
const a = [];
const b = a;
const c = [];
```

Здесь `a`/`b` разделяют идентичность, `c` — другой объект.

#### Шаг 2. Назовите оператор и его правила равенства или преобразования типов

- `===` → без преобразования типов;
- `Object.is` → SameValue;
- `includes` / `Set` / `Map` → SameValueZero;
- `==` → IsLooselyEqual;
- `+` → ToPrimitive, затем строковая либо числовая ветвь;
- `<`/`>=` → сравнение порядка;
- `||` → ложные значения;
- `??` / `?.` → nullish-значения.

#### Шаг 3. Если участвует объект, выполните `ToPrimitive`

Проверьте `[Symbol.toPrimitive]`, затем соответствующий порядок `valueOf()`/`toString()`.

#### Шаг 4. Выполните преобразование примитива

Запишите промежуточные значения явно:

```text
false → 0
""    → 0 в number context
[]    → "" через ToPrimitive
```

#### Шаг 5. Только теперь примените оператор

Не перескакивайте сразу к ответу. Например:

```js
const left = [1];
const result = left + 2;
```

```text
[1] → ToPrimitive → "1"
"1" + 2 → string branch
result → "12"
```

#### Шаг 6. Назовите вывод для рабочего кода

Хороший интервью-ответ заканчивается не головоломкой, а инженерным правилом: нормализуйте данные на границах системы, используйте `===`, выбирайте `??` для значения по умолчанию при `null`/`undefined`, не полагайтесь на скрытое преобразование объектов.

|---|---|
| `if (value)` | истинное/ложное значение |

| Нужно | Инструмент |
|---|---|

## Типичные ошибки

1. **«Тип принадлежит переменной навсегда».** Тип во время выполнения принадлежит текущему значению.
2. **«`const` делает объект неизменяемым».** Он запрещает переназначение привязки.
3. **«Распространение свойств полностью копирует объект».** Это поверхностная копия; вложенные объекты могут оставаться общими.
4. **«Объекты передаются по ссылке».** Аргумент передаётся по значению; скопированное значение-объект обозначает тот же самый объект.
5. **«`typeof null` доказывает, что `null` — объект».** Это историческая особенность оператора.
6. **«`typeof x === "undefined"` всегда означает, что переменная не объявлена».** Объявленный `undefined` выглядит так же; TDZ бросает ошибку.
7. **«`isNaN` проверяет именно `NaN`».** Глобальная функция сначала преобразует тип; `Number.isNaN` не преобразует.
8. **«Любая ошибка вычислений с плавающей точкой исправляется `Number.EPSILON`».** Допуск зависит от масштаба и домена.
9. **«Все объекты истинны, кроме пустых».** Пустые массивы и объекты тоже истинны в логическом контексте.
10. **«`||` и `??` взаимозаменяемы».** Первый реагирует на все ложные значения, второй — только на `null`/`undefined`.
11. **«Опциональная цепочка ловит любую ошибку дальше».** Она защищает конкретную непрерывную цепочку при `null`/`undefined`.
12. **«`Object.is` — глубокое равенство».** Для объектов он по-прежнему сравнивает идентичность.
13. **«`==` просто приводит обе стороны к `Number`».** Алгоритм имеет отдельные ветви для `null`/`undefined`, логических значений, строк, `BigInt` и объектов.
14. **«`+` всегда складывает».** После ToPrimitive строковый операнд выбирает конкатенацию.

## Ловушки на интервью

### Неизменяемость примитива против переназначения

Строка не меняется от `toUpperCase()`, но привязку `let` можно переназначить новой строкой. Объект может мутировать даже через `const`.

### Общая мутация после поверхностного копирования

Сначала сравните идентичность внешнего объекта, затем отдельно идентичность каждого вложенного объекта.

### `NaN`, знаки нуля и разные алгоритмы равенства

```js
NaN === NaN;              // false
Object.is(NaN, NaN);      // true
0 === -0;                 // true
Object.is(0, -0);         // false
[NaN].includes(NaN);      // true
```

### Значение по умолчанию сохраняет или уничтожает валидные ложные значения

Проверьте `0`, `false`, `""` и `NaN` отдельно. `??` сохраняет их все.

### Опциональная цепочка заканчивается раньше, чем кажется

`(object?.a).b` уже не одна непрерывная цепочка. `object?.method()` и `object.method?.()` защищают разные значения.

### Равенство объектов

Два литеральных объекта никогда не становятся одним и тем же объектом только потому, что их ключи и значения одинаковы.

### Головоломка с преобразованием типов

Разбирайте `[] == ![]` только через промежуточные шаги и сразу отмечайте: это проверка ментальной модели, не рекомендация для рабочего кода.

## Как объяснить тему на интервью за 30–60 секунд

### Примитивы, объекты и `const`

> В JavaScript тип принадлежит значению. Примитивы — `undefined`, `null`, логические значения, числа, большие целые, строки и символы — неизменяемы: операция создаёт новое примитивное значение. У объектов есть идентичность и обычно изменяемое состояние. `const` фиксирует привязку, а не объект, поэтому `const user = {}` можно мутировать, но нельзя переназначить. При присваивании значения-объекта копируется значение, ведущее к тому же самому объекту, поэтому возможна общая мутация.

### Передача по значению

> JavaScript передаёт аргументы по значению. Когда аргумент — объект, параметр получает копию значения-объекта, которая указывает на тот же самый объект. Поэтому мутация через параметр видна вызывающему коду, но переназначение параметра не меняет привязку вызывающей функции. Именно поэтому JavaScript неточно называть языком с передачей по ссылке.

### `===`, `Object.is` и SameValueZero

> Для обычного кода выбор по умолчанию — `===`: без преобразования типов, объекты сравниваются по идентичности, `NaN` не равен себе, а `+0` и `-0` равны. `Object.is` использует SameValue: считает `NaN` равным себе и различает знаки нуля. SameValueZero тоже считает `NaN` равным себе, но объединяет оба нуля; его используют `includes`, `Set` и `Map`.

### `||`, `??` и опциональные цепочки

> `||` возвращает запасное значение для любого ложного значения, поэтому может потерять валидные `0`, `false` и пустую строку. `??` использует запасное значение только для `null` или `undefined`. Опциональная цепочка тоже реагирует только на `null`/`undefined` и останавливает одну непрерывную цепочку. Группировка может её разорвать, а существующий метод, который нельзя вызвать, всё равно даст `TypeError`.

### Преобразование типов и `+`

> Преобразование типов бывает явным и неявным. Если оператор получает объект там, где нужен примитив, сначала работает `ToPrimitive`: приоритет у `Symbol.toPrimitive`, затем порядок `valueOf`/`toString` зависит от подсказки. Бинарный `+` после этого выбирает конкатенацию строк, если хотя бы один примитив — строка; иначе выполняет сложение `Number` или `BigInt`. Поэтому я нормализую типы на границах системы и не строю рабочую логику на скрытых цепочках преобразования типов.
