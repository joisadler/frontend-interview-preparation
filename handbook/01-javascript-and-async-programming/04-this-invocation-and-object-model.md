## Ментальная модель

1. Обычная функция получает `this` из конкретного вызова. Стрелочная функция читает внешний лексический `this`.
2. У объекта есть собственные свойства и внутренняя ссылка `[[Prototype]]` на другой объект либо `null`.
3. Чтение свойства идёт вверх по цепочке до первого совпадения. Присваивание и определение свойства подчиняются другим правилам.
4. `.prototype` конструктора — обычное свойство, используемое при создании экземпляров. Это не `[[Prototype]]` самой функции.
5. `new` создаёт экземпляр, связывает его с прототипом и выполняет конструктор. Явно возвращённый объект может заменить экземпляр.
6. Класс организует ту же прототипную модель, но добавляет строгий вызов, поля, наследование и приватные элементы.
7. Собственность и перечисляемость свойства — независимые признаки. Неперечисляемое свойство не становится приватным.
8. Дескриптор задаёт вид свойства и разрешённые операции. Getter и setter являются исполняемым кодом.
9. `preventExtensions`, `seal` и `freeze` ограничивают один объект, а не весь достижимый граф.
10. Proxy перехватывает операции, а Reflect помогает передать их дальше. Обёртка всё равно имеет отдельную идентичность.

Полезны две отдельные аналогии. Цепочка прототипов похожа на настройки с наследованием: локальная настройка выигрывает, иначе ищем выше. Дескриптор похож на правила доступа к конкретному пункту: можно ли читать вычисляемое значение, записывать его, удалять или перечислять. Аналогии объясняют поиск и ограничения, но не означают, что прототипные методы копируются в экземпляры.

## Связное объяснение в формате вопросов и ответов

### 🎯 1. Как форма вызова определяет `this`?

У обычной функции значение `this` определяется выражением вызова. Место, где функция была создана или впервые записана в объект, само по себе не закрепляет получателя.

```js
"use strict";

function readLabel() {
  return this?.label;
}

const first = { label: "first", readLabel };
const second = { label: "second", readLabel };

console.log(first.readLabel());                    // "first"
console.log(second.readLabel());                   // "second"
console.log(readLabel());                          // undefined
console.log(readLabel.call({ label: "explicit" })); // "explicit"
```

Для интервью достаточно начать с четырёх форм:

| Форма вызова | Правило для `this` обычной функции |
|---|---|
| `fn()` | обычный вызов; в строгой функции `undefined` |
| `object.fn()` или `object[key]()` | объект непосредственно перед доступом к методу |
| `fn.call(value, ...)` / `fn.apply(value, ...)` | явно переданное значение |
| `new Constructor(...)` | создаваемый экземпляр для обычного базового конструктора |

Если вызов выглядит как `application.panel.render()`, получателем является `application.panel`, а не весь `application`. Если метод найден в прототипе, получателем всё равно остаётся объект, через который начался вызов.

Строгость определяется телом вызываемой функции. Строгий вызывающий код не превращает чужую нестрогую функцию в строгую. Тело класса и код ES-модуля работают в строгом режиме.

🧓 В нестрогой функции `null` и `undefined` в роли `this` заменяются глобальным объектом соответствующей среды выполнения (realm), а примитивы оборачиваются. Это важно узнавать в старых скриптах и задачах, но современный API не должен зависеть от такой нормализации.

### 🎯 2. Почему отделённый метод теряет контекст?

Выражение `object.method` возвращает функцию как значение. Если затем вызвать её как `callback()`, формы `object.method()` уже нет.

```js
"use strict";

const counter = {
  value: 2,
  increment(step = 1) {
    this.value += step;
    return this.value;
  },
};

const detached = counter.increment;

// Намеренно ошибочный вызов:
// detached(); // TypeError: this === undefined
```

Функция не забыла объект. Изменился вызов:

```text
counter.increment(1) → есть получатель counter
detached(1)          → обычный вызов без получателя
```

Рабочие способы выражают разное намерение:

```js
counter.increment(1);                         // сохранить вызов методом
counter.increment.call(counter, 1);          // вызвать сейчас

const bound = counter.increment.bind(counter);
bound(1);                                    // вызвать позже с закреплённым объектом

const adapter = (step) => counter.increment(step);
adapter(1);                                  // прочитать текущую привязку counter
```

Передача метода как колбэка не создаёт отдельного правила. Значение `this` определяет API, которое позже вызывает колбэк. В браузере обычный обработчик, зарегистрированный через `addEventListener`, вызывается с `this === event.currentTarget`. Это DOM-элемент, а не ваш контроллер. Подробная модель DOM-событий остаётся в 5.6.

```js
// Браузерный пример: button и controller предоставляет приложение.
const onClick = controller.handleClick.bind(controller);

button.addEventListener("click", onClick);
button.removeEventListener("click", onClick);
```

Для снятия регистрации нужна та же функция. Два вызова `bind` создают два разных объекта-функции.

### 🔬 3. Откуда стрелочная функция берёт `this`?

Стрелочная функция не создаёт собственного `this`. Чтение `this` внутри неё обращается к внешнему лексическому контексту. Объектный литерал сам по себе таким контекстом не является.

```js
function makeModel() {
  return {
    label: "object",
    regular() {
      return this.label;
    },
    arrow: () => this.label,
  };
}

const model = makeModel.call({ label: "outer" });

console.log(model.regular());                       // "object"
console.log(model.arrow());                         // "outer"
console.log(model.arrow.call({ label: "ignored" })); // "outer"
```

`call`, `apply` и `bind` могут передать стрелке аргументы, но не могут заменить её лексический `this`. Поэтому стрелка в объектном литерале обычно не подходит для метода, которому нужен текущий объект.

Стрелка внутри обычного метода может быть уместна: она читает `this` вызова внешнего метода.

```js
const queue = {
  label: "jobs",
  items: [1, 2],
  describe() {
    return this.items.map((item) => this.label + ":" + item);
  },
};

console.log(queue.describe()); // ["jobs:1", "jobs:2"]
```

Поле класса со стрелкой тоже получает лексический `this` конкретного экземпляра, но создаёт отдельную функцию для каждого экземпляра. Мы сравним это с методом прототипа в вопросе 14.

### 🎯 4. Что важно помнить про `call`, `apply` и `bind` в объектной модели?

В 1.3 эти API уже разобраны подробно. Здесь восстановим основу и посмотрим на связь с экземплярами.

| API | Когда вызывает | Как принимает аргументы после `thisArg` | Результат |
|---|---:|---|---|
| `fn.call(thisArg, a, b)` | сейчас | отдельным списком | результат функции |
| `fn.apply(thisArg, argsLike)` | сейчас | массивоподобным объектом | результат функции |
| `fn.bind(thisArg, a)` | позже | сохраняет первые аргументы | новая функция |

```js
function describe(prefix, suffix) {
  return prefix + this.label + suffix;
}

const model = { label: "A" };

console.log(describe.call(model, "[", "]"));
console.log(
  describe.apply(model, { 0: "[", 1: "]", length: 2 }),
);

const first = describe.bind(model, "[");
const second = first.bind({ label: "B" }, "]");

console.log(second.call({ label: "C" })); // "[A]"
```

`apply` принимает массивоподобный объект с индексами и `length`, а синтаксис распространения `...` в обычном вызове требует итерируемое значение. Обычный массив подходит обоим механизмам, но произвольный массивоподобный объект может не быть итерируемым.

Повторный `bind` не заменяет первый связанный `this`. Связанные аргументы накапливаются в порядке: аргументы первого `bind` → следующего `bind` → самого вызова.

Если исходную функцию можно конструировать, связанную функцию тоже можно вызвать через `new`:

```js
function Point(x, y) {
  this.x = x;
  this.y = y;
}

const ignored = { marker: true };
const OnAxis = Point.bind(ignored, 0);
const point = new OnAxis(5);

console.log(point.x, point.y); // 0 5
console.log(Object.hasOwn(ignored, "x")); // false
console.log(point instanceof Point, point instanceof OnAxis); // true true
```

При `new` связанный `thisArg` игнорируется: создание требует нового экземпляра. Связанные аргументы сохраняются. У связанной функции обычно нет собственного свойства `.prototype`, хотя она может делегировать конструирование исходной функции. Поэтому наличие `fn.prototype` не доказывает, что функцию можно вызвать через `new`.

### 🎯 5. Как сравнить основные способы создания объектов?

JavaScript не требует одного универсального способа. Сначала определите, где должно жить состояние, должны ли экземпляры разделять методы и какой контракт понятнее пользователю API.

#### Литерал объекта

Литерал создаёт новый объект при каждом вычислении. Обычный прототип — `Object.prototype`; записанные методы являются собственными перечислимыми свойствами.

```js
const counter = {
  value: 0,
  increment() {
    this.value += 1;
    return this.value;
  },
};

console.log(Object.hasOwn(counter, "increment")); // true
```

#### Фабрика

Фабрика — обычная функция, возвращающая объект. Она может использовать литерал, `Object.create`, класс или замыкание.

```js
function createCounter(initial = 0) {
  let value = initial;

  return {
    increment() {
      value += 1;
      return value;
    },
    read() {
      return value;
    },
  };
}

const first = createCounter();
const second = createCounter(10);

console.log(first.increment(), second.read()); // 1 10
console.log(first.increment === second.increment); // false
```

В этом варианте состояние закрыто в привязках каждого вызова, а методы создаются заново. Но утверждать, что любая фабрика обязательно копирует методы, нельзя: конкретная фабрика может делегировать общему прототипу или вернуть экземпляр класса.

#### Функция-конструктор

```js
function Counter(initial = 0) {
  this.value = initial;
}

Counter.prototype.increment = function increment() {
  this.value += 1;
  return this.value;
};

const first = new Counter();
const second = new Counter(10);

console.log(first.increment === second.increment); // true
console.log(Object.hasOwn(first, "increment")); // false
```

Состояние экземпляра — собственные свойства, а общий метод лежит в `Counter.prototype`.

#### `Object.create`

```js
const counterMethods = {
  increment() {
    this.value += 1;
    return this.value;
  },
};

const counter = Object.create(counterMethods);
counter.value = 0;

console.log(counter.increment()); // 1
console.log(Object.getPrototypeOf(counter) === counterMethods); // true
```

`Object.create(proto)` создаёт объект с выбранным `[[Prototype]]`, но не вызывает конструктор. Состояние нужно определить отдельно или передать вторым аргументом как дескрипторы.

#### Класс

```js
class Counter {
  constructor(initial = 0) {
    this.value = initial;
  }

  increment() {
    this.value += 1;
    return this.value;
  }
}

const first = new Counter();
const second = new Counter(10);

console.log(first.increment === second.increment); // true
```

| Подход | Типичное состояние | Типичное размещение методов | Основной компромисс |
|---|---|---|---|
| литерал | собственные поля одного объекта | собственные свойства | простота для одного объекта |
| фабрика с замыканием | закрытые привязки | функции каждого результата | ясная приватность, отдельные функции |
| функция-конструктор | собственные поля | `.prototype` | ручная организация старой модели |
| `Object.create` | явно добавленные поля | выбранный объект-прототип | прямая делегация без конструктора |
| класс | поля экземпляра, включая приватные | методы прототипа | декларативная модель экземпляров и наследования |

Выбирайте по задаче. Небольшому сервису может подойти фабрика с явными зависимостями. Множеству однотипных объектов — класс с общими методами. Композиция часто проще наследования, если нужно соединить независимые обязанности.

### 🎯 6. Что именно делает оператор `new`?

Для обычного базового конструктора полезна последовательная модель:

1. Создаётся новый объект.
2. Его `[[Prototype]]` связывается с `Constructor.prototype`.
3. Конструктор выполняется с новым объектом в роли `this`.
4. Учитывается явное возвращаемое значение конструктора.
5. Возвращается созданный объект либо явно возвращённый объект.

```js
function User(name) {
  this.name = name;
  return 10;
}

const user = new User("Ada");

console.log(user.name); // "Ada"
console.log(Object.getPrototypeOf(user) === User.prototype); // true
```

Возвращённый примитив игнорируется. Явно возвращённый объект или функция заменяет созданный экземпляр:

```js
function Replaced() {
  this.local = true;
  return { external: true };
}

const replaced = new Replaced();

console.log(replaced.external); // true
console.log(replaced.local); // undefined
console.log(replaced instanceof Replaced); // false

function CallableResult() {
  return function result() {};
}

console.log(typeof new CallableResult()); // "function"
```

Если свойство `.prototype` обычного конструктора в момент вызова не содержит объект, механизм создания использует подходящий встроенный прототип; для простого случая это `Object.prototype`.

<details>
<summary>🔬 Точная деталь: границы пяти шагов</summary>

Пять шагов — ментальная модель обычного базового конструктора, а не единый буквальный алгоритм любого `new`. Встроенные конструкторы, Proxy, связанные функции и производные классы имеют дополнительные правила.

В производном конструкторе объект и `this` подготавливаются через `super()`. Если такой конструктор явно возвращает примитив, отличный от `undefined`, возникнет `TypeError`; базовый конструктор просто игнорирует возвращённый примитив.

### 🔬 7. Какие функции можно вызвать через `new` и что показывает `new.target`?

Возможность обычного вызова и возможность конструирования — разные внутренние способности. Спецификация называет их `[[Call]]` и `[[Construct]]`.

| Вид функции | Обычный вызов | Вызов через `new` |
|---|---:|---:|
| обычное объявление или выражение функции | да | да |
| стрелочная функция | да | нет |
| краткая запись метода, getter/setter | да в своём контракте | нет |
| async function или generator function | да | нет |
| class | без `new` бросает `TypeError` | да |
| связанная функция | как исходная | только если исходную можно конструировать |

Добавить стрелочной функции обычное свойство `.prototype` недостаточно: внутреннего `[[Construct]]` у неё не появится. Генератор, напротив, может иметь `.prototype`, не являясь конструктором. Значит, проверка одного свойства ненадёжна.

```js
const Arrow = () => {};
Arrow.prototype = {};

// Намеренно ошибочный вызов:
// new Arrow(); // TypeError: Arrow is not a constructor
```

`new.target` внутри обычной функции равен `undefined` при обычном вызове и конструктору, с которого началось создание, при конструировании.

```js
function Model() {
  this.createdBy = new.target;
}

console.log(Model()); // undefined

const model = new Model();
console.log(model.createdBy === Model); // true
```

В базовом конструкторе наследника `new.target` указывает на производный класс. Это помогает механизму выбрать прототип фактически создаваемого типа. При прямом `new Bound()` связанная функция прозрачна для `new.target`: исходный конструктор видит себя, а не обёртку.

`new.target` полезен для понимания наследования и иногда для защиты функции от неправильной формы вызова. В новом API класс уже обеспечивает требование `new` яснее.

### 🎯 8. Чем `.prototype` отличается от `[[Prototype]]`?

Это два разных отношения.

- `[[Prototype]]` — внутренняя ссылка обычного объекта на следующий объект цепочки или `null`.
- `.prototype` — обычное свойство объекта-функции, которое `new` использует для будущих экземпляров.

```text
User (объект-функция)
  .prototype ───────────────→ User.prototype (обычный объект)
                                  ↑
user (экземпляр) [[Prototype]] ────┘
                                  │ [[Prototype]]
                                  ↓
                           Object.prototype → null

User [[Prototype]] → Function.prototype → Object.prototype → null
```

```js
function User(name) {
  this.name = name;
}

User.prototype.greet = function greet() {
  return "Hi " + this.name;
};

const user = new User("Ada");

console.log(Object.getPrototypeOf(user) === User.prototype); // true
console.log(Object.getPrototypeOf(User) === Function.prototype); // true
console.log(Object.hasOwn(user, "name")); // true
console.log(Object.hasOwn(user, "greet")); // false
console.log(user.greet()); // "Hi Ada"
```

Метод не был скопирован в `user`. Чтение `user.greet` нашло функцию выше по цепочке, а форма вызова `user.greet()` передала `user` как `this`.

Свойство `User.prototype` само является объектом и тоже имеет `[[Prototype]]`. У него обычно есть унаследованная связь с `Object.prototype`. Функция `User` одновременно является объектом со своей собственной цепочкой; эта цепочка не совпадает с цепочкой её экземпляров.

Методы удобно разделять через прототип. Изменяемое состояние конкретного экземпляра обычно должно быть собственным. Если записать один изменяемый массив или объект на прототип, экземпляры будут работать с общей ссылкой.

### 🎯 9. Как чтение свойства идёт по цепочке прототипов?

Для обычного чтения `object.key`:

1. Проверяется собственное свойство `key`.
2. Если его нет, поиск переходит в `[[Prototype]]`.
3. Первое найденное свойство останавливает поиск.
4. Если найден дескриптор свойства с данными, возвращается его `value`.
5. Если найден дескриптор accessor-свойства, вызывается getter с первоначальным получателем.
6. Если цепочка достигла `null`, возвращается `undefined`.

```js
const base = {
  theme: "light",
  title: "base",
};

const child = Object.create(base);
child.title = undefined;

console.log(child.theme); // "light"
console.log(child.title); // undefined
console.log(Object.hasOwn(child, "title")); // true
```

Собственное свойство со значением `undefined` всё равно найдено. Поиск не продолжает искать «более полезное» значение. Отсутствие свойства и существующее свойство со значением `undefined` нужно различать через проверку наличия.

Собственное свойство с тем же ключом **затеняет (shadows)** унаследованное:

```js
child.theme = "dark";

console.log(child.theme); // "dark"
console.log(base.theme); // "light"

delete child.theme;
console.log(child.theme); // "light"
```

Удаление собственного свойства снова открывает унаследованное. Никакого копирования при этом не происходит.

### 🎯 10. Чем присваивание отличается от чтения и определения свойства?

Обычное присваивание `receiver.key = value` не означает «найти свойство и поменять там, где оно лежит». Здесь `receiver` — объект, с которого началась операция записи.

| Что обнаружено при записи | Типичное поведение обычного объекта |
|---|---|
| собственное изменяемое свойство с данными | его значение меняется |
| унаследованное изменяемое свойство с данными | у получателя создаётся собственное свойство |
| унаследованный setter | setter вызывается с получателем в роли `this` |
| неизменяемое свойство с данными | запись отклоняется |
| accessor-свойство без setter | запись отклоняется |
| свойства нигде нет | собственное свойство создаётся, если получатель расширяемый |

```js
const base = {
  set score(value) {
    this.savedScore = value;
  },
};

const child = Object.create(base);
child.score = 7;

console.log(child.savedScore); // 7
console.log(Object.hasOwn(child, "score")); // false
console.log(Object.hasOwn(base, "savedScore")); // false
```

Setter находится на `base`, но `this` равен `child`. Поэтому он создал `savedScore` на получателе.

`Object.defineProperty(child, "score", descriptor)` — другая операция. Она определяет собственное свойство непосредственно и не вызывает унаследованный setter.

```js
Object.defineProperty(child, "score", {
  value: 9,
  writable: true,
  enumerable: true,
  configurable: true,
});

console.log(child.score); // 9
console.log(Object.hasOwn(child, "score")); // true
```

Отклонённое обычное присваивание в строгом режиме бросает `TypeError`; в нестрогом коде оно обычно ничего не меняет. `Object.defineProperty` при недопустимом определении бросает независимо от строгого режима.

Различие трёх операций понадобится ещё дважды: публичное поле класса **определяет** собственное свойство, а корректный Proxy должен сохранить получателя обычного чтения или присваивания.

### 🔬 11. Как проверить цепочку и что на самом деле означает `instanceof`?

`Object.getPrototypeOf(object)` возвращает непосредственный `[[Prototype]]`. `prototypeObject.isPrototypeOf(object)` проверяет, встречается ли этот объект где-то в цепочке, а не только на первом шаге.

```js
function User() {}

const user = new User();

console.log(Object.getPrototypeOf(user) === User.prototype); // true
console.log(User.prototype.isPrototypeOf(user)); // true
console.log(user instanceof User); // true
console.log(Object.create(User.prototype) instanceof User); // true
```

Последняя строка важна: успешный `instanceof` не доказывает, что конструктор выполнялся. В обычном случае оператор ищет **текущее** `Constructor.prototype` в цепочке объекта.

Ловушки:

- после замены `.prototype` старые экземпляры сохраняют прежнюю цепочку и могут перестать проходить проверку;
- встроенные конструкторы из разных сред выполнения (realms) имеют разные прототипы, поэтому массив из `iframe` может не пройти `instanceof Array`; для массива существует `Array.isArray`;
- правая сторона без возможности обычного вызова или подходящего контракта `Symbol.hasInstance` приводит к `TypeError`;
- `Symbol.hasInstance` может переопределить смысл проверки;
- связанная функция делегирует стандартную проверку исходной функции.

Свойство `constructor` не является надёжной проверкой типа. Обычно экземпляр наследует его из объекта `.prototype`, но это обычное изменяемое свойство.

```js
function User() {}

User.prototype = {
  greet() {
    return "hello";
  },
};

const user = new User();

console.log(user.constructor === User); // false
console.log(user.constructor === Object); // true
```

Его можно удалить, затенить или потерять при замене прототипа. Для внешних данных проверяйте нужную структуру и значения. Для собственных объектов выбирайте `instanceof`, проверку приватной метки или явный признак типа только с пониманием реальной гарантии.

### 🎯 12. Зачем нужен `Object.create(null)` и чем `__proto__` отличается от `[[Prototype]]`?

`Object.create(null)` создаёт объект, у которого `[[Prototype]]` равен `null`. На нём нет унаследованных `toString`, `hasOwnProperty` и исторического accessor-свойства `__proto__`.

```js
const dictionary = Object.create(null);

dictionary.toString = "stored";
dictionary["__proto__"] = "ordinary key";

console.log(Object.getPrototypeOf(dictionary)); // null
console.log(Object.hasOwn(dictionary, "toString")); // true
console.log(dictionary["__proto__"]); // "ordinary key"
```

Такой объект удобен как простой словарь без столкновений с именами `Object.prototype`. Он не превращается в универсальную защиту при объединении недоверенных данных. Защита от загрязнения прототипа (prototype pollution) относится к 11.5, а сравнение с `Map` — к 1.6.

🧓 `__proto__` — историческое accessor-свойство на `Object.prototype`, а не имя внутреннего слота. У объекта без прототипа это свойство не наследуется; собственное свойство с таким именем тоже может его скрыть.

Для чтения используйте `Object.getPrototypeOf`, для осознанного изменения — `Object.setPrototypeOf`. Обычно лучше сразу создать правильную цепочку через `Object.create` или `class extends`. Динамическая смена прототипа усложняет модель доступных методов и может нарушить оптимизации движка; точную стоимость нужно измерять в конкретном коде.

`Object.setPrototypeOf` не копирует свойства и не выполняет конструктор. Циклическая цепочка обычных объектов запрещена. У нерасширяемого объекта нельзя установить другой прототип, хотя повторная установка того же значения допустима.

🔬 Запись `{ __proto__: proto }` в литерале — специальный стандартизованный синтаксис установки прототипа. Вычисляемый ключ `{ ["__proto__"]: value }` создаёт обычное собственное свойство. Эти две записи не следует смешивать с унаследованным accessor-свойством.

### 🎯 13. Что класс добавляет к прототипной модели?

Класс организует создание экземпляров и общее поведение декларативно. Но фраза «класс — только сахар над функцией» слишком грубая: имя класса, вызов без `new`, строгий режим и дескрипторы методов имеют собственные правила.

```js
class User {
  constructor(name) {
    this.name = name;
  }

  greet() {
    return "Hi " + this.name;
  }
}

const user = new User("Ada");

console.log(Object.getPrototypeOf(user) === User.prototype); // true
console.log(Object.hasOwn(user, "name")); // true
console.log(Object.hasOwn(user, "greet")); // false
console.log(
  Object.getOwnPropertyDescriptor(User.prototype, "greet").enumerable,
); // false

// Намеренно ошибочный вызов:
// User("Ada"); // TypeError: class constructor cannot be called without new
```

Обычные методы экземпляра находятся в `User.prototype` и являются неперечисляемыми. Они не привязаны к экземпляру автоматически: отделённый `user.greet` всё ещё потеряет получателя.

Объявление класса создаёт лексическую привязку. До инициализации имени действует TDZ:

```js
// Намеренно ошибочное раннее чтение:
// new Before(); // ReferenceError

class Before {}
```

Выражение класса вычисляется в своей позиции. Именованное выражение получает внутреннее имя, доступное внутри тела класса, но не создаёт обычную внешнюю привязку с этим именем.

```js
const Named = class Internal {
  static identity() {
    return Internal;
  }
};

console.log(Named.identity() === Named); // true
console.log(typeof Internal); // "undefined"
```

Всё тело класса строгое. Это влияет, например, на `this` отделённого метода и ошибки записи в неизменяемые свойства.

### 🎯 14. Чем метод прототипа отличается от функции в поле экземпляра?

Три похожие записи создают разное размещение и разный `this`:

```js
class Counter {
  value = 0;

  increment() {
    this.value += 1;
    return this.value;
  }

  callback = () => this.increment();

  dynamic = function dynamic() {
    return this.value;
  };
}

const first = new Counter();
const second = new Counter();

console.log(first.increment === second.increment); // true
console.log(first.callback === second.callback); // false
console.log(Object.keys(first)); // ["value", "callback", "dynamic"]

const callback = first.callback;
console.log(callback()); // 1
console.log(first.dynamic.call({ value: 9 })); // 9
```

| Форма | Где находится | Функция общая? | Как получает `this` | Перечислимая? |
|---|---|---:|---|---:|
| `method() {}` | в прототипе | да | по форме вызова | нет |
| `field = () => ...` | собственное поле | нет | лексический `this` экземпляра | да |
| `field = function () {}` | собственное поле | нет | по форме вызова | да |

Публичное поле экземпляра создаётся как собственное изменяемое, перечислимое и конфигурируемое свойство. Стрелочное поле удобно для устойчивого колбэка, но каждый экземпляр получает отдельную функцию. Это влияет на память, идентичность функции, подмену в тестах и переопределение поведения. Выбор зависит от API, а не от правила «все обработчики должны быть стрелочными полями».

Поля **определяются**, а не присваиваются через унаследованный setter:

```js
class Base {
  set value(next) {
    this.seen = next;
  }
}

class Field extends Base {
  value = 1;
}

class Assignment extends Base {
  constructor() {
    super();
    this.value = 1;
  }
}

console.log(new Field().seen); // undefined
console.log(new Assignment().seen); // 1
```

Стандартная семантика поля использует определение собственного свойства и не вызывает setter базы. Старые режимы транспиляции могли преобразовывать поле в присваивание и вести себя иначе; при расследовании унаследованного кода проверяйте фактический результат сборки.

### 🎯 15. Как `extends` и `super` связывают классы?

`class Admin extends User` создаёт две связанные цепочки:

```text
admin → Admin.prototype → User.prototype → Object.prototype → null

Admin → User → Function.prototype → Object.prototype → null
```

Первая даёт наследование методов экземпляра. Вторая позволяет наследовать публичные статические элементы.

```js
class User {
  constructor(name) {
    this.name = name;
  }

  greet() {
    return "Hi " + this.name;
  }

  static kind = "user";
}

class Admin extends User {
  constructor(name, role) {
    super(name);
    this.role = role;
  }

  greet() {
    return super.greet() + " / " + this.role;
  }
}

const admin = new Admin("Ada", "admin");

console.log(admin.greet()); // "Hi Ada / admin"
console.log(Admin.kind); // "user"
console.log(Object.getPrototypeOf(Admin) === User); // true
```

В производном конструкторе `this` не инициализирован до `super()`:

```js
class Base {}

class Broken extends Base {
  constructor() {
    // Намеренно ошибочная строка:
    // this.ready = true; // ReferenceError
    super();
    this.ready = true;
  }
}
```

`super()` запускает базовый конструктор и подготавливает создаваемый экземпляр. После него инициализируются поля производного класса, затем продолжается тело производного конструктора. Поля базового экземпляра инициализируются до выполнения тела базового конструктора.

Отсюда следует практическая ловушка: базовый конструктор не должен рассчитывать, что поля наследника уже готовы, если он вызывает переопределяемый метод.

`super.greet()` начинает поиск в базовом прототипе, но вызывает найденный метод с **текущим `this`**. Отдельного «родительского экземпляра» нет.

<details>
<summary>🔬 Точная деталь: `super` связан с местом определения метода</summary>

Начальная точка поиска `super` связана с объектом, где метод был определён, через внутренний `[[HomeObject]]`. Получатель вызова остаётся текущим `this`. Если заимствовать метод через `call`, меняется получатель, но не начальная точка поиска `super`.

Производный конструктор может в редком случае вернуть объект, не используя `this` и не вызывая `super()`. Это исключение не меняет рабочее правило: обычный наследник сначала вызывает `super()`, затем инициализирует своё состояние.

</details>

### 🔬 16. Где находятся статические и приватные элементы?

Статический метод находится на объекте-конструкторе. Статическое публичное поле — собственное свойство этого объекта.

```js
class Model {
  static version = 1;

  static describe() {
    return this.version;
  }

  id = 7;
}

console.log(Model.describe()); // 1
console.log(new Model().version); // undefined
console.log(Object.keys(Model)); // ["version"]
```

Статические методы обычно неперечисляемы, а публичные статические поля перечислимы.

Приватный элемент с `#` не является обычным свойством со строковым ключом или ключом Symbol. Его нельзя увидеть через `Object.keys`, `Reflect.ownKeys` или дескрипторы.

```js
class Counter {
  #value = 0;

  #validate(step) {
    if (!Number.isInteger(step)) {
      throw new TypeError("step must be an integer");
    }
  }

  increment(step = 1) {
    this.#validate(step);
    this.#value += step;
    return this.#value;
  }

  read() {
    return this.#value;
  }

  static isCounter(value) {
    return value !== null &&
      (typeof value === "object" || typeof value === "function") &&
      #value in value;
  }
}

const counter = new Counter();

console.log(counter.increment(), counter.read()); // 1 1
console.log(Reflect.ownKeys(counter)); // []
console.log(Counter.isCounter(counter)); // true
console.log(Counter.isCounter(Object.create(Counter.prototype))); // false
```

Доступ проверяет, что конкретный объект действительно несёт нужный приватный элемент. Это **проверка приватной метки (private brand check)**. Одного совпадения прототипа недостаточно.

Отделённый метод можно вызвать с настоящим экземпляром через `call`, но объект-имитация не пройдёт проверку приватной метки:

```js
const read = counter.read;

console.log(read.call(counter)); // 1

// Намеренно ошибочный вызов:
// read.call({}); // TypeError
```

Приватный метод не стоит описывать как обычное свойство прототипа: внешние API работы со свойствами его не видят.

При `new Child()` базовый конструктор инициализирует свои приватные элементы на том же объекте. Поэтому унаследованные публичные методы базы могут работать. Но код наследника не получает лексический доступ к имени `#value` базы.

```js
class Base {
  #value = 1;

  readBase() {
    return this.#value;
  }
}

class Child extends Base {
  #value = 2;

  readChild() {
    return this.#value;
  }
}

const child = new Child();
console.log(child.readBase(), child.readChild()); // 1 2
```

Приватные статические элементы принадлежат конкретному объекту класса и не наследуются как обычные публичные статические свойства.

```js
class StaticBase {
  static #value = 1;

  static safeRead() {
    return StaticBase.#value;
  }

  static dynamicRead() {
    return this.#value;
  }
}

class StaticChild extends StaticBase {}

console.log(StaticChild.safeRead()); // 1

// Намеренно ошибочный вызов:
// StaticChild.dynamicRead(); // TypeError: у StaticChild нет StaticBase.#value
```

Если `#name` вообще не объявлено в доступной лексической области класса, код получает `SyntaxError` ещё до выполнения. Если имя объявлено, но получатель не имеет нужной приватной метки, возникает `TypeError` во время выполнения.

### 🎯 17. Когда композиция проще наследования?

Наследование удобно, когда наследник действительно поддерживает контракт базы, а отношение стабильно. Оно становится хрупким, если:

- база вызывает переопределяемые методы до готовности наследника;
- наследник зависит от внутреннего порядка инициализации базы;
- несколько независимых обязанностей требуют глубокой иерархии;
- замена одной стратегии заставляет создавать ещё один подкласс;
- тесту приходится собирать большой объект только ради одной операции.

Композиция передаёт зависимости явно:

```js
function createReportService({ loadData, formatReport, saveReport }) {
  return {
    async run(id) {
      const data = await loadData(id);
      const report = formatReport(data);
      await saveReport(report);
      return report;
    },
  };
}
```

Здесь нет абстрактного базового класса. Три операции можно менять и проверять независимо. Если общий жизненный цикл и инварианты экземпляра действительно важны, класс остаётся хорошим выбором.

Полезный вопрос на интервью:

> Наследование выражает настоящую модель «является разновидностью» и общий контракт, или используется только ради повторного использования нескольких функций?

Выбор между фабрикой и классом тоже не решается лозунгом. Фабрика удобна для закрытого состояния и явных зависимостей; класс — для множества экземпляров, общего поведения, `instanceof`, приватных элементов и знакомого жизненного цикла. Измеряйте реальную стоимость только при наличии проблемы, а сначала выбирайте понятный API.

### 🎯 18. Как разделить собственные и унаследованные, перечислимые и неперечислимые свойства?

У обычного свойства есть ключ: строка или Symbol. Две независимые оси описывают его положение и участие в некоторых видах перебора.

- **Собственное (own)** свойство находится на самом объекте.
- **Унаследованное (inherited)** находится выше в цепочке прототипов.
- **Перечислимое (enumerable)** учитывается API, которые перечисляют именно такие свойства.
- **Неперечислимое (non-enumerable)** пропускается такими API, но остаётся доступным.

| | Перечислимое | Неперечислимое |
|---|---|---|
| собственное | обычное поле литерала или экземпляра | свойство, определённое с `enumerable: false` |
| унаследованное | метод обычного объекта-прототипа | обычный метод прототипа класса |

Ни одна ячейка не означает приватность.

```js
const token = Symbol("token");
const base = { inherited: 1 };
const object = Object.create(base);

object.visible = 2;
object[token] = 3;

Object.defineProperty(object, "hidden", {
  value: 4,
});

console.log(Object.hasOwn(object, "inherited")); // false
console.log("inherited" in object); // true
console.log(Object.keys(object)); // ["visible"]
console.log(Object.getOwnPropertyNames(object)); // ["visible", "hidden"]
console.log(Reflect.ownKeys(object)); // ["visible", "hidden", token]
```

`Object.hasOwn(object, key)` проверяет только собственное свойство. `key in object` проверяет всю цепочку. Оба возвращают `true`, если свойство присутствует со значением `undefined`.

Прямой вызов `object.hasOwnProperty(key)` ненадёжен:

- метод может быть затенён собственным полем;
- у объекта с `null`-прототипом его нет;
- объект может быть Proxy с неожиданным поведением получения свойства.

Современный вариант — `Object.hasOwn`. Для старой среды важно узнавать `Object.prototype.hasOwnProperty.call(object, key)`.

Ключ Symbol помогает избежать случайного столкновения со строковым именем, но не делает данные секретными: `Reflect.ownKeys` и `Object.getOwnPropertySymbols` их видят. Настоящие приватные поля используют иной механизм.

### 🎯 19. Как выбирать API проверки и перечисления?

Перед выбором ответьте на три вопроса:

1. Нужны только собственные свойства или также унаследованные?
2. Нужны все свойства или только перечислимые?
3. Нужны строковые ключи, ключи Symbol или оба вида?

| API | Собственные | Унаследованные | Только перечислимые | Строки | Symbol | Читает значения |
|---|---:|---:|---:|---:|---:|---:|
| `Object.hasOwn` | да | нет | нет | да | да | нет |
| `hasOwnProperty.call` | да | нет | нет | да | да | нет |
| `in` | да | да | нет | да | да | нет |
| `Object.keys` | да | нет | да | да | нет | нет |
| `Object.values` / `entries` | да | нет | да | да | нет | да |
| `for...in` | да | да | да | да | нет | сам перебор — нет |
| `Object.getOwnPropertyNames` | да | нет | нет | да | нет | нет |
| `Object.getOwnPropertySymbols` | да | нет | нет | нет | да | нет |
| `Reflect.ownKeys` | да | нет | нет | да | да | нет |

`for...in` может увидеть унаследованный перечислимый ключ:

```js
const base = { inherited: 1 };
const object = Object.create(base);
object.own = 2;

const keys = [];

for (const key in object) {
  keys.push(key);
}

console.log(keys); // ["own", "inherited"]
```

Если нужны только собственные свойства, фильтруйте через `Object.hasOwn` или сразу выбирайте `Object.keys` / `entries`. Обычный `for...of` использует протокол итерации и относится к 1.6.

Точная ловушка: собственное неперечислимое свойство может скрыть от `for...in` унаследованное перечислимое свойство с тем же именем. Перебор не равен простому объединению ключей каждого уровня.

`Object.values` и `Object.entries` получают значения и поэтому могут вызвать getter. `Object.keys` для обычного объекта только собирает ключи и getter значений не вызывает. Proxy может выполнить перехватчики даже при запросе ключей и дескрипторов, поэтому перебор сложной обёртки не гарантированно свободен от побочных эффектов.

### 🎯 20. Что описывает дескриптор свойства?

Дескриптор свойства задаёт вид свойства и разрешённые операции.

| Дескриптор свойства с данными | Дескриптор accessor-свойства | Общие флаги |
|---|---|---|
| `value` — сохранённое значение | `get` — функция чтения либо `undefined` | `enumerable` |
| `writable` — разрешена ли запись нового значения | `set` — функция записи либо `undefined` | `configurable` |

Один дескриптор не может одновременно содержать `value`/`writable` и `get`/`set`. Попытка смешать виды бросает `TypeError`. Getter и setter должны быть функциями или `undefined`.

```js
const object = {};

Object.defineProperty(object, "id", {
  value: 7,
});

console.log(Object.getOwnPropertyDescriptor(object, "id"));
// {
//   value: 7,
//   writable: false,
//   enumerable: false,
//   configurable: false
// }

console.log(Object.keys(object)); // []
```

Для **нового свойства** пропущенные флаги `Object.defineProperty` равны `false`; пропущенный `value` равен `undefined`. Это частая ловушка: обычное присваивание и свойство литерала обычно создают флаги `true`.

```js
Object.defineProperties(object, {
  name: {
    value: "Ada",
    writable: true,
    enumerable: true,
    configurable: true,
  },
  rank: {
    value: 3,
    enumerable: true,
  },
});

console.log(Object.keys(object)); // ["name", "rank"]
```

`Object.getOwnPropertyDescriptor` читает один собственный дескриптор. `Object.getOwnPropertyDescriptors` возвращает дескрипторы всех собственных строковых ключей и ключей Symbol. Эти API не идут по прототипу и не вызывают getter обычного accessor-свойства.

При переопределении **существующего** свойства пропущенные поля не сбрасываются автоматически: текущие атрибуты используются как основа. Правило «по умолчанию false» описывает создание нового свойства.

`configurable: false` вводит ограничения, но не всегда немедленно делает значение неизменяемым. У неконфигурируемого свойства с данными и `writable: true` ещё можно менять `value` и один раз перевести `writable` в `false`. Обратно включить запись или сменить вид свойства уже нельзя.

`Object.defineProperties` сначала преобразует переданные описания, затем выполняет определения. Но если фактическое определение одного из последующих свойств завершится ошибкой, это не следует воспринимать как универсальную транзакцию с откатом уже сделанных изменений.

Дескрипторы полезны для библиотек, вычисляемых свойств, слоёв совместимости и точных ограничений записи. В прикладном коде явные методы `readValue` / `updateValue` часто проще искать, логировать и тестировать.

### 🎯 21. Как getter и setter используют получателя операции?

Getter превращает чтение свойства в вызов функции. Setter перехватывает присваивание. Их `this` определяется получателем операции, а не обязательно объектом, где найден дескриптор.

```js
const orderModel = {
  get total() {
    return this.price * this.quantity;
  },

  set total(value) {
    this.price = value / this.quantity;
  },
};

const order = Object.create(orderModel);
order.price = 5;
order.quantity = 2;

console.log(order.total); // 10

order.total = 20;

console.log(order.price); // 10
console.log(Object.hasOwn(order, "total")); // false
```

Accessor-свойство найдено на `orderModel`, но получатель — `order`, потому что чтение началось как `order.total`.

Getter может иметь побочный эффект, бросать ошибку или выполнять дорогую работу. Синтаксис свойства не делает операцию бесплатной. Хороший контракт вычисляемого свойства:

- чтение предсказуемо;
- стоимость ограничена и понятна;
- нет неожиданной сети или длительной записи;
- ошибки соответствуют смыслу свойства;
- setter проверяет входные данные.

Если операции нужны параметры, длительный эффект, явный результат либо сложная обработка ошибки, именованный метод обычно яснее.

`Reflect.get(target, key, receiver)` позволяет явно разделить начало поиска и получателя:

```js
const base = {
  get label() {
    return this.name;
  },

  set label(value) {
    this.name = value;
  },
};

const receiver = { name: "Ada" };

console.log(Reflect.get(base, "label", receiver)); // "Ada"
console.log(Reflect.set(base, "label", "Lin", receiver)); // true
console.log(receiver.name); // "Lin"
console.log(Object.hasOwn(base, "name")); // false
```

Без третьего аргумента получателем является исходный объект. `Reflect.set` возвращает логическое значение, сообщающее об успехе обычной записи. Исключение, брошенное телом setter, всё равно распространяется.

### 🎯 22. Чем `preventExtensions`, `seal` и `freeze` отличаются?

Три уровня целостности усиливают ограничения:

- `Object.preventExtensions(object)` запрещает добавлять собственные свойства;
- `Object.seal(object)` дополнительно делает собственные свойства неконфигурируемыми;
- `Object.freeze(object)` дополнительно делает собственные свойства с данными неизменяемыми.

Они возвращают тот же объект. Состояние проверяют `Object.isExtensible`, `Object.isSealed` и `Object.isFrozen`.

| Операция с обычным объектом | preventExtensions | seal | freeze |
|---|---|---|---|
| добавить собственное свойство | нельзя | нельзя | нельзя |
| удалить конфигурируемое собственное свойство | можно | нельзя | нельзя |
| изменить дескриптор | по прежним разрешениям | только совместимые с неконфигурируемым свойством | только совместимые с неконфигурируемым и неизменяемым свойством |
| изменить значение изменяемого свойства с данными | можно | можно | нельзя |
| вызвать существующий setter | можно | можно | можно |
| изменить вложенный изменяемый объект | можно | можно | можно |

Матрица предполагает прежние разрешения свойства: `seal` не превращает свойство только для чтения в изменяемое. После запрета расширения нельзя сменить прототип на другой.

```js
"use strict";

const nested = { count: 0 };
const frozen = Object.freeze({
  nested,
  title: "fixed",
});

nested.count += 1;

console.log(frozen.nested.count); // 1
console.log(Object.isFrozen(frozen)); // true
console.log(Object.isFrozen(nested)); // false

// Намеренно ошибочные операции:
// frozen.title = "changed"; // TypeError
// frozen.extra = 1;         // TypeError
// delete frozen.title;     // TypeError
```

Операции поверхностные: они ограничивают собственные свойства именно этого объекта. Вложенный объект остаётся изменяемым, если его отдельно не ограничили. Это связь с общими ссылками из 1.2, а не начало темы глубокого копирования.

`const` и `freeze` отвечают на разные вопросы:

- `const` запрещает перенаправить привязку имени;
- `freeze` ограничивает свойства конкретного объекта;
- глубокая неизменяемость — более широкий контракт о достижимых данных и владении ими.

В нестрогом коде некоторые отклонённые присваивания или удаления молча не срабатывают. В строгом режиме они бросают `TypeError`. `Object.defineProperty` при нарушении ограничений бросает всегда; соответствующий `Reflect.defineProperty` обычно возвращает `false` при обычном отказе.

### 🔬 23. Почему замороженный объект всё ещё может менять наблюдаемое состояние?

`freeze` фиксирует дескрипторы, а не отключает код accessor-свойств и не замораживает лексические привязки.

```js
let saved = 0;

const object = Object.freeze({
  get value() {
    return saved;
  },

  set value(next) {
    saved = next;
  },
});

object.value = 7;

console.log(object.value); // 7
console.log(Object.isFrozen(object)); // true
```

Дескриптор accessor-свойства нельзя удалить или заменить, но setter остаётся исполняемым кодом.

Приватные поля класса не являются обычными свойствами, поэтому `freeze` их тоже не делает неизменяемыми:

```js
class Counter {
  #value = 0;

  increment() {
    this.#value += 1;
    return this.#value;
  }
}

const counter = Object.freeze(new Counter());

console.log(counter.increment()); // 1
console.log(Object.isFrozen(counter)); // true
```

Встроенные объекты могут хранить состояние во внутренних слотах. Например, заморозка объекта `Map` не превращает содержимое коллекции в неизменяемую модель данных. Обещание неизменяемости должно учитывать конкретный тип и допустимые методы, а не только результат `Object.isFrozen`.

Глубокая заморозка требует отдельного контракта: обход графа, обработка циклов, решение по классам, accessor-свойствам, встроенным объектам и объектам окружения. Она не относится к этому разделу и не должна автоматически подменять архитектуру владения данными.

### 🔬 24. Что Proxy перехватывает и зачем рядом Reflect?

Proxy создаёт объект-обёртку, который может перехватывать фундаментальные операции над другим объектом.

- **исходный объект (target)** — объект, к которому в итоге обращается операция;
- **обработчик (handler)** — объект с функциями-перехватчиками;
- **перехватчик (trap)** — функция для конкретной внутренней операции;
- **получатель (receiver)** — объект, с которого началось чтение или присваивание.

```text
чтение proxy.key
  → внутренний [[Get]] Proxy
    → handler.get(target, key, receiver)
      → Reflect.get(target, key, receiver)
        → обычный поиск / getter исходного объекта
```

Перехватчик связан с операцией, а не только с одним синтаксисом. Например, перечисление может запросить собственные ключи, а затем дескрипторы. Один `get` не становится универсальным наблюдателем любого взаимодействия.

| Операция | Перехватчик | Стандартное перенаправление |
|---|---|---|
| чтение / запись | `get` / `set` | `Reflect.get` / `Reflect.set` |
| проверка / удаление | `has` / `deleteProperty` | `Reflect.has` / `Reflect.deleteProperty` |
| собственные ключи | `ownKeys` | `Reflect.ownKeys` |
| дескриптор / определение | `getOwnPropertyDescriptor` / `defineProperty` | одноимённые методы Reflect |
| прототип | `getPrototypeOf` / `setPrototypeOf` | одноимённые методы Reflect |
| расширяемость | `isExtensible` / `preventExtensions` | одноимённые методы Reflect |
| вызов / конструирование функции | `apply` / `construct` | `Reflect.apply` / `Reflect.construct` |

Если перехватчик отсутствует, Proxy делегирует операцию исходному объекту. Proxy вокруг функции не получает `[[Call]]` или `[[Construct]]`, которых нет у исходной функции.

```js
const target = { count: 0 };

const proxy = new Proxy(target, {
  set(target, key, value, receiver) {
    if (key === "count" && (!Number.isInteger(value) || value < 0)) {
      throw new RangeError("count must be a non-negative integer");
    }

    return Reflect.set(target, key, value, receiver);
  },
});

proxy.count = 2;

console.log(target.count); // 2
```

`Reflect.get` и `Reflect.set` помогают выполнить соответствующую стандартную операцию и сохранить получателя. Они не «снимают» Proxy автоматически. Если внутри `get` вызвать `Reflect.get(proxy, ...)` на той же обёртке, перехватчик может вызвать себя снова и уйти в бесконечную рекурсию. Для обычного перенаправления используют полученный `target`.

`set` должен сообщить об успехе. Если перехватчик фактически изменил исходный объект, но забыл вернуть результат, он вернёт `undefined`. В строгом режиме присваивание может после этого бросить `TypeError`. Изменение исходного объекта не откатывается автоматически.

`Reflect.apply(fn, thisArg, argsList)` явно выполняет функцию. `Reflect.construct(Constructor, argsList, newTarget?)` явно выполняет конструирование и при необходимости отделяет исполняемый конструктор от типа, чей prototype будет использован. Для обычного приложения это чаще инструмент инфраструктуры, чем повседневная замена `fn()` или `new`.

### 🔬 25. Почему получатель и идентичность мешают полной прозрачности Proxy?

Корректное перенаправление сохраняет получателя:

```js
const target = {
  get label() {
    return this.name;
  },
};

const proxy = new Proxy(target, {
  get(target, key, receiver) {
    return Reflect.get(target, key, receiver);
  },
});

const child = Object.create(proxy);
child.name = "child";

console.log(child.label); // "child"
```

Если заменить перенаправление на `target[key]`, getter получит `this === target` и потеряет первоначальный `child`. Тот же принцип важен для `Reflect.set`: запись через унаследованный setter или свойство с данными должна учитывать получателя.

Но даже правильный получатель не делает обёртку тождественной исходному объекту:

```js
console.log(proxy === target); // false

const map = new Map();
map.set(target, "target");

console.log(map.get(proxy)); // undefined
```

Proxy и исходный объект — разные ключи для `Map`/`WeakMap`, разные значения для `===` и разные участники внешних реестров. Прямое изменение исходного объекта обходит перехватчики обёртки. Если исходный объект остаётся доступен, Proxy сам по себе не создаёт надёжную границу безопасности.

Приватные поля и внутренние слоты принадлежат исходному объекту, а не Proxy:

```js
class Counter {
  #value = 1;

  read() {
    return this.#value;
  }
}

const targetCounter = new Counter();
const proxiedCounter = new Proxy(targetCounter, {});

console.log(targetCounter.read()); // 1

// Намеренно ошибочный вызов:
// proxiedCounter.read(); // TypeError: у Proxy нет #value
```

Похожая ошибка возникает при вызове методов `Map`, `Set`, `Date` и других встроенных объектов, которые требуют внутренний слот на `this`. Иногда перехватчик `get` привязывает метод к исходному объекту, но это меняет получателя, создаёт вопросы идентичности функции и может обходить наблюдение. Универсальной «полностью прозрачной» обёртки так не получается.

Если нужно предоставить несколько известных операций объекта с приватным или встроенным состоянием, явный адаптер или обёртка часто честнее:

```js
function createCounterView(counter) {
  return {
    read: () => counter.read(),
  };
}
```

### 🔬 26. Что ограничивают инварианты Proxy и как работает отзываемый Proxy?

Перехватчик не может противоречить некоторым уже установленным гарантиям исходного объекта. Эти правила называют **инвариантами Proxy (Proxy invariants)**.

```js
const target = {};

Object.defineProperty(target, "id", {
  value: 7,
  writable: false,
  configurable: false,
});

const liar = new Proxy(target, {
  get() {
    return 99;
  },
});

// Намеренно ошибочное чтение:
// console.log(liar.id); // TypeError
```

Для интервью достаточно понимать общий смысл и несколько примеров:

- `get` не может подменить значение собственного неконфигурируемого и неизменяемого свойства с данными;
- `set` не может честно объявить успешной несовместимую запись в такое свойство;
- неконфигурируемое accessor-свойство без getter не может читаться как произвольное значение;
- `ownKeys` обязан включить все собственные неконфигурируемые ключи и не может содержать дубликаты;
- для нерасширяемого исходного объекта результат `ownKeys` должен совпасть со всеми собственными ключами;
- `getPrototypeOf` не может сообщить другой прототип для нерасширяемого исходного объекта;
- `isExtensible` должен согласовываться с исходным объектом.

Это не полный перечень условий всех перехватчиков. Главная модель: язык проверяет Proxy на соответствие необратимым гарантиям исходного объекта и при противоречии бросает `TypeError`.

`Proxy.revocable` создаёт обёртку с управляемым сроком жизни:

```js
const { proxy, revoke } = Proxy.revocable(
  { label: "active" },
  {},
);

console.log(proxy.label); // "active"

revoke();

// Намеренно ошибочная операция после revoke:
// proxy.label; // TypeError

console.log(typeof proxy); // "object"
```

После `revoke()` операции, проходящие через внутренние методы Proxy, бросают `TypeError`. Отзыв не уничтожает исходный объект, не отменяет значения, уже переданные наружу, и не перехватывает `typeof` или само сравнение идентичности.

Отзываемый Proxy полезен, когда доступ к виртуализированному объекту должен действовать лишь до закрытия сессии или разрешения. Но если наружу уже ушли ссылки на исходный объект или его изменяемые части, отзыв обёртки не вернёт их обратно.

### 🎯 27. Как выбрать между обычным объектом, классом, дескриптором и Proxy?

Начните с самого явного контракта, который решает задачу.

| Требование | Разумная отправная точка | Что проверить |
|---|---|---|
| один объект с несколькими полями | литерал | кто владеет состоянием и как вызываются методы |
| небольшой сервис с закрытым состоянием | фабрика | время жизни замыканий и независимость экземпляров |
| много объектов с общим поведением | класс + методы прототипа | собственное состояние, приватные инварианты, поля-функции |
| делегация выбранному объекту | `Object.create` | стабильная цепочка; конструктор не выполнялся |
| вычисляемая характеристика | getter или именованный метод | стоимость и побочные эффекты |
| ограничение одного свойства | дескриптор | явные флаги и ясность для читателя |
| проверка нескольких известных операций | явные функции / обёртка | контракт ошибок и тестируемость |
| общий перехват операций со свойствами | Proxy + Reflect | получатель, инварианты, идентичность, доступность исходного объекта |

Реалистичные применения Proxy:

- наблюдение за доступом в библиотечной инфраструктуре;
- валидация записей по общему правилу;
- виртуальные или ленивые свойства;
- API с отзывом доступа;
- внутренние механизмы фреймворков.

Если нужно проверить два известных метода записи, обычный класс или обёртка обычно понятнее. Если getter запускает сетевой запрос, лучше именованный асинхронный метод. Если наследование связывает независимые обязанности, композиция снижает скрытую связанность.

Proxy добавляет вызовы на пути операций, усложняет трассировку и может мешать оптимизациям. Нельзя честно обещать универсальное «медленнее в N раз»: измеряйте конкретный горячий путь. При ревью кода сначала важнее проверить корректность, идентичность объектов и удобство отладки.

## Ловушки на интервью

### Найденное `undefined` останавливает поиск

Отсутствующее свойство и существующее свойство со значением `undefined` различаются. Проверяйте наличие отдельно от значения.

### Getter находится выше, а получатель остаётся внизу

Всегда называйте два объекта: где найден дескриптор и кто начал операцию.

### Публичное поле и присваивание используют разные операции

Поле определяет собственное свойство и не вызывает setter базы; `this.value = ...` может его вызвать.

### Замороженное accessor-свойство может менять внешнее состояние

`freeze` фиксирует дескриптор. Тело setter остаётся кодом, а приватное или внутреннее состояние не превращается в обычное замороженное свойство.

### Proxy может изменить исходный объект и всё равно закончить запись ошибкой

Перехватчик `set` должен вернуть логическое значение. Ошибка после `false` не является транзакционным откатом.

## Как объяснить тему на интервью за 30–60 секунд

### `this` и потеря контекста

> У обычной функции я определяю `this` по форме вызова: обычный вызов, вызов через объект, явный `call`/`apply` или `new`. Запись функции в объект не привязывает её навсегда. При отделении метода исчезает форма `object.method()`, поэтому колбэку нужен сохранённый результат `bind`, стрелочный адаптер или явный аргумент. Стрелочная функция не создаёт собственного `this` и читает внешний контекст.

### `new`, `.prototype` и `[[Prototype]]`

> Для обычного базового конструктора `new` создаёт объект, связывает его внутренний прототип с `Constructor.prototype` и вызывает конструктор с новым `this`. Возвращённый примитив игнорируется, а возвращённый объект заменяет результат. `.prototype` — обычное свойство конструктора для будущих экземпляров; `[[Prototype]]` — внутренняя ссылка конкретного объекта. Прототипные методы не копируются: поиск находит их выше, а вызов через экземпляр передаёт его как `this`.

### Класс и наследование

> Класс организует прототипную модель: поля находятся на экземпляре, обычные методы — в прототипе, статические элементы — на объекте-конструкторе. Класс требует `new`, его тело строгое, а имя до инициализации находится во временной мёртвой зоне (TDZ). `extends` связывает цепочки экземпляров и конструкторов. В производном конструкторе `super()` инициализирует `this`; `super.method()` начинает поиск в базе, но вызывает метод с текущим экземпляром.

### Свойства и дескрипторы

> Собственность и перечисляемость — независимые признаки. `Object.hasOwn` проверяет собственное свойство, `in` — всю цепочку, `Object.keys` возвращает собственные перечислимые строковые ключи, а `Reflect.ownKeys` — все собственные ключи. Дескриптор описывает свойство с данными либо accessor-свойство; новый `defineProperty` по умолчанию задаёт флагам `false`. Getter и setter выполняют код с получателем операции в роли `this`, поэтому чтение свойства не всегда является простой операцией.

### Уровни целостности

> `preventExtensions` запрещает новые собственные свойства, `seal` дополнительно запрещает удаление и большинство переопределений, а `freeze` делает свойства с данными неизменяемыми. Все операции меняют тот же объект и дают поверхностную гарантию: вложенный объект, setter, приватное поле или внутреннее состояние встроенного объекта могут продолжать меняться. `const` отдельно фиксирует привязку имени.

### Proxy и Reflect

> Proxy перехватывает внутренние операции через специальные функции-перехватчики. Reflect помогает перенаправить стандартную операцию исходному объекту и сохранить получателя для getter и setter. Но Proxy имеет другую идентичность, не получает приватные поля и внутренние слоты исходного объекта и обязан соблюдать инварианты. Поэтому я использую его для общего перехвата или виртуализации, а несколько известных действий выражаю явной обёрткой, которую легче тестировать и отлаживать.

- [ ] Оцениваю размещение состояния и стоимость функций каждого экземпляра.
- [ ] Не использую `constructor` или `instanceof` как универсальную проверку внешних данных.
- [ ] Выбираю композицию или явную обёртку, когда их контракт проще.
- [ ] Не обещаю секретность из-за enumerability или Symbol.
- [ ] Сохраняю границы с 1.3 и 1.5.

## Связанные inventory IDs

| Inventory ID | Покрытие в этой главе |
|---|---|
| `JS-23` | литерал объекта, фабрика, функция-конструктор, `Object.create`, класс и выбор подхода |

| `JS-25` | объявления и выражения классов, методы и поля, `extends`, `super`, статические и приватные элементы |
| `JS-26` | собственные и унаследованные свойства, перечислимость, строковые ключи и ключи Symbol, проверка и перечисление |
| `JS-27` | дескрипторы свойств с данными и accessor-свойств, значения по умолчанию, getter, setter и получатель |
| `JS-28` | `preventExtensions`, `seal`, `freeze`, ошибки строгого режима и поверхностные гарантии |
| `JS-39` | Proxy/Reflect, перехватчики, получатель, инварианты, идентичность, отзыв и выбор API |

Ограниченные cross-references:

- `JS-16–JS-18`: правила `this`, `call` / `apply` / `bind`, возможность вызова через `new` и базовый `new` используются как мост из одобренной 1.3 и не учитываются повторно.
- `JS-29–JS-34`: массивы, копирование, глубокое клонирование и `structuredClone` остаются в 1.5.
- `JS-37`: ключи Symbol используются только как ключи свойств; well-known symbols остаются в 1.6.
- `SEC-17`: словарь с `null`-прототипом упомянут в объектной модели; полная защита от загрязнения прототипа остаётся в разделе о безопасности.
