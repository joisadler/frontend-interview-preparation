Эта глава помогает ответить на три вопроса: **что выполняется сейчас, что сможет начаться следующим и когда браузер получит возможность обновить интерфейс**. Из них собираются и задачи на порядок вывода, и объяснение зависшей страницы.

## Как читать эту главу

**🎯 Interview core:** вопросы 1–9, 11–13 и 15–20, 22. **🔬 Optional precision:** вопросы 10, 14 и 21. Сначала восстановите обычный браузерный сценарий; затем уточняйте границы модели.

```text
синхронный вызов → регистрация работы в среде → готовая задача
  → выполнение JavaScript → контрольная точка микрозадач
  → другие задачи и возможность обновить отображение
```

Это причинная схема, не обещание нарисовать кадр после каждой задачи. Каждый блок `js` независим; если указано «браузер», запускайте его в отдельном скрипте страницы. Переносимые блоки можно выполнять отдельным файлом в Node.js. Не вставляйте несколько блоков подряд в одну консоль: там могут отличаться внешнее выполнение и отображение результатов.

В примерах с очередями код запускается одной синхронной операцией. Предполагается завершение текущего вызова и работающая среда. Бесконечное зависание не запускается: пример истощения очереди намеренно конечный. Ожидаемые результаты приведены в учебной главе; для активного воспроизведения есть отдельные [вопросы](../../question-bank/by-domain/01-javascript-and-async-programming.md#19-event-loop--scheduling) и [условия](../../exercises/prompts/by-domain/01-javascript-and-async-programming.md#19-event-loop--scheduling).

## Ментальная модель

Представьте сотрудника, выполняющего одно обращение за раз. Внешняя служба может ждать доставку параллельно, но её уведомление не вырывает ручку у сотрудника посреди текущей записи. После записи есть короткий список обязательных уточнений; уточнения могут добавлять новые уточнения. Если этот список никогда не заканчивается, очередь посетителей не движется.

Аналогия объясняет текущую работу, задачи и микрозадачи. Она не описывает все потоки браузера и не задаёт период кадров. Главное различие: **готовность работы не равна немедленному запуску JavaScript**.

## Связное объяснение в формате вопросов и ответов

### 🎯 1. Что именно делает цикл событий?

**Цикл событий (event loop)** координирует запуск работы, когда среда может её выполнить. Сам JavaScript описывает выполнение функций и заданий языка; браузер предоставляет DOM, события, таймеры и правила согласования с отображением. Node.js предоставляет другую среду с собственным вводом-выводом и фазами.

Для одного обычного потока выполнения JavaScript две функции не исполняют свои инструкции одновременно. Но это не означает, что весь браузер — один поток: сеть, подготовка данных и другие агенты могут работать независимо. Рабочие потоки рассматриваются отдельно в 8.6.

Поэтому фраза «цикл событий выполняет сетевой запрос» неточна. Он участвует в доставке результата в JavaScript; саму сетевую работу организует среда.

### 🎯 2. Как стек вызовов связан с выполнением до завершения?

**Стек вызовов (call stack)** хранит вложенные активные вызовы. Обычный синхронный вызов идёт до возврата или исключения; готовый таймер не вставляет свой обработчик между двумя его инструкциями. Это называют **выполнением до завершения (run-to-completion)**.

Переносимый пример:

```js
console.log("start");
function outer() {
  console.log("outer");
  function inner() { console.log("inner"); }
  inner();
  console.log("back");
}
outer();
console.log("end");
```

Результат: `"start"`, `"outer"`, `"inner"`, `"back"`, `"end"`. Это вложенные вызовы, не пять задач. Пустой стек — необходимая часть модели перехода к отложенной работе, но не описание всей политики выбора следующей задачи.

Обычный синхронный код также может сам вызвать другую функцию, например обработчик через `dispatchEvent()`. Это вложенное выполнение, а не вмешательство таймера.

### 🎯 3. Что происходит при регистрации таймера?

Вызов `setTimeout` синхронно регистрирует работу в среде и возвращает идентификатор. Сам обработчик запускается позже, когда наступили условия таймера и среда выбрала его задачу.

```js
console.log("A");
setTimeout(() => console.log("timer"), 0);
console.log("B");
```

Результат: `"A"`, `"B"`, `"timer"`. Ноль не означает «вставить прямо сейчас». Пока текущий вызов занят, таймер ждёт, даже если его порог уже пройден. При этом регистрация не требует держать активный стек исходной функции до запуска обработчика.

### 🎯 4. Есть ли одна общая очередь всех событий?

Для браузера это слишком грубая модель. **Задачи (tasks)** поступают из разных **источников задач (task sources)**: таймеров, пользовательского ввода, сети и других механизмов. У цикла событий может быть несколько очередей; среда выбирает подходящую для выполнения работу, соблюдая необходимые правила порядка.

Схема «одна FIFO-очередь для абсолютно всего» не доказывает, кто победит между готовым сетевым уведомлением, таймером и обновлением отображения. Даже слово «событие» не означает новую задачу: часть событий вызывается внутри уже выполняющейся работы.

В интервью слово **macrotask** часто используют как неформальное противопоставление микрозадачам. В HTML Standard основное слово — `task`. Отдельной универсальной очереди с нормативным именем `macrotask queue` из этого не возникает.

### 🎯 5. Что такое микрозадача и когда её запускают?

**Микрозадача (microtask)** — работа, которую среда выполняет в специальных **контрольных точках (microtask checkpoints)**. В браузере к этому механизму привязаны реакции Promise и `queueMicrotask()`.

Для обычного учебного скрипта: сначала завершается синхронная работа, затем выполняются поставленные микрозадачи, прежде чем цикл перейдёт к следующей обычной задаче. Но это не таймер и не отдельный поток.

```js
console.log("sync");
queueMicrotask(() => console.log("micro"));
console.log("after");
```

Результат: `"sync"`, `"after"`, `"micro"`. Сам вызов `queueMicrotask` не прерывает текущую функцию. Поэтому микрозадача подходит для согласования состояния после текущего синхронного участка, но не для ожидания пользовательского ввода.

### 🎯 6. Весь ли Promise выполняется асинхронно?

Нет. Функция, переданная конструктору Promise, вызывается синхронно. Реакция `.then()` — отложенная работа, даже если обещание уже выполнено.

```js
console.log("A");
const ready = new Promise(resolve => {
  console.log("executor");
  resolve();
});
ready.then(() => console.log("reaction"));
console.log("B");
```

Результат: `"A"`, `"executor"`, `"B"`, `"reaction"`. Состояние обещания и запуск реакции — разные события. Если обещание ещё ожидает результата, реакция не становится готовой только от строки `.then()`.

Здесь достаточно этого различия для планирования. Полные правила состояний, цепочек, ошибок и комбинаторов остаются в 1.10.

### 🎯 7. Promise всегда раньше queueMicrotask?

Для готовых реакций в браузере важен порядок постановки, а не название API. Не нужно изобретать постоянный приоритет «все Promise, потом все `queueMicrotask`».

```js
const log = [];
queueMicrotask(() => log.push("q1"));
Promise.resolve().then(() => log.push("p"));
queueMicrotask(() => log.push("q2"));
setTimeout(() => console.log(log), 0);
```

Массив — `["q1", "p", "q2"]`. Если переставить регистрацию первых двух готовых работ, изменится и их порядок. Если Promise ожидает таймера, его реакция попадёт в очередь только после завершения ожидания; это уже другой граф причин.

### 🎯 8. Что значит «очередь микрозадач опустошается»?

Контрольная точка не ограничивается снимком очереди на входе. Микрозадача может добавить новую микрозадачу, и она тоже будет обработана до завершения этой контрольной точки.

```js
const log = [];
queueMicrotask(() => {
  log.push("m1");
  queueMicrotask(() => log.push("m3"));
});
queueMicrotask(() => log.push("m2"));
setTimeout(() => { log.push("timer"); console.log(log); }, 0);
```

Результат: `["m1", "m2", "m3", "timer"]`. В момент добавления `m3` перед ней уже стоит `m2`. Появление новой микрозадачи не отправляет её в стек немедленно и не заставляет ждать отдельного прохода с таймером.

### 🎯 9. Где выполнить микрозадачу, созданную внутри таймера?

Не надо сначала выполнить все таймеры и только потом все микрозадачи. После завершения первого обработчика среда проходит соответствующую контрольную точку.

```js
const log = [];
setTimeout(() => {
  log.push("t1");
  queueMicrotask(() => log.push("m"));
}, 0);
setTimeout(() => { log.push("t2"); console.log(log); }, 0);
```

Для этих двух зарегистрированных подряд таймеров результат — `["t1", "m", "t2"]`. Порядок двух таймеров здесь задан одной средой и одинаковой задержкой; это не правило сортировки произвольных источников задач.

### 🔬 10. Микрозадачи запускаются только в конце большой задачи?

Нет, это полезное первое приближение, а не универсальная граница. Браузер проверяет микрозадачи и при определённых возвратах из вызовов JavaScript, когда стек контекстов пуст. Поэтому реальные события среды и синхронный `dispatchEvent()` не всегда дают одинаковые границы между несколькими обработчиками.

Небольшой браузерный пример с **синхронной** отправкой:

```js
const target = new EventTarget();
const log = [];
target.addEventListener("ping", () => {
  log.push("listener");
  queueMicrotask(() => log.push("micro"));
});
log.push("before");
target.dispatchEvent(new Event("ping"));
log.push("after");
setTimeout(() => console.log(log), 0);
```

Получим `["before", "listener", "after", "micro"]`: внешний синхронный вызов ещё не завершился во время обработчика. Не переносите этот тест на любое реальное пользовательское событие. И не обещайте атомарность произвольной последовательности нескольких браузерных вызовов на основании одного лозунга про «целую задачу».

### 🎯 11. Почему микрозадачи могут заморозить страницу?

Если каждая микрозадача добавляет следующую без остановки, контрольная точка не заканчивается. Другие задачи не получают очередь; обновление интерфейса тоже задерживается. Это **голодание (starvation)**.

Безопасная конечная демонстрация, переносимая:

```js
const log = [];
let count = 0;
function step() {
  log.push(++count);
  if (count < 3) queueMicrotask(step);
}
queueMicrotask(step);
setTimeout(() => { log.push("timer"); console.log(log); }, 0);
```

Результат: `[1, 2, 3, "timer"]`. Рекурсивный вызов здесь не переполняет обычный стек, потому что каждый обработчик возвращается. Это не делает бесконечную версию безопасной для цикла событий.

Цепочка `await` уже выполненных Promise также не является надёжной передачей управления обычным задачам и отрисовке. Синтаксическая асинхронность сама по себе не даёт интерфейсу время.

### 🎯 12. Как разбить длинную работу, чтобы другие задачи получили шанс?

Нужно завершать ограниченные порции и планировать продолжение обычной задачей. Для маленького переносимого примера достаточно `setTimeout`; точная величина задержки не является гарантией отзывчивости.

`visit` и `onDone` ниже синхронны и не выбрасывают исключений. Массив не изменяется снаружи до завершения. Каждый отдельный `visit` должен быть коротким.

```js
function processChunks(items, visit, batchSize, onDone) {
  if (!Number.isInteger(batchSize) || batchSize < 1) {
    throw new RangeError("Positive integer batchSize required");
  }
  let index = 0;
  let active = true;
  let timer = null;
  function stop() {
    if (!active) return;
    active = false;
    if (timer !== null) clearTimeout(timer);
    timer = null;
    items = null; visit = null; onDone = null;
  }
  function step() {
    timer = null;
    if (!active) return;
    const end = Math.min(index + batchSize, items.length);
    while (active && index < end) visit(items[index++]);
    if (!active) return;
    if (index < items.length) {
      timer = setTimeout(step, 0);
    } else {
      const done = onDone;
      stop();
      done();
    }
  }
  timer = setTimeout(step, 0);
  return stop;
}
```

Функция возвращает отмену до первой порции; повторная отмена безопасна. Между порциями возникают границы задач. Порция из ста очень дорогих операций всё ещё может надолго занять поток — число элементов не равно бюджету времени.

Это учебный механизм планирования, не универсальная очередь заданий. Более мощные средства уступки управления и рабочие потоки остаются в 8.2 и 8.6; ограничение параллелизма — в 1.11.

### 🎯 13. Почему setTimeout(fn, 10) может сработать заметно позже?

Задержка задаёт порог допуска, а не момент начала. Пока JavaScript занят, обработчик не начнётся. Добавляются другие задачи, политика среды и ограничения платформы.

Браузер. Короткая намеренная блокировка для демонстрации; точное число миллисекунд не предсказывается:

```js
const log = [];
const start = performance.now();
setTimeout(() => {
  log.push("timer");
  console.log(log, performance.now() - start);
}, 0);
while (performance.now() - start < 8) { /* учебная блокировка */ }
log.push("sync finished");
```

Первое содержимое массива — `["sync finished", "timer"]`. Числовой результат — измерение конкретного запуска, не постоянная `8` или `0`. Даже если среда закончила ожидание раньше, занятый поток задержит вызов.

### 🔬 14. Всегда ли минимальная задержка таймера равна четырём миллисекундам?

Нет. HTML задаёт конкретное правило вложенности: если уровень вложенности таймерной инициализации **больше 5**, задержка меньше 4 мс поднимается до 4 мс. Это относится и к повторяющимся таймерам, а не только к тексту вложенных функций.

Это **ограничение минимальной задержки (timer clamping)**, а не обещание точного периода. Дополнительные ограничения среды могут быть строже. Первая регистрация `setTimeout(fn, 0)` не обязана проходить тот же порог, что длинная цепочка таймеров.

Для проверки различайте нормативное условие, измеренные интервалы и точность часов. Не пишите тест, который требует строго `4.000` мс на определённом тике. Нельзя подтверждать браузерное правило измерением таймеров Node.js.

### 🎯 15. Что меняется в фоновой вкладке?

Браузер может ограничивать частоту таймеров, объединять пробуждения, приостанавливать часть работы. Политика зависит от реализации, видимости, энергосбережения и состояния страницы. Поэтому «интервал всегда вызывает функцию раз в секунду» неверно даже при короткой функции.

Публикация Chrome о версии 88 объясняет механизм усиленного ограничения цепочек, но её пороги нельзя выдавать за универсальный договор всех текущих браузеров. В рабочем коде проектируйте восстановление по актуальному времени и состоянию, а не пытайтесь обойти ограничение нулевыми таймерами.

Изменение видимости — повод пересчитать отображение, но не доказательство, что браузер уже применил конкретный режим ограничения. Искусственная смена флага в тесте не воспроизводит часы работы настоящей фоновой вкладки.

### 🎯 16. Как отличить число тиков от прошедшего времени?

**Дрейф таймера (timer drift)** — отклонение фактических вызовов от ожидаемого расписания. Если при каждом тике уменьшать счётчик на единицу, пропуски и задержки превратятся в неверное время на экране.

Для локального отсчёта задайте конечный момент и вычисляйте остаток при каждом обновлении. В браузере `performance.now()` подходит для измерения интервала в рамках одного времени жизни страницы; для календарных сроков, перезагрузки и серверной истины нужен другой договор часов.

```js
function remainingSeconds(deadline, now) {
  return Math.max(0, Math.ceil((deadline - now) / 1000));
}
console.log(remainingSeconds(5000, 1200)); // 4
console.log(remainingSeconds(5000, 4900)); // 1
console.log(remainingSeconds(5000, 7300)); // 0
```

Входы — конечные отметки одних часов в миллисекундах. Даже если обновление пришло с опозданием, результат соответствует этим отметкам. Это исправляет расчёт, но не заставляет экран обновляться во время приостановки страницы. Периодический опрос сети требует отдельного решения о перекрывающихся запросах и остаётся в 1.11.

### 🎯 17. Что обещает requestAnimationFrame?

`requestAnimationFrame` (**rAF**) запрашивает одно выполнение функции при подходящем обновлении отображения. Оно предназначено для согласования визуальной работы с браузером, обычно до предстоящей отрисовки. Для продолжения анимации нужно запросить следующий вызов.

Браузер; `node` — подключённый DOM-элемент:

```js
function scheduleMark(node) {
  return requestAnimationFrame(() => { node.dataset.frame = "ready"; });
}
```

Запрос возвращает идентификатор, который можно передать `cancelAnimationFrame`. Сохранение ID и завершение владельца по-прежнему важны. Отмена ожидающего вызова не откатывает уже выполненные изменения.

rAF не означает «пользователь уже увидел пиксели» и не обещает работу в фоновой вкладке. Он также не выделяет тяжёлому вычислению отдельный поток: длинная функция в rAF задержит кадр.

### 🎯 18. Почему движение надо считать по времени кадра?

Частота обновления не обязана быть 60 Гц. Если прибавлять по два пикселя за вызов, на разных экранах изменится скорость. Браузер передаёт rAF временную отметку; от неё удобно вычислять положение.

Браузер, `node` — элемент, которым единолично управляет эта анимация. Длительность положительна и конечна; скорость конечна и выражена в пикселях за секунду. Началом считается первый вызов кадра.

```js
function animateX(node, duration, speed) {
  if (!Number.isFinite(duration) || duration <= 0 || !Number.isFinite(speed)) {
    throw new RangeError("Finite speed and positive duration required");
  }
  let active = true;
  let first = null;
  let frame = null;
  function stop() {
    if (!active) return;
    active = false;
    if (frame !== null) cancelAnimationFrame(frame);
    frame = null;
    node = null;
  }
  function tick(now) {
    frame = null;
    if (!active) return;
    if (first === null) first = now;
    const elapsed = Math.min(now - first, duration);
    node.style.transform = `translateX(${speed * elapsed / 1000}px)`;
    if (elapsed < duration) frame = requestAnimationFrame(tick);
    else stop();
  }
  frame = requestAnimationFrame(tick);
  return stop;
}
```

Пропуск кадра меняет шаг положения, но не формулу скорости. В этом варианте после долгой паузы анимация догонит конечный момент; если продукт должен замораживать анимационное время при скрытии, нужна явная политика паузы.

В тесте можно подать разные последовательности временных отметок и проверить одинаковое положение в одинаковый момент. Это проверяет формулу; настоящий браузер отдельно проверяет регистрацию и выполнение кадров.

### 🎯 19. Как объединить несколько обновлений в один кадр?

Если много событий меняют одно визуальное значение, можно хранить последнее значение и иметь не более одного ожидающего rAF. Пока кадр не начался, новые события заменяют данные, а не добавляют ещё один вызов.

Важна точка сброса ID: перед применением значения текущий запрос уже не ожидает выполнения. Если обработчик сам запланирует следующее изменение, оно должно попасть в новый запрос. При завершении нужно отменить запрос и убрать ссылку на тяжёлые данные.

Это объединение визуальных обновлений, не реализация универсального throttle или debounce. Такие договоры остаются в 1.11. Реализация и проверка последнего значения — в [EX08](../../exercises/prompts/by-domain/01-javascript-and-async-programming.md#js-loop-ex08).

### 🎯 20. Гарантирует ли задача или rAF, что DOM уже нарисован?

Изменение DOM синхронно меняет модель документа. Показ пикселей — отдельная работа. Браузер может объединить несколько изменений и не показать промежуточное состояние.

Например, установка надписи «Загрузка» с последующим длинным синхронным вычислением может не дать пользователю увидеть надпись вовремя. Перенести вычисление в микрозадачу недостаточно. Передача управления обычной задачей создаёт возможность планирования, но не обещание обязательного показа конкретного кадра.

rAF полезен для подготовки визуального обновления, а не как стандартный «после paint». Вложенный rAF запрашивает последующее выполнение кадров, но не является доказательством физического показа пикселей. Чтение геометрии может заставить браузер синхронно пересчитать стили или раскладку; это тоже не то же самое, что законченный показ.

<details>
<summary>🔬 Точная деталь: текущая модель стандарта</summary>

В проверенном HTML Living Standard обновление отображения планируется через отдельный источник задач `rendering task source` при подходящей возможности. Поэтому популярная картинка «task → microtasks → paint в каждом обороте» — учебное упрощение. Для практического ответа достаточно сохранить причинные ограничения: не прерывать занятый JavaScript, учитывать микрозадачи и не обещать кадр после каждой задачи.

### 🔬 21. Можно ли перенести браузерную схему целиком в Node.js?

Нет. Общие примеры `синхронный код → готовые микрозадачи → таймер` полезны и там, но у Node.js есть фазы ввода-вывода, `setImmediate()` и отдельный механизм `process.nextTick()`. В обычном Node.js нет браузерного этапа показа документа.

Порядок `setTimeout(..., 0)` и `setImmediate()` вне конкретного контекста нельзя объявлять универсально фиксированным. Не добавляйте `nextTick` в ту же очередь, что Promise: контекст CommonJS, ESM и вложенной микрозадачи имеет значение. В новом коде для обычного переносимого откладывания микрозадачи полезно понимать `queueMicrotask`, а `nextTick` знать для Node-совместимости.

Здесь это обзорная граница среды. Полный курс libuv, тонкая матрица фаз и серверная оптимизация не входят в раздел 1.9. Если задача просит точный вывод с Node-специфичными API, сначала фиксируйте версию и режим запуска.

### 🎯 22. Как спокойно решать задачу на порядок вывода?

Сначала подпишите среду и точку входа. Затем пройдите синхронный код, отдельно записывая готовые микрозадачи и регистрации будущих задач. Не считайте реакцию ожидающего Promise уже поставленной в очередь.

Переносимый пример с готовым Promise:

```js
const log = ["sync"];
setTimeout(() => { log.push("timer"); console.log(log); }, 0);
Promise.resolve().then(() => {
  log.push("promise");
  queueMicrotask(() => log.push("nested"));
});
queueMicrotask(() => log.push("micro"));
log.push("end");
```

Результат: `["sync", "end", "promise", "micro", "nested", "timer"]`. После синхронной части очередь содержит реакцию и `micro`; реакция добавляет `nested` в конец. Таймер начинает свой обработчик после этой контрольной точки.

Если данных недостаточно, ответом может быть **частичный порядок**: некоторые действия обязаны предшествовать другим, а взаимный порядок независимых источников не задан. Честно объяснить эту границу лучше, чем угадать случайный журнал одного запуска.

## Краткий справочник

| Механизм | Что вспоминать |
|---|---|
| Стек | Вложенные активные вызовы; занятый код не прерывается готовым таймером |
| Задача | Работа среды; разные источники не образуют одну универсальную FIFO-очередь |
| Микрозадача | Контрольные точки; новые микрозадачи тоже опустошаются; возможное голодание |
| Promise | Исполнитель конструктора синхронный; готовая реакция отложена |
| Таймер | Порог допуска, не срок исполнения; ограничения, фон и занятый поток дают задержки |
| Время | Считать от отметок/конечного момента; число тиков не равно прошедшим секундам |
| rAF | Один визуальный вызов; временная отметка, повторная регистрация и явная отмена |
| Отображение | Изменение DOM и геометрия не доказывают физический показ кадра |

## Типичные ошибки

- Говорить, что таймер ждёт в стеке или прерывает текущую функцию.
- Называть весь Promise асинхронным или ставить ещё не готовую реакцию в очередь.
- Давать всем Promise постоянный приоритет над `queueMicrotask`.
- Опустошать микрозадачи только один раз до появления вложенных.
- Заменять длинную задачу цепочкой микрозадач и считать проблему отзывчивости решённой.
- Измерять секунды количеством вызовов интервала или обещать ровно 4 мс.
- Считать rAF таймером на 16 мс, отдельным потоком или уведомлением после показа.

## Ловушки на интервью

- Вложенный синхронный обработчик — не обязательно отдельная задача.
- Контрольные точки бывают и на границах вызовов среды, а не только в конце большого скрипта.
- Между двумя таймерами может выполниться микрозадача первого.
- Одинаковая строка журнала в одном запуске не доказывает порядок разных источников.
- Фоновая вкладка не обязана поддерживать частоту таймера или анимации.
- Возможность отрисовки не означает обязательный показ каждого промежуточного DOM-состояния.

## Практические рекомендации

Сначала сокращайте длинные синхронные участки. Для микрозадач выбирайте короткую работу согласования; для порций вычислений создавайте настоящие границы задач. Не используйте микрозадачи для бесконечного опроса. Задавайте отмену ожидающего таймера и кадра у владельца.

Текущее время отделяйте от частоты обновления. Для визуального движения используйте временные отметки; для большого вычисления внутри одного кадра ищите другой способ разбить или вынести работу. Политику фоновой вкладки не превращайте в числовую гарантию продукта.

Экспериментальные средства планирования в обязательный маршрут не добавлены. Node-специфичные механизмы и точные внутренние шаги стандарта имеют обзорную глубину. Исторические публикации браузеров объясняют мотивацию ограничений, но не заменяют проверку текущей целевой среды.

## Как объяснить тему на интервью за 30–60 секунд

### Выполнение и среда

> JavaScript выполняет обычный вызов до завершения. Сеть и таймеры организует среда; готовность их результата не прерывает занятый поток. Цикл событий выбирает подходящую работу. В браузере есть разные источники задач и отдельные контрольные точки микрозадач, поэтому одна FIFO-очередь для всего — слишком грубая модель.

### Микрозадачи

> Реакции готовых Promise и `queueMicrotask` выполняются после текущей синхронной работы в контрольной точке. Важен порядок постановки. Если микрозадача добавила ещё одну, она тоже попадёт в этот проход. Поэтому бесконечная цепочка не даст задачам и интерфейсу времени. Сама функция конструктора Promise при этом вызывается синхронно.

### Таймеры

> Задержка таймера задаёт допуск, а не точное время запуска. Мешают занятый поток, другие задачи, ограничение вложенных таймеров и политика фона. Отсчёт времени я вычисляю по отметке конечного момента, а не уменьшаю на единицу при каждом тике. При завершении отменяю принадлежащий мне таймер.

### Кадры

> rAF запрашивает один вызов для подходящего обновления отображения. Для движения использую его временную отметку, иначе скорость будет зависеть от частоты экрана. Длинный обработчик всё равно блокирует кадр. rAF не обещает работу в фоне и не является уведомлением, что пользователь уже увидел пиксели; ожидающий запрос нужно уметь отменить.
