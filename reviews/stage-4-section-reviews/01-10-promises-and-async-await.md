### Real Fetch fixture and limits

A temporary Python standard-library HTTP server ran only on `127.0.0.1`, outside the repository. Native Fetch checked JSON success, HTTP 503, invalid JSON, pre-abort and cancellation before headers. A streaming endpoint sent headers and an incomplete JSON prefix, then waited for an explicit release endpoint; instrumentation cancelled after a real Response arrived, before releasing the body. The actual getJson fences rejected with AbortError. This uses a causal gate, not a fragile sleep duration or fabricated Response.

A separate instrumented read of a real response aborts after JSON parsing to verify the explicit throwIfAborted boundary. That controlled read hook is distinguished from network timing. EX12 also runs with a real Fetch-backed profile/notices adapter. The server was stopped after verification; no permanent backend or project infrastructure was added. Initial sandbox binding was denied, then standard approved execution allowed the loopback fixture.

The intentional browser rejection is generated by an actual unhandled Promise, not manual event dispatch. A later task attaches catch to exercise the late-handled notification. Browser default reporting is suppressed only for this expected failure; normal outcome handlers are part of their actual examples or assertions. Node's expected failure is isolated and does not terminate the main audit.
